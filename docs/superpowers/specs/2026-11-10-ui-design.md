# UI toolkit design (Phase 15)

Status: decided 2026-11-10 (Day 184) from the spikes in section 12. Scope: the engine's retained-mode widget toolkit, its CPU draw list, the renderer pass that draws it,
platform input events, pointer lock, cursors, the OS clipboard and drag and drop, the viewport widget and UI surfaces (render-to-texture). The phase file
(`plans/phase-15-ui-system.md`) has the goals and the day list; this file records the decisions the days build on and why.

## 1. Modules

- **`engine/ui`** (library `ui`, namespace `vse::ui`, layer 11 beside the RHI): CPU only. The widget tree, surfaces, layout, themes, input routing, the draw list.
  It depends on `text` (layout, cursor, glyph atlas types), the platform's pure-data input headers (`platform_input`, an INTERFACE target: no Wayland, X11 or xkbcommon
  is linked) and the foundation. **No RHI type appears in it**: an image is a `ui::ImageId` (opaque 64 bits) that the renderer maps to a texture by owner.
- **`engine/renderer`** (layer 12) gains `UiRenderer` (Day 190), `ViewportTarget` (Day 201) and `UiSurfaceTarget` (Day 202) and links `ui` for the draw-list type.
- **`ui_window`** (a small library above `ui` and `platform`, Day 194): the only place a widget tree meets an `os::Window`. Widgets, layout, theme and draw code never name a window,
  so an offscreen surface is the normal test case, not a late add-on.

## 2. Coordinates and scale

Layout, themes and widget code work in **logical units**; a surface has a `scale` factor (1, 1.25, 2...). The draw list is in **physical pixels**: rectangles are snapped to whole
pixels when drawn, and borders, paddings and strokes round to whole pixels after scaling (a 1-unit border is 1 pixel at 1x and 2 at 2x, never 1.5). Pointer input from a window
arrives in physical pixels and is divided by the scale; a viewport receives its pointer in its own physical pixels (documented).

## 3. The tree

Widgets are classes with `UniquePtr` children, a parent pointer and a 32-bit **id** (a hash of the parent id and a name or index), so ids survive a rebuild that uses the same names.
State lives in the widget. Dirty flags (layout, draw) propagate to the root. Tree mutation during event dispatch is deferred to the end of the dispatch, so a widget may remove itself
in its own click handler. Destroying a widget with focus, capture or hover clears those references on the surface first.

## 4. Events

One `ui::Event` type (pointer move/down/up/enter/leave in the receiving widget's local space, wheel, key down/up with a repeat flag, text, focus, drag events, tick) with a `handled`
flag and a timestamp from the surface clock. **`ui::Key` is an alias of `os::Key`** (Day 184 amendment: the plan had a separate enum with a `static_assert` table; since `ui` includes
the platform input header anyway, a second enum would only duplicate the list). The platform side has two layers: the polled `os::InputState` stays, and a bounded event queue
(`Window::PollEvent`, Day 185) is what the UI reads, because a poll cannot see a press and release between two frames and has no text or repeat.

## 5. The frame

`Surface::Frame(dt)`: apply queued events, `Update` of the few widgets that animate (caret blink, tooltips, progress bars, auto-scroll), layout if dirty, then the draw list is rebuilt
if anything is dirty (`NeedsRedraw()` is what an on-demand offscreen surface reads). Main thread only; the job system may do asset and font work off thread but never mutates a widget.

## 6. The canvas and the draw list

**`ui::Canvas` is what widgets draw on** (amendment of 2026-11-10): an abstract class in logical units (rect, rounded rect, border, line, triangle, image, text, shadow, clip stack, layers, `Scale()`), with no draw-list or GPU type in it. `ui::DrawListCanvas` is the implementation that converts to physical pixels (snapping as section 1 says) and appends to a `DrawList`; `ui::RecordingCanvas` (tests) records the calls. A new kind of canvas (vector paths, a software rasteriser, an exporter) is added without changing any widget. The rest of this section describes the draw list, the data the `DrawListCanvas` builds.

`ui::DrawList` owns `Vector<Vertex>`, `Vector<u32>` (32-bit indices) and `Vector<DrawCommand>`; `Clear()` keeps capacity so a steady frame allocates nothing.

- **Vertex (40 bytes):** position (2 floats, physical pixels), uv (2), packed RGBA color, the rounded-rect parameters (half width, half height, corner radius, border width) and a
  `flags` word whose low bits select the **mode**: rectangle (signed-distance function), textured coverage (a glyph from an R8 atlas page) or textured color (an image).
  Because the mode is per vertex, rectangles and glyphs of one frame use the same bound texture, and a command is split only by the clip rectangle, the atlas page or the image.
- **Commands** carry an index range, a clip rectangle and the texture (an atlas page or an `ImageId`); consecutive draws with equal state merge.
- **Layers:** `BeginLayer(order)` so popups, tooltips and drag visuals draw above everything regardless of visit order; layers sort by order, stable within an order.
- **Clip stack:** `PushClip`/`PopClip` intersect; an empty intersection drops the draw before any vertex is made.
- **Text** goes in as glyph quads from `text::PositionedGlyph` and the glyph atlas, placed on whole pixels as `TextRenderer` does. Text above 128 px scales from the 128 px raster (the Phase 14 rule).
- **Determinism:** the same input gives the same bytes (a golden of the data for a fixed scene).

## 7. Rounded rectangles and borders: one SDF quad

A rounded rectangle with a border is **one quad (4 vertices, 6 indices)** whose fragment shader evaluates the signed distance to the rounded box and shades the fill and the border
with analytic anti-aliasing from the distance (the derivative of the distance gives one pixel of ramp). Per-corner radii pass as the radius of the nearest corner picked from the
quad-local position. Tessellating the corners costs about 18 times the vertices and 95 times the CPU time (section 12, spike A), needs a second ring of triangles for every border, and its edge is
only as smooth as the segment count (anti-aliasing would need extra geometry or multisampling). One pipeline draws every shape; drop shadows are a larger SDF quad with a blurred edge falloff.

## 8. Themes

A `Theme` is plain data: named colors, metrics (padding, spacing, border width, corner radius, scrollbar thickness, minimum hit size), fonts, and **style entries** per widget kind and
variant name with a table over the states (normal, hover, pressed, focused, disabled, checked). Resolution walks a chain: the widget's own override, the nearest ancestor's, the
surface's theme, then the built-in default. A theme is swapped at run time by `Surface::SetTheme`, which bumps a revision; widgets re-resolve lazily on the next draw, with no rebuild of
the tree. Light and dark are two ordinary `Theme` values. Widgets draw only from the theme (Day 195 adds a test that fails on a literal color or pixel metric in widget sources). Custom
widgets register a kind with the open `WidgetKind` registry and read the same data. A theme loads from a data file in Phase 22; until then it is built in code.

## 9. Surfaces

A `Surface` owns the root widget, size, scale, clock, theme pointer, font provider, focus owner, pointer-capture owner and popup layer. A window feeds a surface through `ui_window`; the
application feeds an in-world surface directly with `SurfaceInput` (for example from a ray cast, using the math-only `RayToSurfacePoint` helper in `ui`). Update policy per offscreen
surface: every frame, on demand, or at a fixed rate; an idle on-demand surface adds no pass and no GPU work. Resize is coalesced to once per frame everywhere (the Phase 1 Wayland
lesson). Offscreen targets are rebuilt through `DeviceResources` after a reset and destroyed through the device's deferred destruction.

## 10. Platform additions (Wayland, X11; Win32 on Day 205)

An input event stream with client-side key repeat on Wayland (the compositor does not repeat for clients) and text from XKB (Day 185); cursor shapes, custom cursor images, pointer
lock and relative motion (Day 186); the OS clipboard (Day 187); OS drag and drop (Day 188). Every operation has a default that reports "unsupported" so Win32 and macOS compile, a
`Supports...()` query so the UI can degrade, and a section in `engine/platform/BACKEND.md`. Everything that waits for another program is asynchronous with a timeout (clipboard
requests 2 s, drops 1 s) so the UI never hangs on a stuck peer, and data from other programs is untrusted: UTF-8 validated, lengths capped, `file://` lists parsed strictly.

## 11. Decisions that are not features

- **Clipboard:** the OS clipboard is implemented (Day 187) and wired into the text field on Day 200; an in-process clipboard stays behind the same asynchronous interface for offscreen
  surfaces and tests. The paste interface is asynchronous from the first day the text field exists (Day 197), so the OS clipboard changes nothing in the field.
- **Word movement** is not in `text/cursor.h` (spike C). The text field implements it in `ui` over the cluster boundaries: a word is a run of letters/digits/underscore (by the
  foundation's character classes), runs of punctuation are words of their own, and whitespace is skipped; it stays in `ui` because only editing widgets use it.
- **Settings:** nothing in the toolkit is user configuration; `ui_demo`'s window and test options are launch-only options in `config_access_check`'s allow list, and the rendering
  settings it shows come from the settings system. A UI scale setting, if wanted later, is declared with `settings::Registry` then.
- **Non-goals:** docking, IME and complex-script input, accessibility tree, file dialogs (Phase 32), tree view (Phase 32 if needed), multi-line text editing (a stretch in the
  phase file, not scheduled), scroll inertia, mipmaps for in-world surfaces, VR interaction rays.

## 12. Spikes (Day 184; throwaway programs in the scratchpad, not committed)

All timings are single-threaded on the development machine, best of 50 repetitions, plain `clang++ -O2`.

**A. Rounded rectangles with borders, 2,000 of them (18x18 units, radius 4, 1-unit border):**

| Method | Vertices | Bytes (vertex data) | Indices | Build time |
|---|---|---|---|---|
| SDF quad | 8,000 | 288,000 (36 B/vertex before the flags word) | 12,000 | 11 us (0.006 us/rect) |
| Tessellated (8 segments per corner, fill fan plus border ring) | 148,000 | 2,960,000 (20 B/vertex) | 432,000 | 1,044 us (0.52 us/rect) |

The SDF quad wins on every axis the numbers can show; edge quality at fractional scales follows from the analytic distance, and is checked by eye on the golden of Day 190.

**B. A frame of 2,000 widgets (2,000 rectangles and 6,000 glyph quads), 32-bit indices:** 32,000 vertices (1.1 MB at 36 B, 1.25 MB with the 40-byte vertex), 48,000 indices,
**61 us** to build. With the mode in the vertex, the 8,000 quads share one texture and merge into 10 commands (one per clip change); with a separate texture for rectangles and for
glyphs, the same frame alternates and needs 4,000 commands, which is why the mode is per vertex (section 6). Layout, atlas lookups and event handling are not in this number.

**C. What `text/cursor.h` gives a text field** (a throwaway program over `Layout`, `NextBoundary`, `PreviousBoundary`): forward and backward boundaries agree for ASCII, a letter with a
combining acute (`a e U+0301 z`: offsets 0 1 4 5), a pair of regional indicators (a flag: 0 1 9 10), a ZWJ family sequence (0 1 19 20), a Hangul jamo syllable (0 9 10) and CRLF
(0 1 3 4): every cluster is one step both ways. Missing: word movement and word selection (the cursor header says so), so the field implements them (section 11).
