# Documentation Conventions

## Three layers

1. **Reference** (`reference/`) — generated by our own `docgen` tool
   (Phase 2.5) from `///` comments on public headers. Facts only: signature, contract, thread-safety, ownership,
   failure behavior.
2. **Guide** (`guide/`) — one page per subsystem: the mental model, the
   rules you must not break, how the pieces fit, common mistakes.
3. **Tutorials** (`tutorials/`) — a goal, numbered steps, complete code
   that compiles, expected output.

## Page template (guide pages)

Overview → Concepts → Usage → Rules & contracts (lifetime, threading,
ownership, failure) → Common mistakes → Performance notes → Platform
notes → See also.

## Rules

- Every code sample compiles. Samples are meant to be extracted and built
  by a docs test target (not wired up yet).
- Contracts that the code asserts (`ENGINE_ASSERT`) are documented as
  "aborts if…", never "undefined".
- State thread-safety and ownership for every type that crosses threads.
- Link to the header, not to a line number.
- Mark unwritten sections `_TODO_`; a page with any `_TODO_` keeps the
  `skeleton` status line.

## Status values

`skeleton` (outline only) → `draft` (written, unreviewed) → `reviewed`
(checked against the code at a named commit).

## Proposed definition of "documented" for an implementation day
*(not yet in CLAUDE.md — needs the user's approval)*

A day that adds or changes public API is done only when its headers have
`///` comments and the relevant guide page is updated or created; the
day file's Done condition lists the pages.
