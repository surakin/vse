# Documentation Conventions

Authoritative for how engine documentation is written. The tool that
enforces it is `docgen` (Phase 2.5; design in `tools/docgen/DESIGN.md`).

## Three layers

1. **Reference** (`reference/`) — generated by our own `docgen` tool from
   `///` comments on public headers. Facts only: signature, contract,
   thread-safety, ownership, failure behavior. Never hand-edited.
2. **Guide** (`guide/`) — one page per subsystem: the mental model, the
   rules you must not break, how the pieces fit, common mistakes.
3. **Tutorials** (`tutorials/`) — a goal, numbered steps, complete code
   that compiles, expected output.

Guide pages follow: Overview → Concepts → Usage → Rules & contracts
(lifetime, threading, ownership, failure) → Common mistakes → Performance
notes → Platform notes → See also.

## Doc-comment grammar (headers)

### Where comments go

| Form | Meaning |
|---|---|
| `/// text` lines directly above a declaration | documents that declaration |
| `///< text` after a declaration on the same line | documents that declaration (used for enumerators and data members) |
| `//! text` lines before the first declaration | the file overview (page intro for the header) |

- A run of consecutive `///` (or `//!`) lines is one comment. A **blank line,
  or any other token, between the comment and the declaration detaches it**
  (warning `detached doc comment`).
- Plain `//` and `/* */` comments are ordinary comments; the tool ignores them.
- The marker is removed together with one following space.
- One doc comment per declaration. Documenting an overload set means
  documenting each overload.

### Text structure

- The **first paragraph is the summary**: one sentence, imperative or
  descriptive, ending in a period, no longer than 160 characters. It is
  required for every public declaration.
- Further paragraphs (separated by an empty `///` line) are details.
- Allowed markup: `` `inline code` ``, `-` bullet lists (continuation lines
  indented two spaces), fenced code blocks (``` with an optional language),
  and `[[Symbol]]` cross-references. Nothing else (no HTML, no headings).

### Contract labels

A line whose text starts with a label and a colon at column 0 of the
comment text begins a labeled field; indented following lines continue it.

| Label | Applies to | Content |
|---|---|---|
| `Param <name>:` | functions/methods/macros with parameters | meaning, units, ownership of the argument; `<name>` must be a real parameter name |
| `Returns:` | non-`void` functions | what is returned, including the failure value |
| `Fails:` | functions that report failure (null, `false`, error code) | when and how failure is reported |
| `Aborts:` | functions with an `ENGINE_ASSERT` precondition | the precondition whose violation aborts |
| `Thread-safety:` | classes/structs, free functions, methods when they differ from the class | begins with one **category** (below), then optional detail |
| `Ownership:` | anything that takes, returns or stores a raw pointer/handle, or owns a resource | who owns what and when it is released |
| `Example:` | any | followed by a fenced code block (compiled if tagged, see *Samples*) |
| `See:` | any | comma-separated `[[Symbol]]` references |
| `Deprecated:` | any | replacement and removal plan |
| `Internal:` | any | marks a declaration as not part of the public surface (excluded from the reference); text says why it is visible |

Each label appears at most once per comment (except `Param`, once per
parameter). Unknown labels are errors.

**Thread-safety categories** (first word, exact spelling):
`immutable` · `thread-safe` (any thread, concurrently) ·
`thread-compatible` (safe if externally synchronized) ·
`owner-thread-only` (one designated thread) · `single-consumer` ·
`not-thread-safe`.

### Visibility

Documented and listed in the reference: namespace-scope declarations in the
headers named by the module map, and `public:` members (struct members are
public by default). Excluded: anonymous namespaces, namespaces named
`detail`, `private`/`protected` members, anything labeled `Internal:`.
Excluded declarations need no documentation.

### Inheritance

A member marked `override` that has **no** doc comment inherits the summary
of the base declaration it overrides (shown as "Inherited from …"). If it has
a doc comment, that comment is used as written.

### Cross-references

`[[Name]]` resolves against the symbol index: `[[Counter]]`,
`[[jobs::Counter::Increment]]`, with an overload hint when ambiguous:
`[[jobs::Scheduler::HelpUntil(Counter&)]]`. Partially qualified names are
accepted if exactly one symbol matches. Unresolved or ambiguous references
are errors. The same syntax works in guide/tutorial Markdown.

## Samples

A fenced code block in a guide or tutorial is compiled when its info string
carries tags: ` ```cpp compile ` (compile only, inside the standard prelude),
` ```cpp compile standalone ` (a whole translation unit),
` ```cpp compile run ` (also run; an adjacent ` ```output ` block must match
stdout). Untagged blocks are illustrative and never built.

## Rules

- Contracts the code asserts (`ENGINE_ASSERT`) are documented as
  `Aborts:`, never "undefined".
- State thread-safety and ownership for every type that crosses threads or
  hands out resources.
- Link to the header path, not to a line number.
- Mark unwritten sections `_TODO_`; a page with any `_TODO_` keeps the
  `skeleton` status line.

## Page status values

`skeleton` (outline only) → `draft` (written, unreviewed) → `reviewed`
(checked against the code at a named commit).

## Proposed definition of "documented" for an implementation day
*(not yet in CLAUDE.md — decided on Day 44 with the user)*

A day that adds or changes public API is done only when its headers have
`///` comments that pass `docgen lint` and the relevant guide page is
updated or created; the day file's Done condition lists the pages.

## Worked example

```cpp
//! Counters: the join primitive of the job system.

/// Tracks outstanding work and lets one coroutine wait for it to finish.
///
/// Increment before submitting the work, decrement when it completes, and
/// `co_await` the counter to resume once the count reaches zero.
///
/// Thread-safety: thread-safe. Any thread may call [[jobs::Counter::Increment]]
///   and [[jobs::Counter::Decrement]]; at most one coroutine may await it.
/// Ownership: must outlive every pending decrement and the await.
/// See: [[jobs::Spawn]]
class Counter {
public:
    /// Adds `n` outstanding units of work.
    /// Param n: how many units to add.
    void Increment(u64 n = 1);

    /// Marks one unit done and, if it was the last, schedules the waiter.
    /// Aborts: the count is already zero.
    void Decrement();
};
```
