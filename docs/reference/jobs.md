Asynchronous file reads for jobs.

A blocking read must never occupy a compute worker, and the awaiting coroutine must never resume on an ad hoc thread. So reads run on one dedicated [`jobs::IoThread`](#jobs-iothread), a plain `std::thread` that is not a participant ([`jobs::WorkerPool::IsParticipantThread`](#jobs-workerpool-isparticipantthread) is false on it), started and stopped with the scheduler. Completion is [`jobs::Counter::Decrement`](#jobs-counter-decrement) called from the I/O thread, which, being a non-participant, hands the continuation to the scheduler's injection queue, so the coroutine resumes on a participant.

Usage inside a job:

```
FileReadResult r = co_await ReadFileAsync(scheduler, "path");
if (r.ok) { /* use r.data[0 .. r.size), owned by r */ }
```

The bytes live in an arena owned by the [`jobs::FileReadResult`](#jobs-filereadresult) and are freed when it is destroyed.

Shutdown drains: requests already queued are still executed, then the I/O thread is joined, and a read issued after that completes immediately with `ok == false`. Awaiting coroutines are only guaranteed to run if the caller joins its outstanding work before destroying the scheduler (see [`jobs::Scheduler::Shutdown`](#jobs-scheduler-shutdown)): the scheduler shuts the I/O thread down first, but a continuation still queued when the workers stop is destroyed unrun. A request blocked in the OS (an `open()` on a FIFO nobody writes to) blocks shutdown until the OS call returns. There is one I/O thread and one FIFO queue, so a slow request delays the ones behind it (head-of-line blocking); a pool of I/O threads can replace it later without changing the awaitable.

The join primitive of the job system.

A [`jobs::Counter`](#jobs-counter) tracks outstanding work; a coroutine `co_await`s it and is resumed once the count reaches zero.

The usage contract is as follows.

- All increments for a wait happen before the `co_await`: the spawner increments, then submits work that decrements (see [`jobs::Spawn`](#jobs-spawn-counter-amp-job-amp-amp)).
- At most one coroutine awaits a counter at a time (asserted).
- The counter must outlive every decrement and the await. A typical placement is a local in the awaiting coroutine's frame.

The waiter is never resumed inline on the decrementer's stack: [`jobs::Counter::Decrement`](#jobs-counter-decrement) hands it to [`jobs::Scheduler::Schedule`](#jobs-scheduler-schedule-std-coroutine-handle-lt-gt), which pushes onto the current participant's deque, or onto the injection queue when called from a non-participant such as the I/O thread. That bounds native stack depth however deep a chain of dependent jobs is.

Whether the awaiter or a decrementer resumes the coroutine is decided by a single atomic read-modify-write on one state word, so exactly one of them resumes it, and neither touches the counter afterwards unless it owns the wake-up. The awaiter therefore cannot finish and destroy the counter while a decrementer still reads it.

A fixed-capacity Chase-Lev work-stealing deque of coroutine handles.

There is one deque per scheduler participant. The owner pushes and pops at the bottom (LIFO: hot and cache-friendly); thieves take from the top (FIFO: the oldest entry, likely the biggest subtree of work).

The algorithm is Chase and Lev, "Dynamic Circular Work-Stealing Deque" (2005), in the C11 formulation of Le et al. (2013), with one deliberate change: wherever the published algorithm places a standalone `atomic_thread_fence(seq_cst)`, the ordering is put on the neighbouring atomic operations instead (seq_cst loads, stores and CAS). That is slightly stronger than strictly necessary, but ThreadSanitizer does not model standalone fences and would report false races.

Capacity is a power of two and fixed: there is no resize. A push on a full deque fails and never overwrites; the scheduler then spills to its injection queue. The top index only ever increases and the bottom index is written only by the owner; both are 64-bit and never wrap in practice. Slot reuse (index & mask) is safe: a push writes slot b only when b - top < capacity, so the slot's previous occupant (index b - capacity) has already been consumed, and a thief that read a slot before losing its CAS discards the value. Changing the capacity or the full check must keep that argument true. Handles are stored as raw addresses and a null handle is never stored.

Awaitable adapters over the asynchronous operations of [`io::File`](foundation-io.md#io-file).

`co_await ReadAsync(scheduler, file, buffer, length, offset)` starts the read and parks the job; the continuation resumes on a scheduler participant, never on the I/O thread, as with [`jobs::ReadFileAsync`](#jobs-readfileasync-scheduler-amp-stringview-usize). The file does its work on its own executor (see [`io::SetDefaultExecutor`](foundation-io.md#io-setdefaultexecutor-ioexecutor-star); pass the scheduler's [`jobs::IoThread`](#jobs-iothread) so blocking reads stay off the workers).

The awaitables are not movable once created: await the temporary (`co_await ReadAsync(...)`).

The allocator behind coroutine frames.

Foundation's `PoolAllocator` is single-threaded, has one fixed slot size and returns null when full; job frames are allocated on one thread and freed on another, vary in size, and `operator new` must not return null. This pool therefore has:

- a few size classes, each a slab reserved up front (address space only; pages are committed as they are first touched), handed out by a bump pointer plus an intrusive free list of returned blocks, behind one central mutex;
- an optional per-thread cache (an intrusive free list per class, no synchronization) that refills from and spills to the central pool in batches. A block freed on a different thread than it was allocated on simply joins the freeing thread's cache, since blocks of one class are interchangeable;
- a counted libc `malloc` fallback for oversize requests or an exhausted class, so [`jobs::FramePool::Allocate`](#jobs-framepool-allocate-usize) never returns null.

Every block carries a 16-byte header (class index and magic) so deallocation routes pooled and fallback blocks without address-range checks and the returned pointer stays 16-byte aligned.

The job coroutine type.

A job is a C++20 coroutine returning [`jobs::Job`](#jobs-job); the scheduler resumes its handle on whichever worker picks it up. Jobs start suspended, so creating one runs no user code until it is submitted. Jobs return void: results travel through pointers to data that outlives the join.

Parameter lifetime. The compiler copies coroutine parameters into the frame, but a reference parameter stays a reference to the caller's object, and a lambda coroutine's captures live in the closure object, not in the frame. Both dangle once the creating function returns, which for a job is almost always before it runs. Write job bodies as free functions (or static members) that take everything by value or as a pointer to data that outlives the job's completion, for example data the spawner keeps alive until it has joined. Never write a job as a capture-by-reference lambda and never pass it a reference parameter.

Frame memory comes from [`jobs::FramePool::Global`](#jobs-framepool-global), never the global heap, so frame allocation does not return null.

Fan-out and join, built purely from jobs, counters and the scheduler.

Job bodies must not capture by reference and the foundation has no `std::function`, so the primitive form of a work function is a plain function pointer plus a `void* user` context. It processes the half-open range `[begin, end)`:

```
void Fn(void* user, usize begin, usize end);
```

`user` and everything it points to must outlive the join, that is until the blocking call returns, or until the counter or awaiter that joined the job returned by [`jobs::ParallelFor`](#jobs-parallelfor-usize-usize-parallelforfn-void-star) has resumed. The typed wrapper stores the callable by pointer and has the same rule.

The range `[0, count)` is split into chunks of `chunk_size` (the last may be short); a `chunk_size` of 0 selects [`jobs::kDefaultChunkSize`](#jobs-kdefaultchunksize), a fixed constant, because adaptive chunking is deferred until a real workload shows it is needed. Each chunk is one job. The chunk count is capped at [`jobs::kMaxChunks`](#jobs-kmaxchunks) by raising the chunk size; see [`jobs::EffectiveChunkSize`](#jobs-effectivechunksize-usize-usize).

The work-stealing job scheduler.

An ordinary object, not a global. Participant 0 is the thread that constructs it ("main"), which helps run jobs only while waiting; the other participants are pinned worker threads.

Work acquisition order, for workers and for main inside [`jobs::Scheduler::HelpUntil(Counter&)`](#jobs-scheduler-helpuntil-counter-amp) alike:

- the participant's own deque, LIFO;
- the injection queue (a mutex-guarded ring);
- a bounded number of steals from random victims (per-participant xorshift32 seeded from the participant index).

A worker whose round found nothing yields a bounded number of times and then parks on a condition variable.

Submission. A participant thread pushes onto its own deque and, if that is full, spills to the injection queue. Any other thread (an I/O thread, a test's plain `std::thread`) uses the injection queue. If the injection queue is also full, participant 0 outside a job (the main thread) runs queued work until the injection queue has `kBackpressureSlack` (512) free slots, so that jobs run during that help can themselves fan out. This backpressure is what lets a single-participant scheduler submit more jobs than the queues hold before it ever calls `HelpUntil`. Any other submitter (a job on a worker, a job run by `HelpUntil`, a non-participant thread) aborts: a capacity bug, never silent loss.

Backpressure only helps leaf-like submissions. A wide fan-out tree that saturates both queues cannot be made to fit by running more of it, since each parent run adds children faster than leaves retire, so such workloads must keep their outstanding job count under the combined capacity (deque plus injection queue, about 8K per participant and queue).

Shutdown. Coroutines suspended in a [`jobs::Counter`](#jobs-counter) await are in no queue, so [`jobs::Scheduler::Shutdown`](#jobs-scheduler-shutdown) cannot free them: callers must join (`HelpUntil` or await) all outstanding work before destroying the scheduler, or those frames leak. Submitting concurrently with or after shutdown is a caller bug (asserted once shutdown has completed).

Which CPUs the process may use and how many job-system participants to run.

The platform-specific queries sit behind these functions so that ports provide their own implementation without touching callers.

The participants of the job system and the threads behind them.

`N` participants are participant 0 (the thread that constructs the pool: "main", never pinned, never looping here) plus `N - 1` spawned workers pinned to distinct allowed CPUs. One participant spawns no threads. Each participant thread has a thread-local identity so any code can ask which participant, if any, it is running on.

## `FramePool` {#jobs-framepool}

`class jobs::FramePool` — defined in `engine/jobs/frame_pool.h`

```cpp
class FramePool { ... }
```

Thread-safe, size-classed allocator for coroutine frames, with an optional per-thread cache.

Requests up to [`jobs::FramePool::kMaxPooledRequest`](#jobs-framepool-kmaxpooledrequest) bytes come from a size class; larger ones, or ones that find their class exhausted, fall back to `malloc` and are counted separately. Blocks may be freed on any thread. A pool cannot be copied. Destroying a pool releases its slabs, so every pooled block must be freed before then; the global pool is never destroyed.

| Field | Value |

| Ownership | owns the reserved slabs of every size class and releases them in the destructor. Blocks returned by allocation belong to the caller until passed back to [`jobs::FramePool::Deallocate`](#jobs-framepool-deallocate-void-star). |

## `Job` {#jobs-job}

`class jobs::Job` — defined in `engine/jobs/job.h`

```cpp
class Job { ... }
```

Move-only handle to a not-yet-started job coroutine frame.

Jobs start suspended: creating a `Job` runs no user code. Submitting it (see [`jobs::Scheduler::Submit`](#jobs-scheduler-submit-job-amp-amp)) calls [`jobs::Job::Release`](#jobs-job-release), which hands the raw handle over and leaves the `Job` empty. From then on the frame owns itself and destroys itself when the body finishes. When the body finishes, the frame is freed first and only then does the completion hook run, so anything woken in response observes the frame already gone. Awaiting a `Job` directly is not supported; join with a [`jobs::Counter`](#jobs-counter).

| Field | Value |
|---|---|
| Thread-safety | not-thread-safe. A `Job` object is owned by one thread at a time; the frame it hands off is resumed by whichever worker runs it. |
| Ownership | owns its frame until [`jobs::Job::Release`](#jobs-job-release) transfers it; a `Job` destroyed without being released destroys its never-started frame (and never runs its completion hook). |

**See also:** [`jobs::Spawn`](#jobs-spawn-counter-amp-job-amp-amp), [`jobs::Scheduler::Submit`](#jobs-scheduler-submit-job-amp-amp)

## `WorkerPool` {#jobs-workerpool}

`class jobs::WorkerPool` — defined in `engine/jobs/worker_pool.h`

```cpp
class WorkerPool { ... }
```

Owns the participant threads: participant 0 is the constructing thread and the others are spawned workers.

Construction returns once every worker has registered its identity. The pool must be destroyed on the thread that constructed it, and overlapping pools on one thread must be destroyed in reverse construction order; both are asserted. It cannot be copied.

| Field | Value |
|---|---|
| Thread-safety | thread-safe for [`jobs::WorkerPool::RequestStop`](#jobs-workerpool-requeststop), [`jobs::WorkerPool::Join`](#jobs-workerpool-join) and the accessors; construction and destruction belong to the constructing thread. |
| Ownership | owns and joins the spawned worker threads; the destructor requests stop and joins them. |

**See also:** [`jobs::Scheduler`](#jobs-scheduler)
