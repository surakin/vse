A small owning reference to a COM object, so the DX12 backend needs no WRL `ComPtr` (design spec decision 10).

The one place the Direct3D 12 and DXGI headers are included (Phase 13 Day 164).

`os/windows/win32.h` brings `<windows.h>` between the unity guards; the D3D12 and DXGI headers go inside their own pair here, so their macros do not leak into the next file of a unity batch (CLAUDE.md, "Unity builds"). The backend uses the OS's own `d3d12.dll` and `dxgi.dll` (no Agility SDK, no D3D12MA, no DirectX-Headers package, no WRL: design spec decision 10).

The DXGI adapters the Direct3D 12 backend can use, described as [`rhi::AdapterInfo`](rhi.md#rhi-adapterinfo) (Phase 13 Day 164).

## `Dx12Device` {#rhi-dx12-dx12device}

`class rhi::dx12::Dx12Device` — defined in `engine/rhi/dx12/dx12_device.h`

```cpp
class Dx12Device final : public Device { ... }
```

The Direct3D 12 device: one adapter, one `ID3D12Device` at feature level 12_0, and one direct queue for all work.

Created by [`rhi::CreateDevice`](rhi.md#rhi-createdevice-const-devicecreateinfo-amp) with `Backend::Dx12` (or [`rhi::dx12::Dx12Device::Create`](#rhi-dx12-dx12device-create-const-devicecreateinfo-amp)). With validation on, the debug layer's messages go to [`rhi::LogRhi`](rhi.md#rhi-logrhi) through `ID3D12InfoQueue1`'s callback and are counted ([`rhi::dx12::GetDebugMessageCounts`](#rhi-dx12-getdebugmessagecounts)). Every wait on the GPU is bounded: it waits in slices and checks for a removed device between them.

| Field | Value |
|---|---|
| Thread-safety | thread-safe, as [`rhi::Device`](rhi.md#rhi-device) is: resource creation and destruction from any thread; `Submit`, `BeginFrame`, `EndFrame` and `WaitIdle` belong to one submission thread. |
| Ownership | the caller owns the device through a [`rhi::dx12::Dx12DevicePtr`](#rhi-dx12-dx12deviceptr); it owns the factory, the adapter and the queue. |
