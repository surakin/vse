# Spatial Partitioning

_Generated by docgen. Do not edit._

**Headers:** `engine/spatial/components.h`, `engine/spatial/dynamic_bvh.h`, `engine/spatial/hash_grid.h`, `engine/spatial/pair_tracker.h`, `engine/spatial/query.h`, `engine/spatial/spatial.h`, `engine/spatial/spatial_set.h`, `engine/spatial/spatial_sync.h`, `engine/spatial/spatial_world.h`, `engine/spatial/static_bvh.h`

The ECS side of the spatial module (Phase 18 Day 244): the components that put an entity into the spatial sets. The sync system of `spatial/spatial_sync.h` reads them; no other code writes `WorldBounds` or `SpatialProxy`.

The dynamic bounding-volume hierarchy (Phase 18 Day 240): for items that move, updated at a cost proportional to what moved. An incremental tree of fat boxes (Box2D's `b2DynamicTree` design) with a bulk top-down build and an incremental optimizer that keep its quality up under motion.

The hash grid (Phase 18 Day 242): for many dynamic items of about the same size (crowds, particles). Kept by the spatial design spec's experiment (a): on 100,000 same-size agents the all-pairs query was 2 times faster than the best BVH and an update a quarter of the cost; it loses on items of very different sizes and on rays, so it is opt-in.

The pair tracker (Phase 18 Day 243): which pairs of items began and which ended overlapping since the last update. The contract physics' narrow phase builds on. Deterministic: the events come out sorted, whatever order the items moved in.

The query vocabulary (Phase 18 Day 241): overlap with a box, sphere or frustum, ray casts (closest, any, all), box sweeps, the k nearest items and all overlapping pairs, with layer masks, an optional filter and a documented order. Free functions over any structure with the two traversals of [`spatial::StaticBvh`](#spatial-staticbvh) and [`spatial::DynamicBvh`](#spatial-dynamicbvh) (`Traverse` and `TraverseRay`), so the static tree, the dynamic tree and later the spatial set answer the same calls, and so do [`spatial::HashGrid`](#spatial-hashgrid) and [`spatial::SpatialSet`](#spatial-spatialset): box and sphere overlaps on them use the grid's cells, the all-pairs query on a grid too; the other queries scan a grid's items (a grid is for overlaps and pairs; use a BVH for rays).

The spatial module (Phase 18): bounding-volume hierarchies, spatial sets and the queries every system shares ("what is near this box, ray, frustum"). Design: `docs/superpowers/specs/2026-11-10-spatial-design.md`; guide: `docs/guide/spatial.md`. The shapes it works on are the foundation's (`math/geometry.h`), shared with the renderer. Structures are generic over a 64-bit key and know nothing of the ECS; the ECS tier (components, the spatial world, the sync system) comes later in the phase.

The spatial set (Phase 18 Day 242): what systems use. One static tree for what does not move, plus a dynamic tree or a hash grid for what does, behind the one query vocabulary of `spatial/query.h`; an item keeps its handle when it moves between the two sides.

The spatial sync system (Phase 18 Days 244-245): keeps the sets of a [`spatial::SpatialWorld`](#spatial-spatialworld) true to the entities that carry the components of `spatial/components.h`.

The spatial world (Phase 18 Day 244): a resource holding the world's named spatial sets, so independent systems (rendering, physics, audio, gameplay) each find their set without coordinating.

The static bounding-volume hierarchy (Phase 18 Day 239): for items that do not move, built once top-down with the binned surface-area heuristic and queried a great deal. Generic over a 64-bit key; it knows nothing of the ECS.

## `DynamicBvh` {#spatial-dynamicbvh}

`class spatial::DynamicBvh` — defined in `engine/spatial/dynamic_bvh.h`

```cpp
class DynamicBvh { ... }
```

A dynamic bounding-volume hierarchy: one leaf per item, holding the item's fat box; inner nodes hold the box of their two children.

`Insert` puts a leaf beside the sibling that adds the least surface area to the tree (a branch-and-bound search) and rotates nodes on the way up to keep the tree balanced; `Remove` takes it out the same way; `Move` does nothing while the new box stays inside the stored fat box and re-inserts the leaf otherwise. A tree built only by insertion answers queries 1.8 to 3.3 times slower than a top-down build of the same boxes (the spatial design spec, experiment (a)), so `Build` makes a fresh tree top-down (the binned SAH of [`spatial::StaticBvh`](#spatial-staticbvh), one item per leaf) and `Optimize` rebuilds a small subtree per call and the whole tree when its quality has degraded. Nodes live in one pool with a free list: after the pool has grown to its working size, `Insert`, `Remove`, `Move` and the queries allocate nothing.

| Field | Value |
|---|---|
| Thread-safety | thread-compatible. Changes need exclusive access; the const queries may run on any number of threads at once between changes. |
| Ownership | owns its nodes and items; it keeps no pointer to what it was given. |

## `HashGrid` {#spatial-hashgrid}

`class spatial::HashGrid` — defined in `engine/spatial/hash_grid.h`

```cpp

```

A uniform grid of cubic cells over all of space, the occupied cells in an open-addressing hash table keyed by their coordinates; each item is registered in every cell its box touches.

A pair is made when two boxes overlap and kept until they have separated by more than their margins: each item's margin is `margin` times its largest extent, and a pair ends when the boxes grown by their margins no longer overlap. ## `PairTracker` {#spatial-pairtracker}

`class spatial::PairTracker` — defined in `engine/spatial/pair_tracker.h`

```cpp
class PairTracker { ... }
```

Keeps the overlap pairs of a [`spatial::SpatialSet`](#spatial-spatialset) between frames and reports what changed.

The caller says what changed: `Touch` for every item added, moved, given another layer or switched between static and dynamic, and `Remove` for every key removed (the item's handle is stale by then). `Update` re-queries only the touched items against the set, so a frame in which few items moved costs few queries. Two static items never form a pair (they cannot start to touch). A key that is removed and added again between two updates and touched again keeps the pairs that still hold (no events for them) and ends the others; a key that is removed and not touched again loses all its pairs; a new key never inherits pairs.

| Field | Value |
|---|---|
| Thread-safety | thread-compatible; `Update` reads the set, which must not change during the call. |
| Ownership | owns its pair list; the set is borrowed for the call. |

## `MakeSpatialSyncSystem(const char*)` {#spatial-makespatialsyncsystem-const-char-star}

`function spatial::MakeSpatialSyncSystem` — defined in `engine/spatial/spatial_sync.h`

```cpp
ecs::SystemDesc MakeSpatialSyncSystem(const char* name);
```

The spatial sync system.

It keeps a [`spatial::SpatialProxy`](#spatial-spatialproxy) on every entity that is in a set:

- an entity with `SpatialBounds`, `WorldTransform` and `SpatialMembership` (and no proxy) gets an item in every set its membership names, on the static side when it has [`spatial::SpatialStatic`](#spatial-spatialstatic), and a [`spatial::WorldBounds`](#spatial-worldbounds); a box that is not finite, or not a box, is refused and counted, and looked at again every frame;
- an entity that loses any of the three components, or is destroyed (found through the world's removal log of `SpatialProxy`, not by scanning), leaves its sets;
- a changed `SpatialMembership` adds the item to the sets that are new, removes it from those that are gone and re-adds it when the layer changed; adding or removing `SpatialStatic` moves the items between the static and the dynamic side.

Needs the resource [`spatial::SpatialWorld`](#spatial-spatialworld) in the world. Register it after the transform propagation and before any system that queries the sets: a query that runs before the sync in a frame sees the previous frame's sets (documented, not an error).

| Field | Value |
|---|---|
| Parameter `name` | the system's name, copied by the schedule. |
| Returns | the system description to `Schedule::Add`. |
| Aborts | the `SpatialWorld` resource is missing. |
| Thread-safety | thread-compatible; it writes the sets, so no query may run on them meanwhile. |
| Ownership | the system owns its queries; the sets belong to the `SpatialWorld`. |

## `StaticBvh` {#spatial-staticbvh}

`class spatial::StaticBvh` — defined in `engine/spatial/static_bvh.h`

```cpp
class StaticBvh { ... }
```

A static bounding-volume hierarchy over [`spatial::Item`](#spatial-item)s.

`Build` makes the tree top-down: each node is split by the binned surface-area heuristic on its longest centroid axis (16 bins), down to leaves of at most 4 items; nodes whose items share one centroid, or that would make the tree deeper than its traversal stack, are split in the middle instead, so the depth stays within [`spatial::kTraversalStackDepth`](#spatial-ktraversalstackdepth) for any input. Nodes are 32 bytes in one array in depth-first order (a node's left child is the next node), and the items are kept in leaf order, so the items of any subtree are one contiguous range. The same items in the same order always build the same tree: every tie is broken by the items' order, never by an address.

| Field | Value |
|---|---|
| Thread-safety | thread-compatible. `Build` and `Clear` need exclusive access; the const traversals may run on any number of threads at once. |
| Ownership | owns its nodes and its copy of the items; `Build` copies the span and keeps nothing of it. |
