# Spatial Partitioning

_Generated by docgen. Do not edit._

**Headers:** `engine/spatial/dynamic_bvh.h`, `engine/spatial/query.h`, `engine/spatial/spatial.h`, `engine/spatial/static_bvh.h`

The dynamic bounding-volume hierarchy (Phase 18 Day 240): for items that move, updated at a cost proportional to what moved. An incremental tree of fat boxes (Box2D's `b2DynamicTree` design) with a bulk top-down build and an incremental optimizer that keep its quality up under motion.

The query vocabulary (Phase 18 Day 241): overlap with a box, sphere or frustum, ray casts (closest, any, all), box sweeps, the k nearest items and all overlapping pairs, with layer masks, an optional filter and a documented order. Free functions over any structure with the two traversals of [`spatial::StaticBvh`](#spatial-staticbvh) and [`spatial::DynamicBvh`](#spatial-dynamicbvh) (`Traverse` and `TraverseRay`), so the static tree, the dynamic tree and later the spatial set answer the same calls.

The spatial module (Phase 18): bounding-volume hierarchies, spatial sets and the queries every system shares ("what is near this box, ray, frustum"). Design: `docs/superpowers/specs/2026-11-10-spatial-design.md`; guide: `docs/guide/spatial.md`. The shapes it works on are the foundation's (`math/geometry.h`), shared with the renderer. Structures are generic over a 64-bit key and know nothing of the ECS; the ECS tier (components, the spatial world, the sync system) comes later in the phase.

The static bounding-volume hierarchy (Phase 18 Day 239): for items that do not move, built once top-down with the binned surface-area heuristic and queried a great deal. Generic over a 64-bit key; it knows nothing of the ECS.

## `DynamicBvh` {#spatial-dynamicbvh}

`class spatial::DynamicBvh` — defined in `engine/spatial/dynamic_bvh.h`

```cpp
class DynamicBvh { ... }
```

A dynamic bounding-volume hierarchy: one leaf per item, holding the item's fat box; inner nodes hold the box of their two children.

`Insert` puts a leaf beside the sibling that adds the least surface area to the tree (a branch-and-bound search) and rotates nodes on the way up to keep the tree balanced; `Remove` takes it out the same way; `Move` does nothing while the new box stays inside the stored fat box and re-inserts the leaf otherwise. A tree built only by insertion answers queries 1.8 to 3.3 times slower than a top-down build of the same boxes (the spatial design spec, experiment (a)), so `Build` makes a fresh tree top-down (the binned SAH of [`spatial::StaticBvh`](#spatial-staticbvh), one item per leaf) and `Optimize` rebuilds a small subtree per call and the whole tree when its quality has degraded. Nodes live in one pool with a free list: after the pool has grown to its working size, `Insert`, `Remove`, `Move` and the queries allocate nothing.

| Field | Value |
|---|---|
| Thread-safety | thread-compatible. Changes need exclusive access; the const queries may run on any number of threads at once between changes. |
| Ownership | owns its nodes and items; it keeps no pointer to what it was given. |

## `StaticBvh` {#spatial-staticbvh}

`class spatial::StaticBvh` — defined in `engine/spatial/static_bvh.h`

```cpp
class StaticBvh { ... }
```

A static bounding-volume hierarchy over [`spatial::Item`](#spatial-item)s.

`Build` makes the tree top-down: each node is split by the binned surface-area heuristic on its longest centroid axis (16 bins), down to leaves of at most 4 items; nodes whose items share one centroid, or that would make the tree deeper than its traversal stack, are split in the middle instead, so the depth stays within [`spatial::kTraversalStackDepth`](#spatial-ktraversalstackdepth) for any input. Nodes are 32 bytes in one array in depth-first order (a node's left child is the next node), and the items are kept in leaf order, so the items of any subtree are one contiguous range. The same items in the same order always build the same tree: every tie is broken by the items' order, never by an address.

| Field | Value |
|---|---|
| Thread-safety | thread-compatible. `Build` and `Clear` need exclusive access; the const traversals may run on any number of threads at once. |
| Ownership | owns its nodes and its copy of the items; `Build` copies the span and keeps nothing of it. |
