The few compiler- and architecture-specific constructs the debugging facilities need, in one place.

Nothing else in the debugging code names a compiler builtin or inline assembly, so a port to another compiler (MSVC, clang-cl) changes this header only.

Platform-neutral description of why a process or thread was stopped abnormally.

Debugging code, the crash handler and the tests speak [`debug::CrashReason`](#debug-crashreason); the platform backends translate their own codes (signals, exception codes) into it.

Running code that is supposed to crash, in a child process, and seeing what happened.

The helper starts a fresh copy of the running program; it does not `fork`, because `fork` does not exist on every platform and in a multithreaded process it leaves the child holding locks it can never release. The child runs one function registered with [`ENGINE_DEATH_TEST_FN`](#engine-death-test-fn); the parent gets a [`debug::ChildResult`](#debug-childresult). A program that wants to be the child calls [`debug::RunDeathTestChildIfRequested`](#debug-rundeathtestchildifrequested) early (the test support in tests/debug does it for Catch2).

Asking whether a debugger is attached to the running process.

Deliberate faults for testing crash handling.

Tests call [`debug::InjectFault`](#debug-injectfault-faultkind) inside a child process (see death_test.h) and check the reported [`debug::CrashReason`](#debug-crashreason); they never name a signal or exception code. Each platform implements the faults it has.

## `CrashReason` {#debug-crashreason}

`enum debug::CrashReason` — defined in `engine/foundation/debug/crash_reason.h`

```cpp
enum class CrashReason : u8 { ... }
```

Why a process died or a fault was reported, independent of the operating system.

A backend maps its native code to the closest value and keeps the raw code beside it. A stack overflow is a hardware access violation on every platform, so a process that only left an exit status reports [`debug::CrashReason::AccessViolation`](#debug-crashreason-accessviolation); [`debug::CrashReason::StackOverflow`](#debug-crashreason-stackoverflow) is reported only by code that saw the fault happen.

| Enumerator | Value | Description |
|---|---|---|
| <a id="debug-crashreason-none"></a>`None` | `0` | The process did not die from a fault (it exited normally, or was killed from outside). |
| <a id="debug-crashreason-accessviolation"></a>`AccessViolation` |  | An invalid memory access: a null or wild pointer, or a write to read-only memory. |
| <a id="debug-crashreason-buserror"></a>`BusError` |  | An access the hardware could not complete, such as a page beyond the end of a mapped file. |
| <a id="debug-crashreason-illegalinstruction"></a>`IllegalInstruction` |  | The CPU met an instruction it cannot execute. |
| <a id="debug-crashreason-arithmeticfault"></a>`ArithmeticFault` |  | A trapping arithmetic error such as an integer divide by zero. |
| <a id="debug-crashreason-stackoverflow"></a>`StackOverflow` |  | The stack ran out; only reported by code that saw the fault happen. |
| <a id="debug-crashreason-abort"></a>`Abort` |  | The program called `abort` (or an equivalent) on purpose. |
| <a id="debug-crashreason-assertfailed"></a>`AssertFailed` |  | An `ENGINE_ASSERT` failed. |
| <a id="debug-crashreason-ensurefailed"></a>`EnsureFailed` |  | An `ENGINE_ENSURE` failed and execution continued. |

## `RunInChild(const char*,const char*,const ChildOptions&)` {#debug-runinchild-const-char-star-const-char-star-const-childoptions-amp}

`function debug::RunInChild` — defined in `engine/foundation/debug/death_test.h`

```cpp
ChildResult RunInChild(const char* name, const char* argument = "", const ChildOptions& options = ChildOptions());
```

Starts the running program as a child, runs the registered death test `name` in it, and reports what happened.

The child inherits the environment (plus `options.extra_env`) and nothing else: no threads, locks or memory of the caller. Every path reaps the child and closes every descriptor it opened.

| Field | Value |
|---|---|
| Parameter `name` | the registered function to run in the child. |
| Parameter `argument` | a short string the function receives; larger inputs go in a file whose name is the argument. |
| Parameter `options` | how to start and watch the child. |
| Returns | the result; `supported` is false where the platform cannot start a process. |
| Fails | `started` is false if the process could not be started; `timed_out` is set if it had to be killed. If the platform never reported how the child ended (its status was reaped by someone else), `started` is true and both `exited` and `terminated` are false. |
| Thread-safety | thread-safe. Each call owns its child and its pipes. The child's environment is built from the process environment, so do not change it (`setenv`) from another thread while a call is running. |

## `IsDebuggerAttached()` {#debug-isdebuggerattached}

`function debug::IsDebuggerAttached` — defined in `engine/foundation/debug/debugger.h`

```cpp
bool IsDebuggerAttached();
```

Reports whether a debugger is attached to this process.

The answer is cached for up to one second, so asking on a failure path costs a clock read, not a system call. On a platform with no way to tell, the answer is false.

Any tracer counts, not only an interactive debugger: on Linux a process run under `strace` or `rr` reports true too, and an assert failure then breaks (SIGTRAP) instead of aborting.

| Field | Value |
|---|---|
| Returns | true if a debugger (or another tracer) is attached; false if none is or the platform cannot tell. |
| Thread-safety | thread-safe. |
