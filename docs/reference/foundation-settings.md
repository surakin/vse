Where setting values live: the abstract [`settings::ConfigStore`](#settings-configstore) and the values it holds.

The settings system reads and writes through this interface and never assumes a file. A store is a flat collection of `key -> value` entries. Implementations: a text file (Day 133), memory, read-only shipped defaults (all in the foundation); the Windows registry, `NSUserDefaults`, Android `SharedPreferences` and console save data follow in the platform phases.

**Staged and immediate writes.** `Set` and `Remove` change the store's *working* state; every later `Get` and `Enumerate` on the same store sees them. A store with [`settings::kCapPerKeyWrites`](#settings-kcapperkeywrites) (a registry) makes each change durable at once; any other store keeps them staged until [`settings::ConfigStore::Commit`](#settings-configstore-commit-const-commitoptions-amp) makes them durable together. [`settings::ConfigStore::Load`](#settings-configstore-load) discards staged changes and reads the durable state again.

The settings text format and its document model (no I/O).

```
# a comment on its own line      ; this style works too
version = 1
[renderer]                       # the section: keys below it are renderer.<name>
present_mode = "mailbox"         # a trailing comment
width = 1920
```

A file is lines. A blank line, or a line whose first non-blank character is `#` or `;`, is a comment. `[a]` or `[a.b]` starts a section; `name = value` sets the key `<section>.<name>` (before any section the name is the whole, possibly dotted, key). A value is a quoted text (`"..."` with the escapes `\"`, `\\`, `\n`, `\t`, `\xHH`) or a bare run of characters that ends at the end of the line or at a blank followed by `#` or `;` (so a bare value cannot start with `#` or `;`: quote it). Lines are at most 4096 bytes and the file is UTF-8 (a byte order mark is accepted and kept).

A [`settings::ConfigDocument`](#settings-configdocument) keeps every line as written, so changing a value rewrites only the value's own bytes, a new key goes at the end of its section, and a document that is not changed serializes to the bytes it was parsed from, including line endings, comments, spacing and lines it could not understand (those are reported as errors and never touched).

The declaration of one setting, and the text form of its values.

The engine's own settings (the ones that used to be environment variables or per-program options) and the log channels as settings.

The environment as a settings layer, and the command line as another.

The settings file store: a human-edited text file that keeps what the human wrote.

Setting keys: validated dotted names such as `renderer.present_mode`.

A key has one to three segments separated by `.`; a segment is a lowercase letter followed by lowercase letters, digits and `_`, at most 31 bytes; the whole key is at most 95 bytes. In a text file the key `renderer.width` is the name `width` in the section `[renderer]`, and `a.b.c` is `c` in `[a.b]`; [`settings::Key::Section`](#settings-key-section-const) and [`settings::Key::Name`](#settings-key-name-const) give that split.

Layered sources: several stores that read as one, lowest to highest, with a way to ask where a value came from.

The order, lowest first: the registry's defaults, then the layers by role: [`settings::LayerRole::System`](#settings-layerrole-system) (shipped defaults), `User` (the user's file, the one that is written), `Project`, `Custom` (a file named by `--settings`), `Environment`, `CommandLine`. A value set in a higher layer hides the lower ones; a value missing or unusable in a layer falls through to the next lower one.

Stores that live in memory: [`settings::MemoryConfigStore`](#settings-memoryconfigstore) (full-featured) and [`settings::ReadOnlyConfigStore`](#settings-readonlyconfigstore) (shipped defaults).

Changing a setting between versions: the format version, per-section schema versions and migration steps.

A settings file records `version = N` (the file format, [`settings::kFormatVersion`](#settings-kformatversion)) and, for each section its owner gave a schema version with [`settings::Registry::SetSchemaVersion`](#settings-registry-setschemaversion-stringview-u32), `<section>.schema = N`. When a file is loaded, a [`settings::MigrationSet`](#settings-migrationset) upgrades the user's store from the version the file has to the version the program has, in order. The upgraded content is in memory (and staged in the store); the file is rewritten, comments and all, the next time the application saves. A file *newer* than the program is read in compatibility mode and never rewritten in an older format.

The registry of settings: what exists, with its type, default, range and metadata, and the current value of each.

A registry is filled at start-up ([`settings::Registry::Register`](#settings-registry-register-const-settingdesc-amp-registererror-star)), frozen ([`settings::Registry::Freeze`](#settings-registry-freeze)) and then only read; the current values change through [`settings::Registry::Publish`](#settings-registry-publish-settingid-const-value-amp) (the settings service does this) and are read by typed handles ([`settings::Setting`](#settings-setting)) at the cost of one relaxed atomic load.

Text the command line shows about settings: `--list-settings`, the generated `--help` section, and `--save-settings`.

Typed handles for reading a setting: `Setting<bool>`, `Setting<i64>`, `Setting<f32>`, `Setting<f64>` and `Setting<E>` for an enum type `E`, and [`settings::TextSetting`](#settings-textsetting) for text.

A handle is one pointer. `Get()` is one relaxed atomic load and a decode, so it is safe and cheap in a hot path from any thread; it sees a published value on the next call after `Registry::Publish` returns. A handle made for the wrong type aborts at creation.

The settings service an application owns: it builds the layer stack, publishes values to the typed handles, tells interested code what changed, and saves.

```cpp
settings::Settings settings(settings::Registry::Global());
settings::LoadOptions load;
load.app_name = "mygame";
load.argc = argc; load.argv = argv;
settings::LoadReport report = settings.Load(load);   // every problem is in the report; nothing stops the others
...
settings::SaveOnExit save(settings);                 // writes the user's file at the end of the scope if anything changed
```

A setting's value: a small tagged value that is cheap to copy and owns no heap memory.

## `FileConfigStore` {#settings-fileconfigstore}

`class settings::FileConfigStore` — defined in `engine/foundation/settings/file_store.h`

```cpp
class FileConfigStore final : public ConfigStore { ... }
```

A [`settings::ConfigStore`](#settings-configstore) over one text file (see [`settings::ConfigDocument`](#settings-configdocument) for the format).

The store reads the file whole on `Load` (a missing file is an empty store). `Set` and `Remove` edit the in-memory document, so a change rewrites only the bytes it touches. `Commit` writes the document with `io::WriteFileAtomic` after copying the previous file to `.bak`.

**A file that cannot be read is never overwritten by accident.** If `Load` finds lines it cannot understand, the store is *damaged*: the lines it could read are available, the rest is kept verbatim, and `Commit` refuses with `Damaged` unless `CommitOptions::replace_damaged` is set (the damaged text is then in the `.bak` file).

If a `Load` could not read the file at all (permission, size cap, I/O), `Commit` refuses with that error until a `Load` succeeds.

Two stores over one file do not merge: the last `Commit` wins as a whole, and a reader never sees a torn file.

| Field | Value |
|---|---|
| Thread-safety | thread-compatible. |
| Ownership | owns its document; the file belongs to the file system. |

## `Settings` {#settings-settings}

The settings of one application: registry, layers, current values, listeners and saving.

| Field | Value |
|---|---|
| Thread-safety | thread-safe. `Set`, `Apply`, `Save`, `Load`, `Provenance` and listener registration are serialized by one recursive lock that is held while the apply function and the listeners run, so changes are announced in the order they were published, a rejected batch is rolled back before anyone else can change anything, and a listener or the apply function may call `Set` again on its own thread (up to 8 deep).
