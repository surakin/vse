The entry point of a windowed program (Phase 13 Day 158), written once in source so no build file chooses it per platform.

A windowed program (a game, a demo) defines `int EngineMain(int argc, char** argv)` and, in one source file at global scope, writes `ENGINE_WINDOWED_PROGRAM(EngineMain)` instead of `main`. The macro expands to the platform's own entry point: `main` on Linux, `wWinMain` on Windows, where it makes the program a Windows (GUI) program: no console window opens when it is started from Explorer. Either way `EngineMain` gets UTF-8 arguments, already stashed for [`os::CommandLine::FromNative`](platform-os.md#os-commandline-fromnative-allocator-amp), and its result is the exit code.

The Windows subsystem comes with the entry point, from source: the macro's expansion carries a linker directive for `/SUBSYSTEM:WINDOWS`, which wins over the `/SUBSYSTEM:CONSOLE` the build gives every program, so tests and command-line tools, which keep a plain `main`, stay console programs, and no build file chooses a subsystem per target. A Windows GUI program writes its output to the handles it inherited (a pipe, a redirected file, ctest's capture) as they are. With none, started from a terminal, it attaches to that terminal's console, so its output appears there (after the shell's next prompt: a shell does not wait for a GUI program); started from Explorer, there is no console and the writes fail (the log file still has everything).

Keyboard and mouse input types shared by every platform backend.

Keys are layout-aware: they name the symbol the user's layout produces, not the physical position. Each backend gives the state the same meaning: on Linux from XKB keysyms (`platform/linux/key_translate.h`), on Windows from the layout's character for a key that types one and the scan code for the others (`platform/windows/win32_keys.h`). The differences on Windows: AltGr is the right Alt alone and no modifier, as XKB's level-3 shift is; a focus loss also releases the mouse buttons (Windows hands the mouse to the other window, where the X11 and Wayland servers still deliver the release); and the wheel is scaled to the Linux backends' 10 units per notch. There is no text input yet on any backend.

The Linux backends' key translation (Phase 13 Day 159 moved it here from the neutral layer): X11 and XKB keysyms to [`os::Key`](#os-key), shared by the Wayland and X11 backends. Windows translates scan codes and its layout's characters instead (`platform/windows/win32_keys.h`).

Wayland connection: the compositor connection and the globals the engine binds.

Wayland seat input: keyboard and pointer events from a `wl_seat` into an `InputState`.

Wayland platform window: the Wayland backend packaged as an `os::Window`.

Wayland window: a `wl_surface` wrapped as a mapped xdg-shell toplevel.

X11 window backend: the fallback `os::Window` built on libX11.

XKB keyboard: libxkbcommon keymap and state used to translate evdev keycodes into engine keys.

Platform-neutral window interface implemented by each display backend (Wayland and X11 on Linux, Win32 on Windows).

The interface is polled: pump events, then read size, close request and the bound `InputState`.

The window host: picks, opens and owns the display backend of the running platform and exposes it as a [`os::Window`](#os-window). The header is the same on every platform; the implementation lives in `platform/<platform>/` (Wayland or X11 on Linux), so a program that includes only this header builds unchanged on each.

Win32 key messages to [`os::Key`](#os-key) (Phase 13 Day 159), with the meaning the Linux backends give keys: layout-aware.

A key that types a character is named by the character the active layout gives it, as XKB names it by its keysym: on a French AZERTY layout the key in the Q position is `Key::A`, and the `&` key is `Key::Num1` only with Shift. The character is computed with the modifiers that choose a level (Shift, Caps Lock, AltGr), not Ctrl or Alt, so Ctrl+A is still `Key::A`. Every other key is named by its virtual-key code and its scan code: left and right Shift by the scan code, left and right Ctrl and Alt by the extended bit, and the navigation keys of the number pad (NumLock off) apart from the separate ones, which are `Unknown` as XKB's `KP_Home` and friends are. Keys the enum has no name for (Pause, Print Screen, NumLock, the number pad's operators and decimal point) are `Unknown`.

The Windows window backend (Phase 13 Day 158): an [`os::Window`](#os-window) over a Win32 top-level window.

Sizes are in physical pixels: every engine program is per-monitor DPI aware (version 2, from its manifest; a thread that is not gets the awareness set around the window's creation), so a window on a 150% monitor that asks for 1280x720 gets a 1280x720 client area, and a move to a monitor of another scale keeps the window the same size to the eye (the system's suggested rectangle is applied). Fullscreen is borderless on the window's monitor (`platform/windows/FULLSCREEN.md`). Input fills the bound [`os::InputState`](#os-inputstate) with the meaning the Linux backends give it (`platform/windows/win32_keys.h` for the keys; the guide's "Windows input" for the rest).

## `WaylandWindow` {#os-wayland-waylandwindow}

`class os::wayland::WaylandWindow` — defined in `engine/platform/linux/wayland/wayland_window.h`

## `Win32Window` {#os-win32-win32window}

```cpp
class Win32Window final : public Window { ... }
```

A top-level Win32 window, as an [`os::Window`](#os-window).

The window procedure finds the object through the window's user data, so the object cannot move: it is neither copyable nor movable, and a holder keeps it in place (the window host holds it by value).
