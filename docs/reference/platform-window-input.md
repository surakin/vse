The OS clipboard: what can be put on it, the answer to a request, and the rules that keep data from other programs from doing harm.

Reading is asynchronous: [`os::Window::RequestClipboard`](#os-window-requestclipboard-clipboardkind-clipboardformat-stringview) returns an id, a later `PumpEvents` queues an [`os::InputEventType::ClipboardData`](#os-inputeventtype-clipboarddata) event with that id, and [`os::Window::TakeClipboardResult`](#os-window-takeclipboardresult-u32-clipboardresult-star) hands over the bytes. A request nobody answers ends with [`os::ClipboardStatus::Timeout`](#os-clipboardstatus-timeout) after two seconds, so a paste never hangs a program.

The mouse cursor: the standard shapes, a custom image, and the pointer lock state machine the window backends share.

Pure data and logic, no display library: the header is part of the `platform_input` target, so the UI and the tests can use it without a window.

Drag and drop between programs: the values shared by every platform backend. The operations are on [`os::Window`](#os-window).

The entry point of a windowed program (Phase 13 Day 158), written once in source so no build file chooses it per platform.

A windowed program (a game, a demo) defines `int EngineMain(int argc, char** argv)` and, in one source file at global scope, writes `ENGINE_WINDOWED_PROGRAM(EngineMain)` instead of `main`. The macro expands to the platform's own entry point: `main` on Linux; `main` on macOS too, which sets up the application object (a regular app with a Dock icon and a Quit menu, `platform/macos/cocoa_window.h`) before `EngineMain` runs, so a program run from a terminal is an ordinary app without a bundle; `wWinMain` on Windows, where it makes the program a Windows (GUI) program: no console window opens when it is started from Explorer. Either way `EngineMain` gets UTF-8 arguments, already stashed for [`os::CommandLine::FromNative`](platform-os.md#os-commandline-fromnative-allocator-amp), and its result is the exit code.

The Windows subsystem comes with the entry point, from source: the macro's expansion carries a linker directive for `/SUBSYSTEM:WINDOWS`, which wins over the `/SUBSYSTEM:CONSOLE` the build gives every program, so tests and command-line tools, which keep a plain `main`, stay console programs, and no build file chooses a subsystem per target. A Windows GUI program writes its output to the handles it inherited (a pipe, a redirected file, ctest's capture) as they are. With none, started from a terminal, it attaches to that terminal's console, so its output appears there (after the shell's next prompt: a shell does not wait for a GUI program); started from Explorer, there is no console and the writes fail (the log file still has everything).

Keyboard and mouse input types shared by every platform backend.

Keys are layout-aware: they name the symbol the user's layout produces, not the physical position. Each backend gives the state the same meaning: on Linux from XKB keysyms (`platform/linux/key_translate.h`), on Windows from the layout's character for a key that types one and the scan code for the others (`platform/windows/win32_keys.h`), on macOS from the layout's character and the key code the same way (`platform/macos/cocoa_keys.h`). On Windows, AltGr is the right Alt alone and no modifier, as XKB's level-3 shift is; a focus loss also releases the mouse buttons (Windows hands the mouse to the other window, where the X11 and Wayland servers still deliver the release); and the wheel is scaled to the Linux backends' 10 units per notch. On macOS Option is Alt and Command is Super, Option does not rename a key, and a trackpad's scroll is 10 points to the notch. Text arrives through the event stream (`platform/input_event.h`).

The input event stream: what a window backend reports in the order the server delivered it, beside the polled `InputState`.

`InputState` answers "what is down now"; it cannot say that a key was pressed and released between two polls, carries no text, and has no key repeat on Wayland. A UI needs all three, so each window also queues `InputEvent`s that the program drains with `Window::PollEvent` after `PumpEvents`. Pure data, no display library: the header is part of the `platform_input` target.

The Linux backends' key translation (Phase 13 Day 159 moved it here from the neutral layer): X11 and XKB keysyms to [`os::Key`](#os-key), shared by the Wayland and X11 backends. Windows translates scan codes and its layout's characters instead (`platform/windows/win32_keys.h`).

Keyboard events for the Linux backends that get raw evdev key transitions (Wayland): key down and up, text, and client-side key repeat.

The Wayland clipboard and primary selection: a `wl_data_device` and a `zwp_primary_selection_device_v1` on the seat, with the transfers done through non-blocking pipes.

Wayland connection: the compositor connection and the globals the engine binds.

Wayland cursor shapes, custom cursor images and the pointer lock for [`os::wayland::WaylandInput`](#os-wayland-waylandinput).

Wayland seat input: keyboard and pointer events from a `wl_seat` into an `InputState`.

Wayland platform window: the Wayland backend packaged as an `os::Window`.

Wayland window: a `wl_surface` wrapped as a mapped xdg-shell toplevel.

X11 cursor shapes, custom cursor images and the pointer lock for [`os::x11::X11Window`](#os-x11-x11window).

The X11 display scale: how the desktop's `Xft.dpi` resource becomes the window's content scale.

X11 window backend: the fallback `os::Window` built on libX11.

XKB keyboard: libxkbcommon keymap and state used to translate evdev keycodes into engine keys.

Platform-neutral window interface implemented by each display backend (Wayland and X11 on Linux, Win32 on Windows).

The interface is polled: pump events, then read size, close request and the bound `InputState`.

The window host: picks, opens and owns the display backend of the running platform and exposes it as a [`os::Window`](#os-window). The header is the same on every platform; the implementation lives in `platform/<platform>/` (Wayland or X11 on Linux), so a program that includes only this header builds unchanged on each.

Win32 key messages to [`os::Key`](#os-key) (Phase 13 Day 159), with the meaning the Linux backends give keys: layout-aware.

A key that types a character is named by the character the active layout gives it, as XKB names it by its keysym: on a French AZERTY layout the key in the Q position is `Key::A`, and the `&` key is `Key::Num1` only with Shift. The character is computed with the modifiers that choose a level (Shift, Caps Lock, AltGr), not Ctrl or Alt, so Ctrl+A is still `Key::A`. Every other key is named by its virtual-key code and its scan code: left and right Shift by the scan code, left and right Ctrl and Alt by the extended bit, and the navigation keys of the number pad (NumLock off) apart from the separate ones, which are `Unknown` as XKB's `KP_Home` and friends are. Keys the enum has no name for (Pause, Print Screen, NumLock, the number pad's operators and decimal point) are `Unknown`.

The Windows window backend (Phase 13 Day 158): an [`os::Window`](#os-window) over a Win32 top-level window.

Sizes are in physical pixels: every engine program is per-monitor DPI aware (version 2, from its manifest; a thread that is not gets the awareness set around the window's creation), so a window on a 150% monitor that asks for 1280x720 gets a 1280x720 client area, and a move to a monitor of another scale keeps the window the same size to the eye (the system's suggested rectangle is applied). Fullscreen is borderless on the window's monitor (`platform/windows/FULLSCREEN.md`). Input fills the bound [`os::InputState`](#os-inputstate) with the meaning the Linux backends give it (`platform/windows/win32_keys.h` for the keys; the guide's "Windows input" for the rest).

## `WaylandWindow` {#os-wayland-waylandwindow}

`class os::wayland::WaylandWindow` — defined in `engine/platform/linux/wayland/wayland_window.h`

```cpp
class WaylandWindow { ... }
```

A `wl_surface` wrapped as an xdg-shell toplevel window with a solid-fill `wl_shm` buffer so it maps.

Per xdg-shell a surface is not mapped until a buffer is committed after the first configure and ack, so the window creates a minimal solid-fill buffer to complete that sequence; real pixel content is expected to come from a swapchain. It owns the surface, xdg surface, toplevel, optional decoration object and buffer, but not the event loop. Movable, not copyable.

| Field | Value |
|---|---|
| Thread-safety | owner-thread-only. Listener callbacks run on the thread that dispatches the connection's events, which must also call its methods. |
| Ownership | owns the surface, xdg objects and buffer; the connection is borrowed and must outlive the window. |

### `Create(WaylandConnection&,StringView,StringView,u32,u32)` {#os-wayland-waylandwindow-create-waylandconnection-amp-stringview-stringview-u32-u32}

`method os::wayland::WaylandWindow::Create` — defined in `engine/platform/linux/wayland/wayland_window.h`

```cpp
static WaylandWindow Create(WaylandConnection& connection, StringView title, StringView app_id, u32 width_hint = 0, u32 height_hint = 0);
```

Creates a toplevel on `connection`, blocks until the compositor's initial configure is acknowledged, then maps it.

Sets `title` and `app_id`, waits with `wl_display_roundtrip`, then attaches a solid-fill buffer sized to the compositor's suggested size (or the hint, or a default) and commits. `width_hint` and `height_hint` give the size used when the compositor suggests none, and the size restored when it sends a 0x0 configure (for example on leaving maximized) with nothing better known.

| Field | Value |
|---|---|
| Parameter `connection` | valid connection; must outlive the returned window. |
| Parameter `title` | window title. |
| Parameter `app_id` | application id the compositor uses to group and identify the window. |
| Parameter `width_hint` | fallback width in pixels; 0 means the built-in 1280x720 default. |
| Parameter `height_hint` | fallback height in pixels; 0 means the built-in 1280x720 default. |
| Returns | the window; check [`os::wayland::WaylandWindow::Valid`](#os-wayland-waylandwindow-valid-const). |
| Fails | returns an invalid window (logged via `LogPlatform`) on any failure. |

## `ContentScaleFromResources(StringView)` {#os-x11-contentscalefromresources-stringview}

`function os::x11::ContentScaleFromResources` — defined in `engine/platform/linux/x11/x11_scale.h`

```cpp
inline f32 ContentScaleFromResources(StringView resources);
```

Reads the `Xft.dpi` resource out of the text of the root window's `RESOURCE_MANAGER` property (the X resource database, one `name:<blanks>value` per line) and returns it over 96 as a content scale.

This is the value GTK, Qt and Chromium use for X11: the X server's own screen size and dpi (`xdpyinfo`) usually say 96 whatever the desktop is set to. Both `Xft.dpi` and the loose binding `Xft*dpi` are read. As in an X resource database, a later line replaces an earlier one with the same name (an appended `xrdb -merge` wins), and the tight `Xft.dpi` beats the loose `Xft*dpi` whatever the order. A missing, malformed or non-positive final value, and anything below 96 dpi, gives 1; anything above 4 times 96 gives 4.

| Field | Value |
|---|---|
| Parameter `resources` | the resource database text; it is only read during the call. |
| Returns | the scale, from [`os::x11::kMinContentScale`](#os-x11-kmincontentscale) to [`os::x11::kMaxContentScale`](#os-x11-kmaxcontentscale). |
| Fails | never; a text with no usable value gives 1. |
