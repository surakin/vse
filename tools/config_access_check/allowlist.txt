# path|reason - files allowed to read configuration (getenv, a --flag) outside the settings system. A stale entry fails the gate.
# The rule: CLAUDE.md ("Anything a user can configure is a setting") and docs/superpowers/specs/2026-11-07-settings-design.md (section 2, the inventory).
engine/foundation/debug/program_setup.cpp|Launch-time debugging switches (--crash-handler=, --crash-test=, ENGINE_CRASH_HANDLER) that must act before main builds any Settings.
engine/foundation/io/posix/file_system.cpp|HOME, XDG_* and TMPDIR (through posix::AbsoluteEnv) locate the configuration directory itself (Linux and macOS), so they are needed before any settings file can be read; ENGINE_APP_NAME names the crash dump directory, which the crash handler needs before any settings exist.
engine/foundation/io/windows/file_operations.cpp|ENGINE_APP_NAME names the crash dump directory, which the crash handler needs before any settings can be read (as on Linux); APPDATA and LOCALAPPDATA locate the configuration directory itself (as XDG_* on Linux), so they are needed before any settings file can be read.
engine/foundation/os/posix/debug/death_test_posix.cpp|The death-test child protocol (environment variables and Catch2 arguments passed to the re-executed test program); not user configuration.
engine/foundation/os/windows/debug/death_test.cpp|The death-test child protocol on Windows: the variables that name the case a child runs, as on Linux.
engine/platform/linux/wayland/wayland_input.cpp|The compose table is chosen by the locale the C library would use (LC_ALL, LC_CTYPE, LANG): a standard system variable the keymap library needs by name, read when the keymap arrives; not a user setting of the engine.
engine/platform/linux/window_host_linux.cpp|ENGINE_WINDOW_BACKEND is read when the window host opens its first window, before an application has Settings; the demos mirror it as platform.window_backend.
engine/platform/windows/window_host_windows.cpp|ENGINE_WINDOW_BACKEND is read when the window host opens its first window, before an application has Settings, as on Linux; the demos mirror it as platform.window_backend.
engine/platform/macos/window_host_macos.cpp|ENGINE_WINDOW_BACKEND is read when the window host opens its first window, before an application has Settings, as on Linux and Windows (Phase 26 Day 311); the demos mirror it as platform.window_backend.
engine/platform/windows/entry_point_windows.cpp|The windowed programs' entry point reads the process command line (GetCommandLineW, CommandLineToArgvW) to build UTF-8 argv before any Settings exist; the settings system parses it from there.
engine/jobs/topology.cpp|ENGINE_JOB_THREADS is read when the scheduler starts, which can be before any Settings exists.
engine/rhi/vulkan/vk_instance.cpp|The validation variables (ENGINE_RHI_VALIDATION*, _FATAL) are read at Vulkan instance creation, a process-wide switch for tests and CI; ENGINE_RHI_VALIDATION_SYNC is also renderer.sync_validation.
engine/rhi/dx12/dx12_device.cpp|ENGINE_RHI_VALIDATION and ENGINE_RHI_VALIDATION_SYNC are read at D3D12 device creation, the same process-wide switches as the Vulkan backend's (vk_instance.cpp); the debug layer is process-wide too. ENGINE_RHI_GPU is read when a device picks its adapter, as on Vulkan (the same value is renderer.adapter, which fills DeviceCreateInfo in programs that have Settings).
engine/rhi/metal/metal_device.mm|MTL_DEBUG_LAYER and MTL_SHADER_VALIDATION are read at Metal device creation only to report them: Metal itself reads them when the process starts the framework, so the validation setting is advisory (Phase 26 Day 316). ENGINE_RHI_GPU is read when a device picks its adapter, as on Vulkan and D3D12 (the same value is renderer.adapter, which fills DeviceCreateInfo in programs that have Settings).
engine/rhi/vulkan/vk_loader.cpp|The Vulkan library path override is read while loading the loader, before a device or any Settings exists.
engine/rhi/vulkan/vulkan_device.cpp|ENGINE_RHI_GPU is read when a device picks its adapter (the same value is renderer.adapter, which fills DeviceCreateInfo in programs that have Settings).
engine/rhi/pipeline_cache_file.cpp|ENGINE_RHI_CACHE_DIR is read when a backend opens its pipeline cache (the same value is rhi.pipeline_cache_dir, which fills DeviceCreateInfo in programs that have Settings).
game/renderer_demo/main.cpp|The demo's launch-only options (--frames, --screenshot, --objects, --lights, --gbuffer, --script, --text, --inject-*, ...) and RENDERER_DEMO_FRAMES: scene and test parameters, not settings; the settings options are handled by demo::DemoSettings.
game/ui_demo/main.cpp|The demo's launch-only options (--frames, --screenshot, --script, --scale): run parameters, not settings; the settings options are handled by demo::DemoSettings.
game/rhi_demo/main.cpp|The demo's launch-only options (--frames, --screenshot, --inject-*, --list-gpus) and RHI_DEMO_FRAMES: test parameters, not settings; the settings options are handled by demo::DemoSettings.
game/renderer_bench/main.cpp|Benchmark parameters (--threads, --draws, --section, ...): not configuration of the engine.
game/rhi_bench/main.cpp|Benchmark parameters (--section, --draws, --skip-uploads, ...): not configuration of the engine.
game/ecs_bench/main.cpp|Benchmark parameters (--entities, --frames, --threads, --csv): not configuration of the engine.
game/spatial_demo/main.cpp|Launch-only demo parameters (--entities, --frames, --stats, --debug-draw, --serial): not configuration of the engine.
game/storage_demo/main.cpp|Launch-only demo parameters (--entities, --frames); --file and --columns only publish storage.path and storage.layout into the demo's own registry (it has no settings service).
game/net_demo/main.cpp|Launch-only demo parameters (--simulated, --large): run parameters, not settings; every limit comes from the net.* settings.
engine/foundation/os/windows/debug/post_mortem.cpp|Reads Windows Error Reporting's LocalDumps values (HKLM) to report where a post-mortem dump would go: the system's configuration, never written, not the program's.
engine/foundation/settings/|The settings system itself: it parses the --set, --settings, --save-settings, --list-settings and --help options and the ENGINE_* environment on behalf of every program.
