# Phase 19 / Day 253 — SQLite Backend I: Statements, Transactions & Errors on `:memory:`

**Phase:** [Phase 19 — Storage](../phase-19-storage.md)
**Depends on:** Day 252 (the interface and the conformance suite); Day 251 (SQLite built and fenced).

**Plan change (2026-11-11, the user's decision):** there is no `MemoryDatabase`. A second backend would need its own SQL parser, which is not worth building. The in-memory backend the storage tests want is `storage::MemoryStore` at the `Store` layer (Day 259); when a test needs a database in memory, it uses SQLite's `:memory:`. This day therefore does what Day 255 used to start: the SQLite backend's statements, transactions and error mapping, run first on private in-memory databases, so the conformance suite gets its first real run without the file system.

## Tasks

- [ ] **Minimal VFS** (`engine/database/sqlite/sqlite_vfs.cpp`, the part a database without files needs): the VFS registered once, thread-safely, as the default; `xRandomness`, `xSleep`, `xCurrentTime(Int64)`, `xFullPathname`; `xOpen`, `xDelete` and `xAccess` answer "cannot open" until Day 254 fills them in. A `:memory:` database never opens a file, so it works with this alone.
- [ ] **`database::SqliteDatabase::Open`** for `:memory:` (an empty `location` is a private in-memory database), the options mapped (`foreign_keys=ON`, `busy_timeout`); `Close`. A named location is `Unsupported` until Day 254. The sqlite3 calls stay in `engine/database/sqlite/` (`sqlite_boundary_check`).
- [ ] **Statements:** `Prepare` over `SqlText`, binding every `Value` kind (text and blobs bound by copy), by index and by name, typed column views with the type reported, `Reset`/`ClearBindings`, `Step` mapped to row, done or error; a statement fails safely after its connection closed (documented, tested).
- [ ] **Transactions and savepoints:** `Begin` (deferred and immediate), `Commit`, `Rollback`, the `Savepoint` family with the identifier check, `InTransaction`, `LastInsertRowId`, `ChangedRows`, `SchemaVersion` and `WriteSchemaVersion` (`PRAGMA user_version`, inside this backend only); misuse (a nested `Begin`, `Commit` without `Begin`) is `Misuse`.
- [ ] **Error mapping:** a table from SQLite primary and extended result codes to `ErrorCode` (constraint kinds, `BUSY`, `LOCKED`, `CORRUPT`, `NOTADB`, `FULL`, `IOERR` family, `READONLY`, `TOOBIG`, `MISUSE`, syntax errors, a form SQLite lacks) with the backend code and message kept; no SQLite code or `sqlite3_*` type reaches a public header.
- [ ] **Features:** `Supports` reports what the backend does (savepoints, `WITHOUT ROWID`, add-column, named parameters, foreign keys, write-ahead log and concurrent readers once Day 254 lands the file locks).
- [ ] **Conformance:** the Day 252 suite runs on a SQLite `:memory:` fixture. The cases that need a second connection to one database (two connections, busy writer, schema version seen from another connection, `Another()`) need a named location, so the fixture reports `kSharedLocation = false` and those cases skip with the reason until Day 254 (files) runs them; the suite gains that trait in this day.
- [ ] **Tests** (`tests/database/sqlite_memory_test.cpp`): the mapping table (every listed code maps as documented, an unknown code is `Other`); statement outliving its connection; 1,000 statements prepared and destroyed with no leak (asan); values bound as text and as blob keep their type; a statement text that is not a literal does not compile (`database_sql_check` fixtures already cover the gate).
- [ ] **Runs (CLAUDE.md "Tests run by phase"):** `scripts/test-phase.sh --affected` plain; then the asan and tsan flavors (statement lifetime); quote each run's final `ran X of Y tests (phases ...)` line in this file and never say "all tests pass" for a reduced run. `ctest -L docs` (public headers and the guide change). Build clean (warnings are errors) with Clang and GCC, unity on and off. New code uses the engine's wrappers and types, never `std` (`std_usage_check`).
- [ ] **Two machines (CLAUDE.md "Windows is a supported platform"):** the code is portable; it is built and tested on the Windows PC no later than Day 265, and until then the day is listed as "open until the other machine runs it" in `KNOWN-ISSUES.md`.
- [ ] **Documentation (CLAUDE.md "Public API is documented before a day is done"):** public headers carry `///` comments with the contract labels (`docs/DOC-CONVENTIONS.md`); `docgen lint` stays at zero; `cmake --build build --target docs` output committed; the guide page `docs/guide/database.md` is updated (one backend, the `:memory:` rule, the skipped cases).
- [ ] **Module rules (CLAUDE.md "Module dependencies follow ARCHITECTURE.md"):** `ARCHITECTURE.md`, `tools/module_deps_check/modules.txt` and the CMake targets (with `_asan`/`_tsan` flavors) stay in step; no upward edge, no cycle; every new test file has its line in `tests/phases.txt` (phase 19).
- [ ] **Day review (CLAUDE.md, required):** `/code-review high` over the day's diff after the scoped tests; verify, fix (with a regression test that fails without the fix) or decline each finding with a reason; record the count and outcome under "Post-implementation code review" below and in `STATUS.md`.
- [ ] `STATUS.md` and `KNOWN-ISSUES.md` updated in the same commit; commit and push.

**Done:** SQLite, behind the database interface, runs the conformance suite on in-memory databases; a statement it cannot run is an error value. The multi-connection cases are skipped with a reason until Day 254.
