## Notes (2026-11-11, Linux machine)

- **Settings.** `storage.path` (text), `storage.layout` (`blob`, `columns`), `storage.autosave_seconds` (0 is off) beside the four limits; `PathFromSettings`, `ColumnsFromSettings`, `AutosaveSecondsFromSettings`. **Deviation:** the plan names `WorldStorage::OpenFromSettings`; a `WorldStorage` borrows its store, so the opener is `LocalStorage::OpenFromSettings(backend, settings, components, &out)` (`local_storage.h`), which owns the connection, the SQL store and the `WorldStorage`. The backend is passed in because `storage` may not name SQLite.
- **Save is plan, write, adopt.** `Save` was split: `Plan` reads the world (encodes in rounds of `batch_size`, on the workers when a scheduler is given, each task filling its own slot, so the result is independent of the schedule), `Write` touches the store only, `Adopt` updates the session. The synchronous `Save` is the three in a row (it now holds the encoded records of a whole save in memory instead of streaming them; `Write` frees each as it goes; to be measured on Day 265). `SaveAsync` runs `Plan` on the caller (the main thread of the scheduler) and `Write` as one job; because the world is not read afterwards, "the world as the frame left it" holds by construction. The world is advanced at the snapshot, so later writes are stamped later than the save. **Deviation:** the encoding happens inside the `SaveAsync` call (parallel, but the caller waits for it), only the store writes are in the background; for an incremental save that is proportional to the changes.
- **`LoadAsync`** copies the stored records and metadata into a `MemoryStore` on a job; `AsyncLoad::Finish` runs the ordinary `Load` from that copy on the caller's thread. The world is untouched until `Finish`. Decoding stays on the caller (it creates entities).
- **Autosave** is `Autosaver` (`Update(dt)` once a frame, `SaveNow`, `Flush`), not an ECS system: `SaveAsync` uses the scheduler's blocking parallel loop, which is main-thread-only, and systems may run on workers.
- **Demo** `game/storage_demo` (ctests `storage_demo_runs`, `storage_demo_columns_runs`, phase 19): a city with a hierarchy and the spatial sets is saved to a file named by the settings, loaded into a fresh world and compared component by component; 200 box queries agree between the original, the loaded world and a scan; 60 frames with the autosaver, then the last autosave equals the running world. **Not done:** the render-scene draw-list comparison; `MeshRenderer` holds a GPU mesh and has no stored form until the asset pipeline (Phase 21) (KNOWN-ISSUES.md).
- **Tests** (`tests/storage/async_test.cpp`, 11 cases): async equals sync byte for byte over 104 worlds with 1-8 participants; five rounds of world changes while the writer runs (TSan clean); cancel at each of the progress callbacks (every cut leaves the store as it was; 8 or more cuts hit); a second writer is `Busy`; an injected store failure comes from `Finish`; a handle dropped without `Wait` on a scheduler with no workers (hung before the fix: confirmed by a mutation that timed out); incremental async rounds equal a fresh full save; autosaver; `LoadAsync` (untouched world, cancelled, selected keys); settings and `LocalStorage` on a real file with columns and a low limit.
- Gates: `config_access_check` (allow-list entry for the demo's launch flags), `sqlite_boundary_check`, `module_deps_check`, `std_usage_check`, `file_access_check`, `platform_neutral_check` pass. Clang (unity and not) and GCC (not unity) build clean. Docs: storage 389 of 389 documented; `ctest -L docs` 7 of 7 (the tutorial `docs/tutorials/saving-a-world.md` compiles and runs).
