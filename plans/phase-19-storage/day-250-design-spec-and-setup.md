# Phase 19 / Day 250 — Design Spec, Spikes & Phase Setup

**Phase:** [Phase 19 — Storage](../phase-19-storage.md)
**Depends on:** Phase 18 complete (the spatial members are rebuilt on load, never stored); Phase 17 (change stamps, the removal log, `Parent`); Phase 9 (`io::File`); Phase 11 (settings).

Settle the storage and database design with measurements before any code, fix the benchmark baseline, and set up the phase. This is a planning-and-spike day: no engine code ships.

## Tasks

- [ ] **`CURRENT_PHASE` becomes 19** in the commit that completes this day's first task, with phase 19 named in `tests/phases.txt` (its `flavors 19` line and the `tests/database/` and `tests/storage/` mappings arrive with the first test, Day 251).
- [ ] **Spec** `docs/superpowers/specs/2026-11-NN-storage-design.md` recording each decision below with its reason (the planner's defaults in brackets; a spike that disproves one amends the later day files in the same commit):
      - modules [`engine/database` (the interface, the in-memory implementation and `engine/database/sqlite/`, layer above `foundation` only) and `engine/storage` (registry, identities, `Store`, `SqlStore`, the world codec; depends on `foundation`, `ecs`, `jobs` and `database`); no ECS type in `database`, no SQL type in `storage`'s public headers];
      - two interfaces [`storage::Store` is a **record store** (put, get, remove, scan, an all-or-nothing batch) so a binary file store or a network store implements record I/O only; `storage::WorldStorage` is the non-virtual layer that reads a `World` through the registry, writes records and loads them back; the phase file's `Store::Save(world, ...)` is realised as `WorldStorage::Save`];
      - registry [stable component id (a `u32` written in code, checked unique) plus name, version, field descriptions by pointer-to-member, custom save/load pairs, upgrade chains; canonical little-endian encoding, bit-exact floats, no padding; a `Derived` flag for components rebuilt on load (`WorldTransform`, `HierarchyDepth`, `WorldBounds`, `SpatialProxy`)];
      - identities [`EntityKey` 128-bit random, stored as a component; a `KeyIndex` resource; references stored as keys, resolved in a second pass; a missing target is a `Status` or a nulled reference by option];
      - what is stored [components of entities only; no resources; the spatial sets, render handles and derived components are rebuilt; the list of ECS resources stored is empty];
      - layouts [blob per component record as the default; column-per-field tables for components flagged queryable, if the layout spike justifies them];
      - incremental saves [chunk written-ticks since the last save inside a process; across processes a stored content hash per record so unchanged records are not rewritten; the removal log's capacity limit and the fallback when it overflowed];
      - determinism [the same stored state into an empty world gives the same entity order and archetype layout];
      - threads [one writer at a time per database, readers on worker jobs, the async forms run on the job system];
      - untrusted input [every length bounded by a setting, every decode checked, a hostile file is an error value];
      - settings [`storage.path`, `storage.layout`, `storage.max_record_bytes`, `database.journal_mode`, `database.synchronous`, `database.busy_timeout_ms`, `database.integrity_check`];
      - not in this phase [a binary save-game file store, a network store, a cloud store, resources, streaming of world cells (Phase 33), the asset format (Phase 21 reuses the registry, not the database)].
- [ ] **Spike (a), the SQLite VFS over `io::File`:** list what SQLite needs from its OS layer (`xOpen`, `xRead`, `xWrite`, `xTruncate`, `xSync`, `xFileSize`, locking, `xDelete`, `xAccess`, `xFullPathname`, randomness, sleep, time, and the shared-memory methods WAL uses) against what `io::File` offers (read and write at an offset, `Flush`, `Sync`, `Truncate`, no file locking, no shared memory); decide whether a VFS built on `io::File` with in-process locks and `locking_mode=exclusive` (or a heap-backed WAL index) is practical, which journal mode the defaults use, and what the fallback is (an entry on the `file_access_check` allow list). Record the answer; Day 254 builds exactly that.
- [ ] **Spike (b), the storage layout:** 100,000 entities with six components each, stored (1) as one blob row per component, (2) as one blob row per entity, (3) as column-per-field tables, in SQLite: insert time in one transaction, full load time, file size, and one field query (all entities with `health < 10`); record a table and choose the default and the queryable option.
- [ ] **Spike (c), the in-memory database's scope:** write down the exact SQL statements and column types `SqlStore` will use (create table and index, insert and insert-or-replace, select with equality `WHERE` and `ORDER BY`/`LIMIT`, update, delete, transactions, savepoints, a schema-version value); that list is the contract of the in-memory implementation (Day 253) and the portable subset `SqlStore` is restricted to.
- [ ] **Spike (d), SQLite itself:** choose and pin the amalgamation version and its SHA-256, the compile options (no extension loading, no shell, no deprecated interfaces, `SQLITE_DQS=0`, `SQLITE_DEFAULT_FOREIGN_KEYS=1`, threading mode, `SQLITE_OS_OTHER` if the VFS route is chosen), and the vendored size; check the license text to ship.
- [ ] **Benchmark definition** fixed in the spec so Day 265 cannot move the goalposts: workloads (100,000 and 1,000,000 entities, six components, depth-5 hierarchy; full save, full load, incremental save with 1 percent changed, an idle-world incremental save), the metrics, and the pass condition for each (numbers set from the spikes).
