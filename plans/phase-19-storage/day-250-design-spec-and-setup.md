      - modules [`engine/database` (the interface, the in-memory implementation and `engine/database/sqlite/`, layer above `foundation` only) and `engine/storage` (registry, identities, `Store`, `SqlStore`, the world codec; depends on `foundation`, `ecs`, `jobs` and `database`); no ECS type in `database`, no SQL type in `storage`'s public headers];
      - two interfaces [`storage::Store` is a **record store** (put, get, remove, scan, an all-or-nothing batch) so a binary file store or a network store implements record I/O only; `storage::WorldStorage` is the non-virtual layer that reads a `World` through the registry, writes records and loads them back; the phase file's `Store::Save(world, ...)` is realised as `WorldStorage::Save`];
      - registry [stable component id (a `u32` written in code, checked unique) plus name, version, field descriptions by pointer-to-member, custom save/load pairs, upgrade chains; canonical little-endian encoding, bit-exact floats, no padding; a `Derived` flag for components rebuilt on load (`WorldTransform`, `HierarchyDepth`, `WorldBounds`, `SpatialProxy`)];
      - identities [`EntityKey` 128-bit random, stored as a component; a `KeyIndex` resource; references stored as keys, resolved in a second pass; a missing target is a `Status` or a nulled reference by option];
      - what is stored [components of entities only; no resources; the spatial sets, render handles and derived components are rebuilt; the list of ECS resources stored is empty];
      - layouts [blob per component record as the default; column-per-field tables for components flagged queryable, if the layout spike justifies them];
      - incremental saves [chunk written-ticks since the last save inside a process; across processes a stored content hash per record so unchanged records are not rewritten; the removal log's capacity limit and the fallback when it overflowed];
      - determinism [the same stored state into an empty world gives the same entity order and archetype layout];
      - threads [one writer at a time per database, readers on worker jobs, the async forms run on the job system];
      - untrusted input [every length bounded by a setting, every decode checked, a hostile file is an error value];
      - settings [`storage.path`, `storage.layout`, `storage.max_record_bytes`, `database.journal_mode`, `database.synchronous`, `database.busy_timeout_ms`, `database.integrity_check`];
      - not in this phase [a binary save-game file store, a network store, a cloud store, resources, streaming of world cells (Phase 35), the asset format (Phase 22 reuses the registry, not the database)].

## Notes

- Spec: `docs/superpowers/specs/2026-11-11-storage-design.md` (decisions, four spikes with tables, the benchmark pass condition in section 4). Spikes were throwaway programs (not committed; `std` and the system SQLite 3.54.1 on purpose), Ryzen 9 7950X3D, NVMe.
- Findings that changed the plan: (1) **the VFS route works** on exactly `io::File`'s surface, but WAL needs a version-2 VFS with shared-memory methods (a version-1 VFS silently stays in `DELETE`); 600 injected-failure runs were consistent; no allow-list entry needed (Day 254 amended: real lock rules, a lock file, sync and truncate faults); (2) **the default layout is one row per entity** (a framed blob), 3.2x faster to insert and 4x faster to load than a row per component and half the size; column tables are optional for queryable components (Days 262-263 amended); (3) **a full save sorts by key** (3.9x-6.2x faster inserts; Day 260 amended); (4) `SchemaVersion()` on `Connection` and `Supports(AddColumn)` replace `PRAGMA` text (Days 252-253 amended); (5) `ByteWriter`/`ByteReader` move to `foundation/bytes/` so Phase 20's `NetWriter` shares them (Day 256 and `plans/phase-20-networking.md` amended).
