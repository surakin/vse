# Phase 20 — Networking (TCP, UDP, and Possibly QUIC)

**Status: complete on Linux (2026-11-12), Days 266-279 and 281 done, Day 280 (QUIC/TLS/encryption) deferred by the user. Open: the Windows PC run of Days 277-281. Next: Phase 21 needs its day files before it starts.**

**Depends on:** Phase 2 (job system and its async I/O, the scheduler that runs network work), Phase 9 (file layer patterns: errors as values, a test double that proves the interface), Phase 11 (settings), Phase 16 (wrappers), Phase 13 (the Windows platform layer, for the Windows socket backend). Phase 19 (storage) is not required, but a store over the network is its first user.
**Goal:** one portable socket and transport layer for the whole engine (game traffic, tools, remote debugging, the resource system's network backend, a store over the network), with TCP and UDP from the first day and a QUIC transport if the Phase's spike justifies it.
**Definition of done:** a `net` module with addresses (IPv4 and IPv6), non-blocking TCP and UDP sockets on Linux and Windows through one interface, readiness handled by the job system's I/O (no thread per connection), and a `Transport` interface above sockets that gives callers connections with reliable ordered and unreliable channels; implemented on TCP and on UDP (with the reliability layer written here); tested on loopback with injected loss, reordering, duplication, delay and partial reads and writes, race-free under the sanitizers, with hostile input fuzzed. The QUIC decision is recorded with its evidence, and a QUIC transport exists if the decision is yes.

## Key deliverables (broken into days below)

- **Socket layer.** `net::Address`/`Endpoint` (a value type with no syscalls, parsing and formatting), `net::Socket` for TCP streams, listeners and UDP datagrams, non-blocking only, with the platform code in `linux/` and `windows/` directories behind a `BACKEND.md` checklist (as the platform, file and settings layers do); `socket`, `bind`, `connect` and the like are called only from those directories (a gate like `file_access_check` enforces it). Name resolution uses the system's resolver (`getaddrinfo`, part of the OS) run on a job so it never blocks a frame. IPv6 and dual-stack where the OS allows. Errors are values (`net::Status`), never exceptions, with portable codes (refused, reset, timed out, unreachable, would block, address in use).
- **Readiness and I/O on the job system.** `epoll` on Linux and I/O completion ports (or `WSAPoll` first) on Windows, feeding the job scheduler's existing async I/O so a coroutine can `co_await` a read, a write, an accept or a datagram; timers and timeouts through the same facility. No ad hoc thread pools (`PLAN.md` assumption #15).
- **TCP.** Framing helpers (length-prefixed messages with a size limit), backpressure (a bounded send queue that reports full instead of growing), graceful and abortive close, keep-alive and connect timeouts from settings.
- **UDP and the reliability layer.** Datagrams with the MTU in mind, then, above them, the part games need and TCP does not give: connection establishment with a handshake and a challenge against address spoofing, sequence numbers and acknowledgements, channels (unreliable, unreliable-sequenced, reliable-ordered, reliable-unordered), fragmentation and reassembly of large messages, round-trip-time estimation, congestion control (a conservative, documented algorithm), and keep-alive and timeout. Written here and tested hard, since it is the part with the subtle bugs.
- **The transport interface.** `net::Transport`/`net::Connection`: `Listen`, `Connect`, `Send(channel, bytes, reliability)`, `Receive`, connection events (opened, closed with a reason), per-connection statistics; implemented by the TCP transport and the UDP transport, and by a **simulated transport** (an in-process one with configurable loss, reordering, duplication, latency and bandwidth) that every higher layer's tests use and that proves the interface fits more than one backend.
- **Message encoding (Phase 19 Day 256 puts the bounds-checked `ByteWriter`/`ByteReader` in `foundation/bytes/`; `NetWriter`/`NetReader` extend them with quantized floats and bit packing rather than re-implement them).** A bit/byte `NetWriter`/`NetReader` over `Span` with bounds checks, fixed-width and variable-width integers, quantized floats, strings with limits; no pointer casts; every read can fail with an error value. It reuses the serialization vocabulary of Phase 19 where that fits (the same primitives, not the same formats).
- **Security basics.** Every length bounded before allocation, a per-connection memory budget, a rate limit on handshakes and on accepts, nothing trusted before the handshake completes; the transport does not provide confidentiality by itself (see the encryption question below). Parsers are fuzzed.
- **QUIC (a spike, then a decision).** QUIC (RFC 9000) needs TLS 1.3 and a large amount of state machine; writing it from scratch is a project of its own and the zero-third-party rule says to prefer what the operating system provides. The spike compares: (a) a vendored library (for example ngtcp2 with a TLS library, quiche, msquic) as an individually justified exception like FreeType and LuaJIT, (b) the operating system's own (Windows ships MsQuic; Linux has no system QUIC), (c) not doing QUIC and putting TLS on the TCP transport, (d) deferring QUIC to a later phase. The outcome is a recorded decision for the user (it adds a dependency whichever way it goes), with sizes, licenses and what each costs to port to the other platforms; if the answer is yes, a QUIC `Transport` is implemented behind the same interface, with streams mapped to reliable channels and datagrams to unreliable ones.
- **Encryption and authentication** are a design question the spec raises and the user decides: none in this phase (trusted networks only), DTLS/TLS through the same vendored or OS library as the QUIC decision, or an authenticated-encryption layer of our own on top of an audited primitive (never custom cryptography). The default plan is to decide it together with QUIC, since both want a TLS implementation.
- **Tools and tests.** A loopback echo and throughput benchmark (messages per second, latency percentiles, CPU per connection), a soak test with thousands of simulated connections, a `net_probe` tool for manual checks, and a settings group (`net.*`: ports, timeouts, buffer sizes, simulated conditions for testing).
- **Integration.** The resource system's network backend (Phase 21) and a network store for Phase 19 become thin users of this layer; replication of ECS state (snapshots, deltas from the change stamps, interest management through `engine/spatial`) is a later phase's work, and the spec records the hooks it will need so they are not retrofitted.

## Notes / open questions

- **Sockets are the operating system's own API** (like Win32 and POSIX file calls), so using them is not a third-party dependency; only QUIC and TLS can add one, and each such dependency needs its own entry in `PLAN.md` (assumption #26 states the rule and the open decision).
- **Platforms:** Linux and Windows first; macOS is designed in (the same BSD socket interface, `kqueue`), and mobile and consoles need their socket backends and permission/lifecycle handling (Phases 27 and 28 list them). Nothing in the transport interface may assume a desktop OS.
- **No packet sniffing, raw sockets or anything that needs privileges**: ordinary unprivileged sockets only.
- **Determinism and tests:** the simulated transport is deterministic (seeded) so a networking bug can be replayed; the real-socket tests use only loopback and ephemeral ports and are labelled so a sandbox without network access skips them with the reason.
- Out of scope for this phase: game-level replication and prediction, matchmaking and relay servers, NAT traversal, voice, HTTP and WebSocket clients (a possible later addition on top of TCP+TLS), and any web or browser platform.
- The day files are written (2026-11-11). The QUIC/TLS/encryption spike is Day 266 and the user deferred the decision on 2026-11-12 (Day 280 is skipped); Days 267-279 do not depend on it. Day 278 (Windows backend) and the Windows half of Day 281 run on the Windows PC.
