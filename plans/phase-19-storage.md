# Phase 19 — Storage (Entity Persistence & the SQL Database Interface)

**Depends on:** Phase 17 (ECS: entities, components, change detection, the scene bridge), Phase 18 (spatial partitioning: spatial members are rebuilt on load, never stored), Phase 9 (file layer: `io::File`, atomic writes), Phase 11 (settings), Phase 16 (wrappers: all new code uses them).
**Goal:** one generic way to save and load entities, independent of where the bytes go, so that save games, persistent worlds, editor scenes, server state and tools all use the same interface; a SQL database interface under it, with SQLite as the first implementation.
**Definition of done:** a `storage` interface saves a selection of entities of a `World` (components, hierarchy, stable identities) and loads them back into a world, exactly (round trip is bit-exact for every stored component, tested), versioned (an older stored version loads through registered upgrades), and incremental (a save writes what changed since the last one, using the ECS change stamps). A `database` interface (connections, statements, transactions, typed values, errors as values) has a first implementation on SQLite and an in-memory test double; a SQL storage implementation sits on the database interface. No SQL type reaches code above the database interface and no storage type reaches code that only uses the ECS.

## Key deliverables (to be expanded into day-by-day tasks when started)

- **Component serialization registry.** Today the ECS has no serialization (a Phase 17 limit). This phase adds, outside `ecs` and without changing its hot paths, a registry that describes how each component type is stored: a stable name and numeric id (never the in-memory type id, which changes between builds), a version, a field description (scalars, vectors and quaternions, fixed arrays, `String`, entity references, enums) or a custom save/load pair, and a chain of upgrade functions between versions. A component not in the registry is not stored (and a debug check lists the ones that carry data but are not registered, so a new component cannot be forgotten silently). The registry is the piece Phase 21 (asset pipeline) reuses for its level format.
- **Stable identities.** An `EntityKey` (a 128-bit id, generated once and stored with the entity through a component) names an entity across saves, processes and machines; entity ids of a world are never stored. Entity references inside components (`Parent`, user references) are stored as keys and remapped on load; a reference to an entity that is not in the stored set is an error value, not a dangling id.
- **The storage interface.** `storage::Store`, an abstract interface (the same pattern as `io::File` and the RHI: upper layers never know the backend): `Save(world, selection, options)`, `Load(world, selection, options)`, `Delete`, `List`, a transaction-like unit so a save is all or nothing, synchronous and asynchronous forms (asynchronous ones run on the job system), progress and cancellation, and errors as values (`storage::Status`). A selection is "every entity with `EntityKey`", a set of keys, or a query (an ECS query plus a filter). Loading can create, replace or merge, and says what it did.
- **Incremental saves.** A saver remembers the world tick of its last save and writes only the chunks whose stamps changed, plus removals (the ECS removal log), so saving a large mostly idle world costs what changed. A full save and an incremental one produce the same stored state (tested).
- **The database interface.** `database::Database`, `Connection`, `Statement` (prepare, bind by index and name, step, columns), `Transaction` (begin, commit, rollback, savepoints), typed values (null, integer, real, text, blob), a result as rows pulled one at a time, errors as values (`database::Status` with a portable code and the backend's message), and a capability query (`Supports(Feature)`) so code can ask for what a backend lacks. No SQL text is built from user data by concatenation anywhere in the engine: statements are prepared and bound (a gate checks for `Execute` with a formatted string outside tests).
- **First implementation: SQLite.** A vendored SQLite amalgamation behind the interface, in one library (`database_sqlite`); only its implementation file includes the SQLite header (a boundary gate like the debugging facade's). Its file access goes through the engine's file layer (a SQLite VFS built on `io::File`, so the `file_access_check` rules hold and the platform backends stay the only place that touches the operating system) or, if that proves impractical, through a documented entry on that gate's allow list decided by the phase's spike. Write-ahead logging, a busy timeout, foreign keys on, and a single writer with many readers are the defaults, set through the settings system.
- **Second implementation: in memory.** A small in-memory database that implements the interface (enough SQL for the storage layer's own statements, or a restricted statement set it recognizes), as the test double that proves the interface does not leak SQLite: the same conformance suite runs against both.
- **SQL storage implementation.** `storage::SqlStore` on `database::Connection`: a schema (entities, component rows per registered component or one blob table per component, hierarchy, a metadata and version table), migrations of the schema itself with a recorded version, indexes on the key, and bulk paths (multi-row inserts inside one transaction). Whether components are stored column per field (queryable from SQL, good for tools and servers) or as blobs (fast, opaque) is a design question the spec settles with measurements; both may exist behind the same interface.
- **Other stores later, not now.** The interface is shaped so a binary file store (a save game in a single file, using `io::File`), a store over the network (Phase 20) and a cloud store fit without changing callers; none is built in this phase beyond what the conformance suite needs.
- **Integration.** A settings group (`storage.*`: location, journal mode, busy timeout), a demo saving and loading the Phase 17 and 18 demo worlds (the loaded world renders and culls like the original, compared by the golden image and by a brute-force comparison of the spatial sets), benchmarks (save and load of 100,000 and 1,000,000 entities, full and incremental), and the guide `docs/guide/storage.md`.

## Notes / open questions

- **SQLite is a third-party library and is an accepted exception (the user confirmed it on 2026-11-10; `PLAN.md` assumption #25, same category as FreeType and LuaJIT).** The reason: a correct, crash-safe, transactional SQL engine is not engine-differentiating work and the user asked for SQL storage; it ships inside the runtime binary of programs that use storage, vendored as source under `third_party/sqlite/` (public domain), pinned by version and hash, compiled with the options the spec lists (no extension loading, no shell). Only the `database_sqlite` implementation file includes its header.
- **Storage is not the asset pipeline.** Assets (Phase 21) are authored, minted, immutable and versioned per type; storage is the mutable state of a running world (progress, placed objects, a server's persistent entities). They share the component serialization registry and the identity rules, not the formats; the spec states the boundary so a minted level does not become a database dump or the reverse.
- **Scope of what is stored is the user's call to extend:** components of entities only. Resources of the world, the spatial sets, the render handles and every derived structure are rebuilt on load; the spec lists which ECS resources are stored (none by default).
- **Determinism:** loading the same stored state into an empty world produces the same entity order and the same archetype layout (tested), so replays and tests can rely on it.
- Threading: one writer at a time per database; reads run on worker jobs; the interface documents what is thread-safe.
- Security: a stored file is untrusted input on load (a save game from the internet). Every length is bounded, every decode is checked, and a corrupted or hostile file produces an error value and never an out-of-bounds read (fuzzed and sanitizer-tested).
- Windows and Linux are both supported from the start (the SQLite VFS and the file layer already have both backends); macOS is designed in.
