## Result

`game/common/textures.{h,cpp}` (shared by the demo and tests, not part of the RHI): procedural textures (checkerboard, solid, UV gradient), `CreateSampledTexture` (create, upload level 0, optionally `GenerateMips`, wait), and the throwaway `.rtex` container (`BuildRtex` makes a CPU mip chain - averaged as linear light for sRGB formats - `WriteRtex`/`ReadRtex` with full validation, `CreateTextureFromRtex` uploads every stored level). `CubeRenderer` gained a textured mode (`CubeOptions::textured`, `SetTexture`) using the new `textured.vert`/`textured.frag` (sample the texture at the interpolated uv, multiply by the vertex color; UBO, texture and sampler in one bind group). `rhi_demo` draws the textured spinning cube, loading `game/rhi_demo/assets/checker.rtex` (all nine mip levels stored, sRGB, regenerated by the golden-update switch) with trilinear filtering and anisotropy 16, and falls back to a procedural texture; `--screenshot` works (checked on Wayland and X11 with validation clean). Tests (`tests/rhi/vulkan_textured_cube_test.cpp`): a 2x2 nearest-filtered texture shows its four colors in the face's quadrants; the same mid-gray as `RGBA8_UNorm` and `RGBA8_SRGB` gives 64 and 27 on the red channel (the sRGB decode); a 256x256 one-texel checkerboard with generated mips stays within 110..145 over a face patch while the single-level version spans at least 100 levels (proves the mips are bound); the textured cube against `tests/rhi/golden/textured_cube.ppm` (inspected by eye) with three analytic cell probes (sRGB decode and face tint applied by hand); rtex round trip and every damaged-file case; procedural content; sRGB mip averaging; a 1x1 texture with mips requested. Guide section "Textures in draws"; tutorial step "Add a texture" with a compiled and run null-device sample. Docs 1683/1683 (8 samples).

Deviation from the plan: the `.rtex` writer lives in `game/common/textures.cpp` rather than in test-only code, so the demo asset can be regenerated with `ENGINE_RHI_UPDATE_GOLDEN=1` and the format has one implementation.

## Post-implementation code review

`/code-review high` returned 8 findings.

Fixed: (1) `CreateSampledTexture` asks for mips only when the image has more than one level (a 1x1 image would have tripped an assert); a test covers it. (2) The tests' scratch files are per-process (`gpu_test::TempPath`, also used by the golden and diff-image paths): the same tests are registered in three executables that ctest can run at once. (3) `BuildRtex` averages the color of sRGB formats as linear light, as the GPU's `GenerateMips` does; the asset was regenerated and a test checks 188 instead of 128. (4) The helpers accept only the four 8-bit RGBA/BGRA formats (R32_Float and friends would have been averaged byte-wise); a test checks the refusal. (5) The demo falls back to the procedural texture when the file loads but cannot be uploaded, not only when it is missing. (6) `<string>` is included. (7) The mip test's comment says about five texels per pixel. (8) Day file and `STATUS.md`.

Declined: the absolute asset path baked into the demo (`RHI_DEMO_ASSET_DIR`): the demo is a development tool run from the build tree, and it already falls back to a procedural texture and says so; installing assets belongs with the asset pipeline. Running the asset check in the sanitizer flavors: it is a plain file read of a committed asset and fails there only if the asset really is damaged. The mip thresholds were left as measured (the single-level version spans about 255 levels, the mipped one stays within a few levels of mid-gray), not tuned to a driver.
