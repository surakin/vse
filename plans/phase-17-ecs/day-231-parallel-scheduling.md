# Phase 17 / Day 231 — Parallel Scheduling Through the Job System

**Phase:** [Phase 17 — ECS](../phase-17-ecs.md)
**Depends on:** Day 230; Phase 2 (`Scheduler`, `Counter`, `parallel_for`).

The stretch goal of the original plan, made a deliverable: independent systems run as jobs, one system's chunks run in parallel, and the result stays deterministic.

## Tasks

- [x] **Conflict graph:** from the declared access sets, two systems conflict when one writes what the other reads or writes (components and resources); `Schedule::Build()` groups each stage into *waves*: the largest sets of mutually non-conflicting systems that respect the order constraints, found greedily in registration order (a later system never overtakes an earlier conflicting one, which preserves the sequential semantics).
- [x] **Execution:** a wave submits one job per system through the job `Scheduler` and joins on a `Counter`; the frame thread helps (`HelpUntil`) as everywhere else in the engine; no thread of the ECS's own; with `ecs.parallel_systems` off, or no scheduler, the waves run inline in order (the same code path with a different submit).
- [x] **Chunk parallelism inside one system:** `ForEachChunkParallel(fn, grain)` over the query's chunks through `ParallelForBlocking`/`ParallelFor`; a chunk is the unit of work (no two jobs touch one chunk); the grain defaults to a count that gives each worker a few jobs; the system's command buffer becomes one buffer per job taken from the `CommandBufferPool`, merged in chunk order at the end so playback is independent of the job schedule.
- [x] **Determinism contract** (written in the guide): for systems whose results do not depend on iteration order, a frame's resulting world state is bit-identical to the sequential run; ordering-sensitive reductions use `ForEachChunk` with per-chunk partial results combined in chunk order (a helper `ReduceChunks<T>(init, per_chunk, combine)`).
- [x] **Safety net:** in debug builds each system's declared access is enforced (Day 230), and a `ParallelAccessChecker` records, per wave, which component columns each running system touched; two systems of one wave touching the same column with a write is an assert naming both.
- [x] **Tests** (`tests/ecs/parallel_test.cpp`, with the job scheduler at 1, 2, 4 and the machine's count): wave construction on hand-made access sets (disjoint writers share a wave, reader-after-writer does not, order is preserved); a pipeline of 8 systems over 200k entities gives a world state equal to the sequential run (compared by hashing all component bytes) over 50 frames and over 20 different thread counts/timings (`ENGINE_JOB_THREADS`); `ReduceChunks` equals the sequential sum exactly for floating point (fixed chunk order); command buffers from parallel chunks apply in chunk order; the access checker catches a deliberately wrong declaration; **tsan** runs the whole file; a stress test of 1,000 frames with 16 systems and random structural commands ends with `Validate` clean; scaling table (1, 2, 4, N workers) for one heavy system recorded here.

Build clean (warnings are errors) with Clang and GCC, unity on and off. New code uses the engine's wrappers and types, never `std` (`std_usage_check`).

## Notes

- Waves: `Build()` puts a system one wave after the latest earlier system of its stage that conflicts with it (component or resource write/read overlap) or must precede it; `Schedule::WaveOf(position)`. `Run` with a `jobs::Scheduler` (`SetScheduler`) and `ecs.parallel_systems` on submits the members of a multi-system wave as jobs inside `World::BeginParallel/EndParallel` (queries skip their non-thread-safe iteration bookkeeping) and `HelpUntil`s; a wave of one runs on the frame thread and may fan out. Otherwise strictly sequential, same code per system (`RunSystem`).
- `Query::ForEachChunkParallel` (with and without a `CommandBufferPool`: one buffer per range of chunks, applied by range number = chunk order), `Query::ReduceChunks<T>`, `SystemContext::ForEachChunkParallel/ReduceChunks`. A job cannot `HelpUntil`, so inside a multi-system wave the same calls run their ranges in order on that job's thread (same result).
- `engine/ecs` now links `jobs` (`allow ecs jobs` in `modules.txt`, `ARCHITECTURE.md` row and note updated).
- **Deviations:** no separate `ParallelAccessChecker` type: a wrong declaration is caught by the Day 230 declared-access check, and waves are conflict-free by construction from the same declarations (test: `a wrongly declared system is caught while running in a wave`); undeclared touches through captured pointers are left to ThreadSanitizer (documented). The "20 thread counts/timings" are 8 worker counts x 3 repeats of a fresh scheduler, not `ENGINE_JOB_THREADS`.
- Scaling of one heavy system (500k entities, debug build, best of 5, chunks split by `ForEachChunkParallel`): 1 participant 186.0 ms, 2: 93.8 ms, 4: 48.5 ms, 8: 25.0 ms (7.4x at 8). The release-build parallel efficiency target is measured on Day 235.
- Open: the Windows build and run ("Two machines").
- Runs: `ran 2070 of 5355 tests (phases: all; flavors: plain; display: included; crash tests: excluded)` (only the two known X11 failures), asan `ran 1553 of 5355`, tsan `ran 1235 of 5355` (the whole `Parallel:` file included, clean); after the review's small fixes the ecs tests were re-run plain and under tsan, GCC and Clang non-unity clean, `ctest -L docs` 7 of 7.
