# Phase 2 / Day 34 — Async I/O Integration

**Phase:** [Phase 2 — Job System & Coroutines](../phase-02-job-system.md)
**Depends on:** Day 32 (Counter/await mechanism) and Phase 1 Day 16
(`os::ReadFileToArena`).

Phase design decision **D8**: blocking reads run on a **dedicated I/O
thread that is not a pool participant**, and the awaiting coroutine is
resumed on a *participant* by going through `Counter::Decrement`'s
injection-queue path (Day 32) — so a slow read never occupies a compute
worker, and no continuation ever runs on an ad hoc thread.

## Tasks

- [x] Implement `IoThread` in `/engine/jobs/async_io.h`/`.cpp`: one
  `std::thread` (not registered as a participant; `IsParticipantThread()`
  is false on it) servicing a mutex+condition-variable request queue,
  started and stopped with the `Scheduler`; shutdown drains or rejects
  pending requests deterministically and joins.
- [x] Define `ReadFileAsync(path)` as a `co_await`-able: the request owns
  a `String`-or-fixed-buffer copy of the path and its own
  `ArenaAllocator` for the result; the awaiting job `Increment`s a
  per-request `Counter`, enqueues the request, and suspends on that
  counter. The I/O thread calls `os::ReadFileToArena` (the arena is used
  by exactly one thread at a time: the I/O thread until completion, then
  the awaiting job — the counter's release/acquire provides the
  happens-before), stores a `FileReadResult { ok, data, size }`, and
  `Decrement`s the counter from the I/O thread, which (non-participant)
  routes the continuation through the injection queue.
- [x] Failure path: a missing/unreadable file yields `ok == false`
  without hanging the awaiter or the I/O thread.
- [x] Test: inside a job, `co_await ReadFileAsync(path)` returns the
  correct bytes for a test file generated by the test (known contents,
  including a multi-megabyte one and an empty one) and fails cleanly for
  a nonexistent path.
- [x] **Assert** (not just log) the resume thread: after the `co_await`,
  `IsParticipantThread()` is true and the thread id differs from the
  `IoThread`'s id. Log the id too for diagnosis.
- [x] Test concurrency: 64 jobs each awaiting a different file read at
  once all complete correctly, and while a deliberately slow read is in
  flight (a FIFO/blocked path or a large file), unrelated compute jobs
  still run on the workers (proves the read isn't blocking a worker).
- [x] Run under `jobs_tests_tsan` and `jobs_tests_asan`.
- [x] Commit.

**Done:** `co_await ReadFileAsync(path)` inside a job returns the correct
contents (and fails cleanly on a bad path), the awaiting coroutine
always resumes on a registered participant and never on the I/O thread
(asserted), compute jobs keep running during a slow read, clean under
TSan/ASan.

## Post-implementation code review (2026-11-03, `/code-review high`)

Fixed: `IoThread::Enqueue` after shutdown aborted the process → it now
returns false and the awaiter completes inline with `ok == false` (test);
`Shutdown()` serialized so concurrent callers all return only after the
join (test, 50 rounds); per-request 64 MiB arena reservation replaced by
sizing the arena from the file's real length on the I/O thread (no
up-front mmap for every request, no silent failure of huge reservations,
files over `max_bytes` fail); `ReadState` now derives from `IoRequest`
(static_cast, no offsetof/reinterpret_cast); redundant second assert in
`await_resume` replaced by the Debug log of the resuming participant the
plan asked for; FIFO test releases the blocked I/O thread via an RAII
guard so a failing REQUIRE cannot hang `~Scheduler`; new tests for
shutdown draining, reads after I/O shutdown, concurrent Shutdown; dead
variable removed; docs reworded: the drain guarantees queued requests
RUN, but awaiters only resume if the caller joins its work before
destroying the Scheduler.
Declined: head-of-line blocking of the single I/O thread behind a stuck
request — that is the design of D8 (documented in async_io.h; a pool of
I/O threads can replace it later behind the same awaitable).
