# Phase 11 / Day 137 — Move the Renderer onto the Shared System

**Phase:** [Phase 11 — Settings System](../phase-11-settings-system.md)
**Depends on:** Days 131-136; Phase 8 (`renderer::RenderSettings`, `SettingsRegistry`, `Renderer::ApplySettings`).

The first consumer, with no change in behavior: every Phase 8 settings test passes against the new registry. Files touched: `engine/renderer/render_settings.*`, `renderer.*`, `device_resources`, the tests in `tests/renderer/`.

## Tasks

- [x] The 14 built-in rendering settings are declared in the shared `settings::Registry` under the `renderer.` section (`renderer.present_mode`, ...), with their types, defaults, ranges and policies; `CostClass` becomes the renderer's **apply class table** (`none`, `dynamic`, `swapchain`, `pipeline-rebuild`, `device-reset`) registered with the settings; `capability` and `mechanism_only` are kept as attributes of the description. Decide in the day (spec rule from Day 130) whether `renderer::SettingsRegistry` remains as a thin facade for the existing API or the call sites move; either way **no test of Phase 8 is weakened** (a test may change its spelling of a key, never its expectation).
- [x] `renderer::RenderSettings` stays the value type the renderer works with (a plain struct of resolved values with `Set*`/`Get*` by id), now built from and written to a `settings::Settings` snapshot (`RenderSettings::FromSnapshot`, `ToChanges`); `DiffSettings`/`ResolveSettings`/`Capabilities` keep their meaning.
- [x] The text format: `SerializeSettings`/`ParseSettings` (Phase 8) become thin wrappers over `config_text` with the section `[renderer]`; the version-1 text of Day 104 loads through a migration (keys without the section prefix map to `renderer.*`) and is a fixture (Day 136's check); a Phase 8 `ParseSettings` test file keeps passing unchanged apart from the section header.
- [x] `Renderer::ApplySettings` is wired as the apply hook for the `renderer.*` changes: `Settings::Apply` hands the renderer the change list, the renderer applies the cheapest sufficient action at the frame boundary on the owner thread as before, and a failure rolls the setting back (Day 135's rollback) with the renderer's existing status; `Renderer::SetSettingsSource(Settings*)` is optional (a renderer still works with a plain `RenderSettings`).
- [x] Tests (phase 11 and the existing phases): all `tests/renderer` settings, apply, device-loss and reset tests pass; new tests: change a rendering setting through `Settings::Set` and observe the renderer apply it with the right cost class; a rollback through the new path; a settings file with `[renderer]` keys loads, applies at start-up, saves a changed value in place; the version-1 fixture loads.
- [x] **Documentation:** `docs/guide/render-settings.md` rewritten around the shared system (keys, apply classes, the file section, the migration note); `renderer.md` links updated; reference regenerated; `docgen lint` zero; `ctest -L docs`.
- [x] Run `scripts/test-phase.sh --affected` (this day touches the renderer, so it runs phases 4, 5 and 8 too) and the asan and tsan flavors; quote the lines. The renderer demo runs 1000 frames with `--validation` on Wayland and X11.
- [x] **End-of-day review (CLAUDE.md):** `/code-review high`. Extra scrutiny: behavior-preservation (diff the settings listing before and after), the owner-thread rule, rollback.
- [x] Update `STATUS.md`; commit.

**Done:** the rendering settings live in the shared registry and are loaded, layered and saved by the shared system, every Phase 8 test still passes with its expectation unchanged, and the renderer applies changes arriving through `Settings`.


## Result

- Decision (the spec rule from Day 130): `renderer::SettingsRegistry`, `RenderSettings`, `DiffSettings`, `ParseSettings` and `SerializeSettings` stay exactly as they were, so **no Phase 8 test is touched** (all 233 renderer test cases pass unchanged). `engine/renderer/shared_settings.h/.cpp` is the bridge: `RegisterSharedSettings` declares the 14 settings as `renderer.<name>` (types, defaults, ranges, policies, capabilities, text limit 63, apply class = `CostClass`) and schema version 2, `AddRendererMigrations` renames the schema-1 flat keys, `RenderSettingsFromSnapshot`/`RenderSettingsToChanges` convert, `ApplySharedChange` is the apply hook for `Renderer::ApplySettings`, `RendererCapability` feeds the capability check, `SyncSharedFromRenderer` realigns after a queued change failed.
- Not done as the plan said: `SerializeSettings`/`ParseSettings` are not rewritten as wrappers over `config_text` (their fixed-capacity, allocation-free contract and line-numbered reports are what the Phase 8 tests pin down); instead the Phase 8 file loads through the migration, and a test checks that the old parser and the new path read the schema-1 fixture to equal settings. `Renderer::SetSettingsSource` was not added (the apply function and `SyncSharedFromRenderer` cover it without the renderer depending on `Settings`).
- New: `SettingDesc::max_text`; `tests/renderer/shared_settings_test.cpp` (phase 11; declarations versus the old registry's defaults, a `[renderer]` file applied at start-up and saved in place, a Dynamic and a Swapchain change through `Settings`, a device-reset failure rolled back through the settings system, capability refusal, the schema-1 fixture `renderer_v1.cfg`, a second change before the first applies, resync, over-long text); `settings_fixtures` now names the test source per fixture in `SCHEMAS.txt`.
- Runs: plain `ran 1276 of 3348 tests (phases: all; flavors: plain; display: included; crash tests: excluded)` (only the known X11 test fails); asan `ran 941 of 3348`; tsan `ran 658 of 3348`; `renderer_demo` 1000 frames `--validation` on Wayland and X11 exit 0 (the demo itself does not use the shared system until Day 138); docs lint 4001/4001.

## Post-implementation code review

`/code-review high`: 10 findings. Fixed (tests added): a second change made before the first was applied dropped the first (the request is now built from the values the settings system holds); a queued change that failed later left the two systems apart (`SyncSharedFromRenderer`); long text was cut silently (the shared declaration now carries `max_text` and refuses it); the key table was built without synchronisation (a thread-safe static); a heap allocation per changed key and a magic length 9 (a lookup over the static keys); the duplicated text copy; the `sset` alias in a public header (spelled out); the fixture check weakened by accepting any test (each fixture names its own test source, only whole-line comments are stripped); test clean-ups (dead members, `<cstdlib>`, a double negation, the full saved text). Declined: none.
