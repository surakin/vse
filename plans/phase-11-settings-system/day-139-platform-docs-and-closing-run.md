# Phase 11 / Day 139 — Platform Checklists, Guide, Closing Full Run & Wrap-up

**Phase:** [Phase 11 — Settings System](../phase-11-settings-system.md)
**Depends on:** Days 130-138.

Make the store interface something Windows, macOS and the mobile and console targets can implement without redesign, finish the documentation, run everything, close the phase.

## Tasks

- [ ] **Backend checklist** `engine/foundation/settings/BACKEND.md`: what each platform store implements — **Windows registry** (`HKCU\Software\<app>`: sections as subkeys, typed values `REG_DWORD`/`REG_QWORD`/`REG_SZ`, lists as `REG_MULTI_SZ`, no comments or order, per-key writes, `RegNotifyChangeKeyValue` for the change capability, 32/64-bit view, group policy keys as a read-only `System` layer), **macOS** (`NSUserDefaults` suites or a plist file through the file store, `NSUserDefaultsDidChangeNotification`), **Android** (`SharedPreferences`, `apply()` versus `commit()`), **iOS** (`NSUserDefaults`), **consoles** (save-data APIs behind the same store, size limits and commit latency); one `###` section per virtual function of `ConfigStore` and per `Backend:`-labeled function; a ctest `settings_backend_lists` keeps it in step with the headers (as `io_backend_lists` does) and `settings_cross_syntax_windows|macos` compile the neutral headers for those targets with clang's `-fsyntax-only`.
- [ ] A **registry-shaped store sketch** in `tests/settings/` (`NoOrderConfigStore` from Day 132 extended to typed per-key writes, no comments, notifications from another thread) passes the full conformance suite, so the Windows port starts from a passing model; record in the checklist which conformance cases a registry store needs capability flags for.
- [ ] Add the Phase 12 and 13 items to their plan files (the registry store and the `NSUserDefaults` store, run the conformance suite, the standard locations), a note to Phase 15 (the UI's settings screens bind to the registry metadata: labels, groups, ranges, `restart_required`; `Settings` listeners drive live updates) and to Phase 20 (scripting reads and sets settings by key).
- [ ] **Guide pass:** read `docs/guide/settings.md` end to end as a new developer (Keys and values, Declaring a setting, Reading, Where values live, The file format, Layers, Environment and command line, Loading/changing/saving, Reacting to a change, Changing a setting between versions, Writing a store backend, Settings in an application); a "Which API do I use?" table at the top; every tagged sample compiles and runs; `docs/guide/README.md` current; `docgen lint` zero; reference regenerated and committed.
- [ ] Update `CLAUDE.md`: a hard architectural constraint "Anything a user can configure is a setting registered with `settings::Registry` and read through `Setting<T>` or `Settings`; no new ad hoc `getenv` or flag parsing for configuration, no config file formats of its own" with its exceptions (pre-`main` bootstrap variables listed in the spec, third-party code, tools' own CLI) and a pointer to the check below; `PLAN.md` assumption added; `STATUS.md` commands.
- [ ] **A configuration check** (`tools/config_access_check`, ctest, like the Phase 9 gate): fails on a new `getenv` or `--flag` parse in `engine/` and `game/` outside an allow list with a reason per entry (the bootstrap variables, the demos' launch-only options, the settings system itself); stale entries fail; planted-violation self-tests.
- [ ] Known-issues sweep: every deferral filed (remote and live-reloaded config, a UI binding layer, secrets and per-machine state, the Windows registry and other platform stores, autosave policies beyond the first, list-valued settings if cut, migration tooling), entries this phase fixed removed.
