# Phase 22 / Day 315 — The Resource Backend Interface, the Filesystem and Memory Backends & Mounts

**Phase:** [Phase 22 — Asset Pipeline & Resource System](../phase-22-asset-pipeline.md)
**Depends on:** Day 314; Phase 9 (`io::File`, `io::Path`, `io::Directory`).

The seam every backend implements, and the first backend: loose files for development.

## Tasks

- [x] **`asset::ResourceBackend`** interface: `Stat(id, &info)` (size, content hash if known, modification stamp), `Open(id, &reader)` returning a `ResourceReader` (`Size`, `ReadAt(offset, bytes)` synchronous, `ReadAtAsync` for backends that can), `ReadTable(&ResourceTable)` (**the backend's id <-> path table, added 2026-11-13 at the user's request: a stored table when the backend has one (a special file, a pak section, a server's reply) or one built on demand (a folder scan, a server query, the host's registrations); `Capabilities` has a `stored_table` bit; the result is complete or an error, never silently partial; paged for backends that cannot return it at once**) **`ReadTableAsync(token) -> TableTicket` (added 2026-11-13, the user: the backend needs an asynchronous way to read the table; a folder scan or a server query must not block the caller)**: `IsDone`, `Wait`, `Cancel` by token (a cancelled read leaves no partial table), `Finish(&ResourceTable)` for the whole table, and `TakePage(&ResourceTable)` for the pages that have arrived so far, so a large table can be consumed as it comes (every page is complete entries; the last one is marked); a `Capabilities` bit `async_table` says the backend reads natively without a thread (the network backend); one without it runs `ReadTable` on a job, so every backend has the call and `ReadTable` stays the blocking form (it is `ReadTableAsync` plus `Wait` for the backends that read natively), and `List(prefix, &ids)` as a bounded view over it, `Watch(&changes)` (polling, returns ids changed since the last call), `Name()`; `Capabilities` bits (ranged, async, watch, writable=false).
- [x] **`FilesystemBackend`** over `io::`: a root directory; virtual path to file path mapping that refuses escapes (`..`, absolute paths, symlink loops by a depth limit); the id-to-path index built by walking the directory once and refreshed by `Watch` (modification stamps); reads through `io::File` ranges.
- [x] **`LoadBufferPool`** (Day 313 Spike 5: a read into a fresh buffer is 4x slower than into a pre-faulted one, 75 ms against 17.5 ms per 256 MiB): a pool of 64-byte-aligned buffers (page-aligned above 1 MiB) whose pages are touched when the buffer is created, handed out with a size class, returned on release, bounded by `assets.buffer_pool_bytes`; `ResourceReader::ReadAt` reads into a pool buffer; a test shows a second load of the same size reuses a buffer and allocates nothing.
- [x] **`FilesystemBackend` and ids:** the table is a minted `resources.table` (`NAMES` blob) at the root when present, otherwise built on demand by one walk of the directory that reads each loose blob's header (the path is the file's location, the id the blob's own), never an id from a file name; a stored table is a cache that is never trusted over the files: `Open` checks the blob's own id against the table's, and a mismatch is an error naming both (so a stale table cannot silently point an id at the wrong file); two files claiming one id are refused naming both; a copied blob (a duplicated id) is refused.
- [x] **`MountTable`:** ordered mounts (`/` prefix to backend, priority); lookup returns the highest-priority backend that has the id; **it owns the merged `ResourceTable`** (built lazily from each backend's `ReadTable`, rebuilt for the changed mount when `Watch` reports a change; `Resolve(path)` and `PathsOf(id)` answer from it; a path two mounts map to different ids is won by the higher priority and the loser is listed as shadowed, never silently dropped); a loose-file mount over a pak mount overrides it; unmount; a snapshot for tests; **`RefreshTablesAsync()` starts every mount's `ReadTableAsync` without blocking and merges each table as it arrives (in priority order, so the result does not depend on arrival order); until a mount's table is in, `Resolve(path)` answers `NotReady` (never `NotFound`, which would be a lie), and loads by id are unaffected because they never use the table; `TablesReady()` and a completion callback tell the owner.**
- [x] **`HostMemoryBackend` (a real backend, not only a test double; added 2026-11-13, the user's request):** resources whose bytes the *host application* provides at run time, so a host that embeds the engine (Phase 23's C API, `engine_resources_*`) supplies content directly, with no file, pak or server. `Add(id, bytes, options)` registers a resource (with optional paths, which the backend's table reports; without one the resource is reachable by id only) (**copied** into backend-owned memory, or **borrowed**: the host keeps the bytes alive and gives a release callback with a user pointer that the backend calls exactly once when the resource is replaced, removed or the backend is destroyed, never while a `ResourceReader` of it is open); `Replace(id, bytes)` and `Remove(id)` at any time, from any thread (readers already open keep reading the old bytes until they close: a reference-counted entry, so a replace never tears a load); `Stat` reports the size and the content hash (computed on `Add`, or supplied by the host and **verified** on `Add` when the host passes one: a mismatch is refused); a `Watch` change record for every add, replace and remove (the resource manager's reload path, Day 328, uses it); a byte budget (`assets.memory_backend_bytes`; `Add` past it returns `LimitExceeded`: back-pressure, not eviction, because the host owns the content); ids follow the Day 314 rules (the host passes the stable `ResourceId`, never a path; a duplicate `Add` of a live id is refused unless it is `Replace`). The dependency rule of this phase holds here too: the backend only stores blobs, but `Remove` and `Replace` of an id that the manager reports as depended upon by a loaded resource return `InUse` with the dependents named (a `ResourceInUse` query the manager supplies, Day 328), so a host cannot break a dependency by accident; the host retries after unloading or forces it with an explicit `Remove(force)` that unloads the dependents first, atomically. Mounted through `MountTable` like any backend (typically at a high priority so host content overrides a pak).
- [x] **A fault-injecting wrapper (`FaultyBackend`)** around any `ResourceBackend` (injectable failures, short reads and latency) for the tests of every later day, like the file layer's network-like double; the memory backend stays a production class.
- [x] **Backend conformance suite** (`tests/asset/backend_conformance.h`): written once against `ResourceBackend`; run against the filesystem backend, the memory backend and the fault-injecting wrapper over it (the pak and network backends join on Days 316 and 332).

- [x] **Tests:** the memory backend: copied and borrowed bytes (the release callback runs once, only after the last open reader closes), a replace while a reader is open, a hash mismatch refused, the byte budget, concurrent add/replace/remove/read under tsan, a watch record per change, removing an id a loaded resource depends on refused with the dependents named; path escape attempts, a file that disappears between `Stat` and `Open`, a directory with 10,000 entries, a change seen by `Watch`, mount priority and override, a read past the end.

## Post-implementation code review

`/code-review high`: 10 findings. Fixed (7): a removed `HashMap` slot kept the entry alive and delayed the borrowed release (test); the host's release
ran under the change lock (reentrant-release tests); a forced replace unloaded dependents before it could fail (test); `PollChanges` ran `Watch`
under the mount lock; every filesystem `Open` did extra `realpath`, header and `stat` calls (now one open, link containment checked once at scan time);
the chunked `FaultyReader` skipped the bounds check (found by the conformance suite); a stale table failure was shown during a refresh, and the mount
order was sorted per call (now kept ordered; equal-priority test). Declined, filed in `KNOWN-ISSUES.md` (3): the filesystem backend holds its lock
during a rescan; walk depth cap and untested symlink branch; out-of-memory in the middle of a path commit.
