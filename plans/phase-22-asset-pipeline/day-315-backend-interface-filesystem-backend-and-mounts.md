# Phase 22 / Day 315 — The Resource Backend Interface, the Filesystem and Memory Backends & Mounts

**Phase:** [Phase 22 — Asset Pipeline & Resource System](../phase-22-asset-pipeline.md)
**Depends on:** Day 314; Phase 9 (`io::File`, `io::Path`, `io::Directory`).

The seam every backend implements, and the first backend: loose files for development.

## Tasks

- [ ] **`asset::ResourceBackend`** interface: `Stat(id, &info)` (size, content hash if known, modification stamp), `Open(id, &reader)` returning a `ResourceReader` (`Size`, `ReadAt(offset, bytes)` synchronous, `ReadAtAsync` for backends that can), `List(prefix, &ids)` (bounded), `Watch(&changes)` (polling, returns ids changed since the last call), `Name()`; `Capabilities` bits (ranged, async, watch, writable=false).
- [ ] **`FilesystemBackend`** over `io::`: a root directory; virtual path to file path mapping that refuses escapes (`..`, absolute paths, symlink loops by a depth limit); the id-to-path index built by walking the directory once and refreshed by `Watch` (modification stamps); reads through `io::File` ranges.
- [ ] **`LoadBufferPool`** (Day 313 Spike 5: a read into a fresh buffer is 4x slower than into a pre-faulted one, 75 ms against 17.5 ms per 256 MiB): a pool of 64-byte-aligned buffers (page-aligned above 1 MiB) whose pages are touched when the buffer is created, handed out with a size class, returned on release, bounded by `assets.buffer_pool_bytes`; `ResourceReader::ReadAt` reads into a pool buffer; a test shows a second load of the same size reuses a buffer and allocates nothing.
- [ ] **`FilesystemBackend` and ids:** the id index is built from the `.id` sidecars and the minted `NAMES` blob, never from file names; two files claiming one id are refused naming both; a copied file with its sidecar (a duplicated id) is refused; a source with no sidecar is minted only by the tool that writes one.
- [ ] **`MountTable`:** ordered mounts (`/` prefix to backend, priority); lookup returns the highest-priority backend that has the id; a loose-file mount over a pak mount overrides it; unmount; a snapshot for tests.
- [ ] **`MemoryBackend` (a real backend, not only a test double; added 2026-11-13, the user's request):** resources whose bytes the *host application* provides at run time, so a host that embeds the engine (Phase 23's C API, `engine_resources_*`) supplies content directly, with no file, pak or server. `Add(id, bytes, options)` registers a resource (**copied** into backend-owned memory, or **borrowed**: the host keeps the bytes alive and gives a release callback with a user pointer that the backend calls exactly once when the resource is replaced, removed or the backend is destroyed, never while a `ResourceReader` of it is open); `Replace(id, bytes)` and `Remove(id)` at any time, from any thread (readers already open keep reading the old bytes until they close: a reference-counted entry, so a replace never tears a load); `Stat` reports the size and the content hash (computed on `Add`, or supplied by the host and **verified** on `Add` when the host passes one: a mismatch is refused); a `Watch` change record for every add, replace and remove (the resource manager's reload path, Day 323, uses it); a byte budget (`assets.memory_backend_bytes`; `Add` past it returns `LimitExceeded`: back-pressure, not eviction, because the host owns the content); ids follow the Day 314 rules (the host passes the stable `ResourceId`, never a path; a duplicate `Add` of a live id is refused unless it is `Replace`). The dependency rule of this phase holds here too: the backend only stores blobs, but `Remove` and `Replace` of an id that the manager reports as depended upon by a loaded resource return `InUse` with the dependents named (a `ResourceInUse` query the manager supplies, Day 323), so a host cannot break a dependency by accident; the host retries after unloading or forces it with an explicit `Remove(force)` that unloads the dependents first, atomically. Mounted through `MountTable` like any backend (typically at a high priority so host content overrides a pak).
- [ ] **A fault-injecting wrapper (`FaultyBackend`)** around any `ResourceBackend` (injectable failures, short reads and latency) for the tests of every later day, like the file layer's network-like double; the memory backend stays a production class.
- [ ] **Backend conformance suite** (`tests/asset/backend_conformance.h`): written once against `ResourceBackend`; run against the filesystem backend, the memory backend and the fault-injecting wrapper over it (the pak and network backends join on Days 316 and 326).
- [ ] **Tests:** the memory backend: copied and borrowed bytes (the release callback runs once, only after the last open reader closes), a replace while a reader is open, a hash mismatch refused, the byte budget, concurrent add/replace/remove/read under tsan, a watch record per change, removing an id a loaded resource depends on refused with the dependents named; path escape attempts, a file that disappears between `Stat` and `Open`, a directory with 10,000 entries, a change seen by `Watch`, mount priority and override, a read past the end.
- [ ] **Runs (CLAUDE.md "Tests run by phase"):** `scripts/test-phase.sh --affected` plain; then the asan and tsan flavors when the day touched concurrency, lifetime or memory code; quote each run's final `ran X of Y tests (phases ...)` line in this file and never say "all tests pass" for a reduced run. `ctest -L docs` when a public header or a guide changed. Build clean (warnings are errors) with Clang and GCC, unity on and off. New code uses the engine's wrappers and types, never `std` (`std_usage_check`); file access only through `io::` (`file_access_check`); settings only through `settings::Registry` (`config_access_check`).
