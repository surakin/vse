# Phase 22 / Day 335 — glTF Import I: The Importer Library, the JSON Library, the Container & Accessors

**Phase:** [Phase 22 — Asset Pipeline & Resource System](../phase-22-asset-pipeline.md)
**Depends on:** Days 315 (`HostMemoryBackend`), 319 (mesh), 333 (the `asset_mint` project); PLAN.md assumptions #4, #17 and #19 as amended 2026-11-14.

Added 2026-11-14 (the user): glTF 2.0 assets (`.gltf` and `.glb`) import into the engine's own formats, **in memory, from a library an application may link** (amended the same day: the first plan made the importer an offline tool that no program could link). The use that decides the design is the host (the user's Matrix client, whose 3D rooms fetch `.glb` files at run time): bytes in, minted blobs out, added to a `HostMemoryBackend` that the rest of the engine reads like any other backend. The offline `asset_mint import-gltf` of Day 338 is a thin command over the same library. This day builds the library's foundation (module, JSON library, container, accessors, limits); Day 336 imports meshes; Day 337 skeletons and animation; Day 338 images, textures, materials, the in-memory entry and the command.

## Decisions (planner's defaults; the user confirms or overrides)

- **A new module, `engine/asset_import`** (library `asset_import`, header `asset_import/gltf_import.h`), above `asset` and `renderer` (the material templates) in `ARCHITECTURE.md`, with **nothing in the engine depending on it**: the runtime libraries (`asset`, `renderer`, `scene`, ...) never include it, a program links it only if it imports at run time. `module_deps_check` and the Day 339 gate enforce the direction.
- **The importer works on bytes and returns bytes.** `ImportGltf(ByteSpan file, const GltfSource& source, const ImportOptions&, ImportResult*)`: `source` is an interface that reads what the glTF names by URI (`GltfSource::Read(uri, Vector<byte>*)`; the tool's implementation reads files through `io::` inside the glTF's directory, a host's reads from wherever it fetched the file, a `.glb` needs none). The result holds each imported resource (id, type, blob bytes, a suggested resource path), the import manifest **as data** (kind, glTF index and name, id; the tool writes it next to the file, a host keeps it or not) and the report (counts, every dropped feature and warning with its glTF object). `ImportIntoBackend(HostMemoryBackend&, const ImportResult&)` adds every blob under its suggested path; the dependencies are in the blobs, so the closure loads atomically (Day 328).
- **ids:** from the manifest passed in (a re-import keeps them), else drawn from an `IdSource` (the random source by default; tests pass a seeded one so imports are byte-identical).
- **No exceptions, no abort on a hostile file** (the input may come from the network): every failure is a `Status` naming the glTF object; limits (`ImportLimits`: file bytes, JSON depth, node, mesh, accessor, buffer view and image counts, decoded pixels, total output bytes) are settings (`assets.import.*`, Day 339) with the defaults of the struct, checked before anything is allocated.
- **JSON: a vetted vendored library, chosen by a spike at the start of this day; no hand-written parser** (the user, 2026-11-14: "I still don't want to reinvent json parsing"; the first amendment of the day had proposed our own reader and is withdrawn). The input may be hostile and untrusted (the host fetches files from rooms) and exceptions are disabled, so the choice is made on those terms, not on convenience: **yyjson** (C99, MIT, one `.c` and one `.h`, an iterative reader, strict RFC 8259 by default, errors by return value with a position, a pluggable allocator so memory can be capped) is the default candidate; the others in the spike are **RapidJSON** (header-only C++, no exceptions, SAX and DOM, recursion-bounded parse), **simdjson** (fast, but a large C++ surface and SIMD paths that must be deterministic and portable to every target) and **jsmn** (a tokenizer only: too little). **nlohmann/json is out** for this module (it throws or aborts on a wrong type, and it needs `std` types; it stays in `tools/shader_mint`). The spike's criteria, written in the spec: license; size; security history; no exception, no abort and no unbounded allocation on hostile input (a fuzz run of 5,000 mutated documents under asan with a capped allocator); depth handled without recursion or with a limit; strict number and UTF-8 handling; one place to cap the allocation; builds clean with `-Wall -Wextra -Werror` on Clang, GCC and MSVC (or is compiled as C with the project's flags and its own warnings listed); the same results on every machine. The winner is vendored pinned by version and SHA-256 under `third_party/` with `VENDORED.md` (PLAN.md #19 gets its entry that day), included only by `engine/asset_import/json_view.*` (a gate, as for the other third-party boundaries), and the loser is recorded in the spec.
- **Work runs on the job system** (assumption #15): `ImportGltfAsync` (Day 338) returns a ticket like `TableTicket` (progress, cancel); the block compression of textures already fans out over the workers.
- **The `.gltf`/`.glb` file is the source of truth for the offline tool** (a mesh of a million vertices would be a half-gigabyte text file): `asset_mint mint` regenerates every blob from it deterministically through this library, and the project's source kind `.gltf` keeps an import manifest `NAME.gltf.import` next to the file (the one place the "source carries its id" rule of 2026-11-13 does not hold: a third-party format has no id field). An in-memory host has no sidecar: it passes the manifest it kept.

## Outcome

The spike chose **yyjson 0.13.0** (the record, with the other candidates and the numbers, is in the spec: "The JSON library"); `third_party/yyjson/` holds `yyjson.c`, `yyjson.h` and `LICENSE` unmodified with `VENDORED.md` and a `CMakeLists.txt` that builds one static C library per flavor (`yyjson`, `yyjson_asan`, `yyjson_tsan`) with the writer, the incremental reader, file access, the utilities and the non-standard syntax compiled out and the reader's depth limit set to 128; PLAN.md #19, CLAUDE.md and BUILD.md say so. The module `engine/asset_import` (library `asset_import`, plain, asan and tsan; layer 13 with the one same-layer edge `asset_import -> asset`, nothing depends on it): `json_view.{h,cpp}` (the only file that includes yyjson: `JsonDocument::Parse` over a pool allocator sized from the input's length before parsing, a repeated key refused, `JsonValue` with typed accessors whose refusals name the path), `gltf_container.{h,cpp}` (`ParseGltf`: `.glb` and `.gltf`, `data:` and external buffers through `GltfSource`, `CleanRelativeUri`, `DecodeBase64`, the buffer views and accessors checked against their buffers with checked arithmetic, `extensionsRequired`, the limits), `gltf_accessor.{h,cpp}` (`ReadAccessorFloats` and `ReadAccessorUnsigned`: every component type, normalized, strides, padded matrix columns, accessors with no view, sparse overrides), `gltf_import.{h,cpp}` (the whole API of Days 335 to 338 declared and documented: `ImportLimits`, `GltfSource`, `IdSource` with a random and a seeded implementation, `ImportManifest` with `Match` and a text form, `ImportOptions`, `ImportResult`, `ImportGltf` (reads and reports the container; `Unsupported` until Day 336), `ImportIntoBackend` (atomic)), and the new `ErrorCode::Unsupported`. The gate `json_boundary_check` (yyjson only in `json_view.cpp`, cloned from the SQLite gate with planted-violation self-tests). Tests: `tests/asset/gltf_writer.h` (a glTF/GLB writer for tests), `gltf_json_test.cpp` (valid and malformed text, repeated keys, nesting at 127, 128, 129 and 100,000 levels, 5,000 mutated documents) and `gltf_container_test.cpp` (the container, hostile URIs, damaged `.glb` files, the limits, ranges, every accessor type, matrices, sparse accessors, base64, the manifest, the id sources, `ImportIntoBackend`, bounded reads). Docs: the guide section "Importing glTF", the module in `docs/reference/modules.txt`, `ARCHITECTURE.md`.

Deviations (also in `KNOWN-ISSUES.md`): `ImportGltf` imports nothing yet (the day was the foundation: Day 336 imports meshes); the settings `assets.import.*` are Day 339 (the limits are the defaults of `ImportLimits`); the JSON depth limit (128) is a compile-time definition of the vendored library, not a field of `ImportLimits`; a `.glb` BIN chunk is copied into the document's buffer, not referenced.

Runs: see `STATUS.md`.

## Post-implementation code review

`/code-review high` over the day's tree: 9 findings, all fixed. The macOS branch of the root `CMakeLists.txt` did not add `engine/asset_import` while `tests/asset` linked it (added); `ImportManifest::Claim` depended on the order of the calls, so a new object could take the entry another object matched by name (replaced by `Match`, which matches all the objects of a kind at once, by name then by index, and does not let an entry that belongs to another object by name be taken; tested with a reorder and with a new unnamed mesh); a source or a `data:` URI could return or decode far more than the buffer's `byteLength` before the check (`GltfSource::Read` takes `max_bytes` and a `data:` URI is refused by its length, tested with a thousand-byte file and a base64 bomb); the `.glb` buffer copy used the aborting `Resize` (`TryResizeUninitialized`, reported as `LimitExceeded`); the manifest's repeated-id check was quadratic and `Match` is a sort and binary search; the JSON pool was zero-filled for its worst-case size (`TryResizeUninitialized`) and every object of two or more members allocated a vector to check repeated keys (objects up to 16 members are compared pairwise); a zero `byteLength` was reported as `TooLarge` (now `Invalid`, tested); a `(void)` cast on an unused parameter and a swallowed rollback failure in `ImportIntoBackend` (the parameter is unnamed, a failed rollback is reported); and the comment of the gate said "database". The bookkeeping finding (STATUS.md, KNOWN-ISSUES.md, this section) is this commit.
