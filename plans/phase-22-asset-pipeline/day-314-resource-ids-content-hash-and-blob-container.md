# Phase 22 / Day 314 — Resource Ids, the Content Hash & the Versioned Blob Container

**Phase:** [Phase 22 — Asset Pipeline & Resource System](../phase-22-asset-pipeline.md)
**Depends on:** Day 313; Phase 16 (wrappers); Phase 19 Day 256 (`ByteWriter`/`ByteReader`).

The value types and the container every later day writes into and reads from; pure CPU, tested on any machine.

## Tasks

- [x] **`asset::ResourceType`** (a 32-bit tag as four characters, e.g. `MESH`, `TEXR`, `MATL`, `LEVL`) and a registry of known types with their current version.
- [x] **`asset::ResourceId`: a stable 64-bit id (the user's answer of 2026-11-13: identity is permanent, the path is an alias)**; not derived from the path. `ResourceId::None()` is the explicit null reference. **One file per asset, the id inside it (the user, 2026-11-13: no sidecar files, people forget to handle two files together).** Every source format is ours (assumption #4), so each carries its id in its own header: an `id <hex>` line at the top of the text forms (`.mesh.src`, `.material.src`, `.level.src`, a texture's parameters file) and an id field in the raw image container's header. The id is assigned exactly once, by `asset_mint adopt <file>` (the only command that creates an id: 64 bits from the OS entropy source, written into the source), and committed with the file; a rename, a move and a plain `mv` therefore carry the id with the file. **`mint` is a pure function of the sources**: a source with no id is a mint error naming `adopt`. A copy (`cp`) duplicates the id; the mint refuses two sources with one id, naming both, and `asset_mint copy` or `reid` gives the new file its own. **Every minted blob's header carries its own `ResourceId`**, so the runtime never needs a source or a sidecar: a backend learns the id of a loose blob by reading its header. **`asset::ResourceTable` (the user, 2026-11-13: the engine needs one table where the id <-> path map lives)** is the in-memory bidirectional map of normalized virtual paths and ids (one path, one id; one id, any number of paths; per entry the id, the type and the paths): `Resolve(path)`, `PathsOf(id)`, `Add`/`Remove`, iteration by prefix, `Merge(other, priority)` reporting shadowed entries, a bounded size, and a canonical serialization as a standard `NAMES` blob (sorted by id, so deterministic). A table is not a file format owned by one backend: **each backend supplies its own** (a stored table, or one built on demand, Day 315), and the mount table merges them. The hot load path stays id-only; the table serves path lookups at the edges (`Load(path)`, level and material sources, tools, logs, host APIs). Path normalization (`/` separators, no `.` or `..` segments, no trailing slash, case-sensitive, UTF-8 NFC through the foundation string module, a length limit); formatting for logs, a collision check used by the packer.
- [x] **`asset::ContentHash`** (the hash chosen on Day 313) over bytes and over a stream of chunks; its published test vectors.
- [x] **The dependency section (standard, every type):** a sorted array of `(ResourceId, ResourceType, expected type version, role)` records, strictly sorted by id with no duplicates, no `None`, no self-reference, count bounded; `BlobReader::Dependencies()` returns it as a span; a blob whose type reads a `ResourceId` anywhere else must list it here (the minters build both from one reference collector, so the two cannot differ; a test per type decodes every id in the blob and checks it is in the list). There are no optional dependencies.
- [x] **The blob header and sections:** magic, type, version, the blob's own `ResourceId`, the target tag (the platform family its layout was made for, Day 333), flags, section count, payload size, content hash, a section table (id, offset, size); every section starts at an offset aligned to 64 bytes (and to the page size for sections above 1 MiB, if Day 313's spike says it helps) so a loader can hand a span of the file buffer straight to the GPU upload; the section table is a fixed-size array read in one pass; `BlobWriter` (sections appended with alignment, hash filled at the end) and `BlobReader` (validates the header, every offset and size against the buffer before any use, rejects overlapping and out-of-range sections; the hash is verified only on request, never implicitly, so the load path pays for bounds checks and nothing else).
- [x] **Versions are enforced, upgrades are offline:** `BlobReader` accepts the current version of its type only and returns `UnsupportedVersion` for any other, with a message naming `asset_mint remint`; the registry of current versions is the one source of truth the minters, the packer, `verify` and the manager share; the upgrade chain itself (an `UpgradeRegistry` with one function per (type, from version), applied in order, failing on a gap) lives entirely in `tools/asset_mint`, written from Day 318 on with each type's first format, so no upgrade code is linked into a game; this day only fixes its contract in the spec and tests the refusal.
- [x] **Errors are values** (`asset::Status`, `asset::ErrorCode`: `MissingDependency`, `DependencyTypeMismatch`, `DependencyCycle`, `DuplicateId`, `NotFound`, `Corrupt`, `UnsupportedVersion`, `TypeMismatch`, `TooLarge`, `Io`, `Cancelled`, `Offline`, `LimitExceeded`, `WrongTarget`).
- [x] **Tests** (`tests/asset/blob_test.cpp`, `id_test.cpp`): hash vectors; id and path-normalization tables (valid and invalid); write-read round trips of blobs with 0 to 16 sections; every truncation and every single-byte corruption of a golden blob is rejected or caught by the hash, never crashes; a golden old-version blob is refused with `UnsupportedVersion` (the upgrade itself is tested on Day 333); a fuzz of random bytes against `BlobReader` (a million cases, seeded).

Deviations from the task text, each on purpose:

- **`BlobReader::Dependencies()` returns no span.** `DependencyCount()` and `DependencyAt(i)` decode a record from the bytes (20 bytes each, no padding), so no struct is laid over the buffer and no alignment or aliasing assumption is made; the cost is a few loads per record, on a section that is small (bounded at 4096 records).
- **The golden old-version blob is simulated**: the old blob is written with a registry at version 1 and opened with one at version 2 (and a container version patched by one). A committed golden file arrives with `asset_mint remint` (Day 333), which needs a real old blob to upgrade.
- **The header carries the blob's own `ResourceId` and a target tag** (the 2026-11-13 plan amendments); the `NAMES` type is the only one whose id may be null.
- **`kMaxBlobBytes` is 4 GiB** (the review's finding on the 1 TiB bound); a settings-controlled bound can replace it when the settings land (Day 337).
- `asset_mint adopt` (the only creator of ids) is Day 333; this day provides `GenerateResourceId` and the parse and format it uses.
