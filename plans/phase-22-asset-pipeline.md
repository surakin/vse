**Goal:** a resource system with pluggable storage backends, versioned per-type binary formats, offline tooling that produces them deterministically, and a runtime manager that loads them synchronously and asynchronously: the foundation Phase 30 (Unreal import) targets when converting external content into engine-native form. See root `PLAN.md` assumption #12 for the settled design decisions this phase implements.
**Definition of done:** (the principles above hold: loads do no conversions, old versions are refused and upgraded offline) an offline mint converts source assets (our own custom formats) into engine-ready blobs, packed into a pak, loadable at runtime through the filesystem, pak and network backends with identical results, with no editor or tool code linked into the game binary; minting is deterministic (same inputs and tool version give byte-identical outputs, tested for every minter, across worker counts and across the three machines); a device reset recreates every loaded resource; hostile blobs, paks and requests are refused; the benchmark table is in the spec.

## Principles (the user, 2026-11-13) — they override anything below that reads otherwise

- **Loading performance is paramount.** A minted blob is laid out for the machine that loads it: sections aligned for direct GPU upload, vertex and index data in the exact layout the RHI consumes, textures in their final GPU format with every mip level already generated, strings and references already resolved to ids, no text and no compression on the load path. The loader's job is to read the bytes into an aligned buffer and hand spans of it to the GPU upload; every cost that can be paid at mint time is paid at mint time. Load speed is measured (Day 340) and has pass conditions.
- **Load-time conversions are discouraged.** No format conversion, mip generation, color-space conversion, index re-ordering, re-validation of minted data, decompression or re-encoding when a resource loads. A conversion at load time is a defect in the minter or the format, not a feature of the loader; the manager counts any it is forced to do (`Stats::load_conversions`) and the demo and the benchmarks assert the count is zero. What runtime still checks is bounds (sizes and offsets against the buffer, cheap) so a corrupt file cannot crash it; the content hash is verified when a pak or a network cache entry is opened or fetched and by `asset_mint verify`, not again for every load (a setting turns per-load verification on for development).
- **A resource dependency can never be broken (the user, 2026-11-13: in Unreal, broken asset dependencies are a never-ending source of bugs; here they must not exist).** Not detected late: made impossible by construction, and checked at every stage so that a hole in one is caught by the next. (1) **Identity is stable:** a `ResourceId` is a permanent id assigned once by `asset_mint adopt` and written into the source file itself (one file per asset, no sidecar) and into every blob's header; the path is only a name for it, so rename and move never change an id and there are no redirectors. (2) **References are typed ids, resolved at mint time:** a source may write paths, the minter resolves them, and an unresolved or wrongly typed reference is a mint error. (3) **Every blob declares its dependencies in one standard section**, and the loader follows only declared dependencies. (4) **The mint tool refuses what would break a reference:** deleting an asset that is referenced, an id used twice, a cycle; rename, move and delete are `asset_mint` commands that know the references. (5) **`pack` refuses an incomplete closure**, and a pak names any base pak it relies on by content hash. (6) **The runtime loads a resource and its whole closure atomically:** a handle is published only when every dependency is loaded and of the declared type; a failure names the chain and leaves nothing half-loaded. (7) **No silent fallback:** a missing dependency is an error; fallback resources exist only behind a development setting, and every use is counted and fails the demos and tests. There are no optional references: a reference that may be absent is an explicit null id, not a pointer to something that may not exist.
- **Asset upgrades are enforced, offline, whenever possible.** The runtime loads the current version of every format and refuses an older one with `UnsupportedVersion` and a message naming the fix (`asset_mint remint`); the upgrade chains live in `tools/asset_mint`, not in the game. Enforcement points: the minter only writes the current version; `asset_mint pack` refuses a blob that is not current and verified; a format version bump changes the manifest so the next `mint` rebuilds everything of that type; `asset_mint verify --require-current` runs in ctest over the sample project and over a fixture of every older version (which must be reported, and upgraded by `remint` to blobs byte-identical to a fresh mint); a pak and a network server announce their format versions and the manager refuses a mount that serves old ones at mount time, not at first use.

## Decisions made for this plan (the user, 2026-11-12)

- **Source formats are custom, plus glTF import (amended 2026-11-14, the user):** text sources for meshes, skeletons, clips, textures' parameters, materials and levels, and a trivial raw image container, are the engine's own; **glTF 2.0 (`.gltf`, `.glb`) imports through the `engine/asset_import` library** (Days 335-338; in memory, so an application such as the host can import at run time into a `HostMemoryBackend`, and the offline `asset_mint import-gltf` is a thin command over it) into the same formats, with PNG and JPEG decoders vendored for that library (PLAN.md #4, #17, #19). The runtime libraries (`asset`, `renderer`, ...) never read glTF, PNG or JPEG and never depend on the importer; a program opts in by linking it.
- **Texture compression is ours:** a deterministic BC1, BC4, BC5 and BC7-subset encoder in the minter, decoders at runtime; ASTC waits for Phase 28.
- **The network backend is read-only over `net::TcpTransport`** with a content-hash disk cache, retry with back-off and an offline mode; no authentication and no encryption (the user deferred encryption on 2026-11-12: trusted networks only).

## Key deliverables (broken into days below)

- **Resource identity and the blob container** (Day 314): `ResourceId`, `ContentHash`, a versioned blob with bounded sections and an upgrade chain.
- **The resource table (the user, 2026-11-13):** one id <-> path map (`asset::ResourceTable`, Day 314) that each backend supplies, stored (a `resources.table` file, a pak section, a server reply) or built on demand (a folder scan, a server query, the host's registrations), merged by the mount table by priority; the load path is id-only, paths are resolved at the edges.
- **Backends and mounts** (Days 315, 316, 332): filesystem (loose files, for fast iteration), memory (content the host application provides at run time, reachable from Phase 23's C API), pak (the shipping default), network; upper layers ask by id and never know which served it.
- **Skeletal assets and animation (the user, 2026-11-13):** packed vertex formats in the RHI (Day 317), the skeleton and animation clip formats with minters (Days 318, 320), skin attributes in the mesh format (Day 319), an animation runtime (sampling, blending, additive, root motion, parallel and deterministic; the new module `engine/animation`, Day 321) and GPU skinning from a per-frame joint palette (Day 322); Phase 30's skeletal import writes these formats. Out of scope and filed: retargeting between skeletons, morph targets, state machines, blend trees and IK (Phase 34), compute pre-skinning, non-uniform scale in poses.
- **Per-type formats and minters** (Days 319, 323-325, 326, 327): mesh, texture (with BCn), material, level (with the only optional text form); each with a version, golden old blobs and a deterministic minter.
- **The resource manager** (Days 328-330): handles, cache, dependency graph, fallbacks, device-reset survival, asynchronous loading with priorities, cancellation and a per-frame streaming budget.
- **The network side** (Days 331, 332): a protocol and server over the TCP transport, and the caching, retrying, offline-capable client backend.
- **The tool** (Days 333, 334): `asset_mint` (adopt, mint, pack, verify, list, check; then copy, reid, refs, rename, move, delete, remint, unmint), incremental and deterministic; `pack --target` retargets minted blobs for a platform through per-type transforms (offline only, ids and dependencies untouched).
- **glTF import (the user, 2026-11-14; Days 335-338; amended the same day to an in-memory library for the host):** `engine/asset_import` (`ImportGltf`, `ImportGltfAsync`, `ImportIntoBackend`; our a vendored JSON library chosen by a spike (yyjson by default); limits as settings) and `asset_mint import-gltf` over it read `.gltf`/`.glb` (meshes, skins, animations, images, textures, PBR metallic-roughness materials, optionally the default scene as a level) and mints engine blobs with stable ids kept in an import manifest; hostile files are refused naming the object; unsupported features are refused or dropped with a counted warning, never approximated silently. zlib, libpng and a JPEG decoder are vendored, linked through the importer only.
- **Integration** (Days 339-341): settings, the boundary gate, `asset_demo`, benchmarks, guides, closing runs on three machines and the phase review.

## Notes / open questions

- The BC7 subset (which modes and partitions) is decided by Day 313's spike, not here.
- Whether the pak gains compression (and which codec: a vendored one would be a new third-party entry) is out of this phase; the format reserves a flag.
- ASTC, a network write path, authentication and encryption are all later work; each is filed in `KNOWN-ISSUES.md` on Day 340.
- The Unreal importer (Phase 30) writes the same blob formats through the same writers; nothing in this phase links Unreal code.
- Windows and macOS: no resource-system code is platform specific except the filesystem backend's directory walk, which uses `io::Directory`; the BC formats exist on both (Metal supports BC on the Mac's GPU; arm64 and iOS devices do not, which is why ASTC is Phase 28).
