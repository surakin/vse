# Phase 23 — The Engine as a Loadable Library

**Status: planned at phase level (2026-11-13, the user's request); the day files are not written yet, so the phase cannot start (CLAUDE.md, "Planning policy").** Placed right after Phase 22 so that physics (24), audio (25) and scripting (26) are built knowing the export rules, and after the asset pipeline so the library's surface is known.

**Depends on:** Phase 22 (the resource system is part of what a host loads), Phase 13 (Windows: DLLs) and Phase 21 (macOS: dylibs), Phase 12 (module layering: the library's shape follows `ARCHITECTURE.md`), Phase 11 (settings: one registry across the boundary), Phase 7 (debugging: crash handling and symbols across libraries), Phase 2 (jobs: one scheduler, thread-locals), Phase 16 (wrappers: no `std` type crosses a boundary by construction).
**Goal:** the engine can be built as a loadable library (`libengine.so`, `engine.dll`, `libengine.dylib`) that a host program loads at run time, in addition to the static libraries games link today. A host sees a **versioned, flat C ABI** (opaque handles, no C++ type across the boundary); the engine inside stays C++. Static linking stays the default and keeps every optimization it has; the shared build is an option, tested as thoroughly as the static one.
**Definition of done:** with `-DENGINE_BUILD_SHARED=ON` the whole engine builds as one shared library (and, if the spec says so, per-module libraries for development) on Linux, Windows and macOS with symbols hidden by default and an explicit export list; a header `engine_c.h`, valid C, declares the C API (version negotiation, create/destroy, frame loop, window and renderer, a world, the resource manager, settings and logging); a host can have the engine render into a surface the host provides (below); a host program written in C loads the library with `dlopen`/`LoadLibrary`, checks its version, runs a headless frame and shuts it down; a gate fails when the exported symbol list changes without a version bump or when a C++ type appears in the C header; two libraries in one process see one settings registry, one log, one job scheduler and one allocator (no duplicated singletons); unloading and reloading the library works when the host has shut the engine down; the full suite passes in every flavor with the engine built both ways; the guide and a tutorial are written.

## Key deliverables (to be broken into days before the phase starts)

- **Build system.** `ENGINE_BUILD_SHARED` (default off); the module targets become object or static libraries that link into one `engine` shared target; position-independent code throughout; the sanitizer flavors work with shared libraries (asan runtime sharing, tsan); the unity builds and the module dependency gate (`module_deps_check`) keep their rules; Windows import libraries and PDBs, macOS install names and `@rpath`, Linux `SONAME` and symbol versioning decided in the spec.
- **Symbol visibility and the export list.** Hidden by default (`-fvisibility=hidden`, `/GL` and `__declspec` equivalents); one `ENGINE_API` macro in `build_defs.h` for the few things exported; a committed list of exported symbols checked by a gate (`abi_check`) so a change is a decision, not an accident. Everything an application needs goes through the C API; C++ headers keep working for programs that link the static libraries.
- **The flat C ABI.** `engine_c.h`: opaque handles with generations, `size`-prefixed structs and a version number in every call that takes one, error codes (the engine's `Status` types mapped), strings as pointer and length, callbacks with a user pointer, explicit ownership for every returned buffer, no exceptions or C++ types, compiled by a C compiler in the tests. Covers: version query and negotiation, engine create/destroy with settings, logging hook, the frame loop, window host and renderer, worlds and entities at a basic level, the resource manager (Phase 22), jobs submission, and the crash handler.
- **One of everything across the boundary.** The singletons and global state of foundation (log channels, the settings registry, the job scheduler's thread-locals, the allocator and its statistics, the debug and crash handler, the unity macro wrappers) exist once in the shared library; a host or plugin library never carries its own copy. Memory allocated in one library is freed in the same one (the allocator interface, and no `delete` of a library-owned object across the boundary). Thread-local destruction order at unload is tested (the Phase 2 review found one such leak).
- **The loader.** A small header-only helper for hosts (`engine_loader.h`: C, no engine dependency) that opens the library, resolves one entry point that returns a function table (so there are no import libraries and a missing newer function is detectable), checks the ABI version and refuses an incompatible library with a message; the symbol table approach also gives a stable surface for scripting-language bindings (Phase 26).
- **Unload and reload.** The engine can be shut down completely and the library unloaded and loaded again in one process (all threads joined, all registrations removed, no static destructor ordering hazards); documented limits (a host must not unload with the engine alive).
- **Plugins in the other direction (decided in the spec).** Whether the *game* can itself be a loadable library that the engine's host loads and reloads while running (hot reload of game code) is a question for the spec: the C ABI makes it possible; the work is deferred unless the spec includes it.
- **Platform notes.** Linux shared objects and `RTLD_LOCAL`/`RTLD_DEEPBIND` choices; Windows DLLs (one CRT, no `std` types across, `DllMain` limits: no work in it), delay-loading not used; macOS dylibs and hardened-runtime rules; iOS (Phase 28) and consoles (Phase 29) forbid or restrict dynamic loading of non-bundled code, so the static build remains the way there and the spec says what the C API means on them.
- **Rendering into a host-provided surface (added 2026-11-13, the user's request).** A host application can have the engine render without an engine-created window, and take the frames. The spec decides the modes; the order of work is: (1) **a headless device and renderer through the C API** (a device with no window, `RenderFrame` into a `FrameTarget`, already supported inside the engine: Phase 15's offscreen path); (2) **CPU readback** into a host-owned buffer (a format and stride the host names, one copy per frame, on every backend; also the screenshot and test path); (3) **shared GPU textures**: the host imports or exports a texture shared with the engine's device (Vulkan external memory by fd or Win32 handle, D3D12 shared handle, Metal `IOSurface`), with the synchronization contract (fences or keyed mutex) and the ownership rules written in the C header; (4) **embedding in a foreign native window** (an `HWND`, `NSView`, `wl_surface` or X11 window the host owns: a swapchain on a surface the engine did not create, with resize and loss reported through the C API), only if the spec finds it needed. Each mode is a capability the host queries (`engine_caps`), a backend may refuse one with a clear status, and each has a test (a C host that renders a known scene and compares pixels, through readback and through a shared texture on the platform where it runs). The surface descriptor in the C ABI is versioned and size-prefixed like the rest, so a mode added later is not an ABI break. RHI additions (texture export and import, a foreign-surface creation path in the platform layer) follow the usual rules: behind the RHI interface, `BACKEND.md` checklists updated, Metal and DX12 parity noted.
- **Tests and tools.** A C host (`tests/engine_library/host_c.c`) that loads the library at run time and runs a headless frame; an ABI snapshot test; a duplicated-singleton test (a second small library that links the C API sees the engine's registry and log); unload and reload cycles under asan; the existing suites run once more with the engine built shared; sizes and start-up time compared with the static build (a benchmark).
- **Docs.** `docs/guide/engine-library.md` (building it, the C API, versioning rules, writing a host, platform notes), a tutorial `docs/tutorials/loading-the-engine.md` (a C host that opens a window and clears it), and the spec `docs/superpowers/specs/2026-11-NN-engine-library-design.md` written on the phase's first day.

## Notes / open questions (to settle in the spec on the first day)

- Host-provided surfaces: which of the four modes a first host needs (the user's host is the driving case; ask for its platform and graphics API before the spec), and whether shared textures must work across different GPUs or only on the engine's own device.
- One shared library for the whole engine or one per module (per-module is better for development rebuilds and worse for symbol management and start-up). Recommendation: one aggregate library for distribution, per-module shared targets only as a development option.
- How much of the engine the C API exposes in this phase (the minimum is: engine, renderer frame loop, window, world and entity basics, resource loads, settings, logging). Later phases add to the API with their own version bump.
- Whether the C API is hand-written or generated from the C++ headers' doc comments (the project has `docgen`); recommendation: hand-written first, generated tables for the version check.
- Windows: one DLL needs the same CRT in the host and the engine only if memory or `FILE*` cross the boundary, which the C API forbids; confirm with a test host built with a different CRT setting.
- Interaction with `ENGINE_UNITY_BUILD` and with link-time optimization across the static libraries (the static default must not get slower).
- Not in this phase: a stable C++ ABI, language bindings (Phase 26 uses the C API for scripting), a plugin marketplace, or an editor plugin system (Phase 32).
