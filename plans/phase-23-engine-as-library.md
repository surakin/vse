# Phase 23 — The Engine as a Loadable Library

**Status: planned (2026-11-15): the day files are written (Days 342-357, `plans/phase-23-engine-as-library/`), so the phase can start once Phase 22's open items are accepted; Phase 27 (3D text) moved to Days 358-373 to make room.** Placed right after Phase 22 so that physics (24), audio (25) and scripting (26) are built knowing the export rules, and after the asset pipeline so the library's surface is known.

**Depends on:** Phase 22 (the resource system is part of what a host loads), Phase 13 (Windows: DLLs) and Phase 21 (macOS: dylibs), Phase 12 (module layering: the library's shape follows `ARCHITECTURE.md`), Phase 11 (settings: one registry across the boundary), Phase 7 (debugging: crash handling and symbols across libraries), Phase 2 (jobs: one scheduler, thread-locals), Phase 16 (wrappers: no `std` type crosses a boundary by construction).
**Goal:** the engine can be built as a loadable library (`libengine.so`, `engine.dll`, `libengine.dylib`) that a host program loads at run time, in addition to the static libraries games link today. A host sees a **versioned, flat C ABI** (opaque handles, no C++ type across the boundary); the engine inside stays C++. Static linking stays the default and keeps every optimization it has; the shared build is an option, tested as thoroughly as the static one.
**Definition of done:** with `-DENGINE_BUILD_SHARED=ON` the whole engine builds as one shared library (and, if the spec says so, per-module libraries for development) on Linux, Windows and macOS with symbols hidden by default and an explicit export list; a header `engine_c.h`, valid C, declares the C API (version negotiation, create/destroy, frame loop, window and renderer, a world, the resource manager, settings and logging); a host can embed the engine in a native window it owns (below); a host program written in C loads the library with `dlopen`/`LoadLibrary`, checks its version, runs a headless frame and shuts it down; a gate fails when the exported symbol list changes without a version bump or when a C++ type appears in the C header; two libraries in one process see one settings registry, one log, one job scheduler and one allocator (no duplicated singletons); unloading and reloading the library works when the host has shut the engine down; the full suite passes in every flavor with the engine built both ways; the guide and a tutorial are written.

## Key deliverables (broken into the days above)

- **Build system.** `ENGINE_BUILD_SHARED` (default off); the module targets become object or static libraries that link into one `engine` shared target; position-independent code throughout; the sanitizer flavors work with shared libraries (asan runtime sharing, tsan); the unity builds and the module dependency gate (`module_deps_check`) keep their rules; Windows import libraries and PDBs, macOS install names and `@rpath`, Linux `SONAME` and symbol versioning decided in the spec.
- **Symbol visibility and the export list.** Hidden by default (`-fvisibility=hidden`, `/GL` and `__declspec` equivalents); one `ENGINE_API` macro in `build_defs.h` for the few things exported; a committed list of exported symbols checked by a gate (`abi_check`) so a change is a decision, not an accident. Everything an application needs goes through the C API; C++ headers keep working for programs that link the static libraries.
- **The flat C ABI.** `engine_c.h`: opaque handles with generations, `size`-prefixed structs and a version number in every call that takes one, error codes (the engine's `Status` types mapped), strings as pointer and length, callbacks with a user pointer, explicit ownership for every returned buffer, no exceptions or C++ types, compiled by a C compiler in the tests. Covers: version query and negotiation, engine create/destroy with settings, logging hook, the frame loop, window host and renderer, worlds and entities at a basic level, the resource manager (Phase 22), jobs submission, and the crash handler.
- **One of everything across the boundary.** The singletons and global state of foundation (log channels, the settings registry, the job scheduler's thread-locals, the allocator and its statistics, the debug and crash handler, the unity macro wrappers) exist once in the shared library; a host or plugin library never carries its own copy. Memory allocated in one library is freed in the same one (the allocator interface, and no `delete` of a library-owned object across the boundary). Thread-local destruction order at unload is tested (the Phase 2 review found one such leak).
- **The loader.** A small header-only helper for hosts (`engine_loader.h`: C, no engine dependency) that opens the library, resolves one entry point that returns a function table (so there are no import libraries and a missing newer function is detectable), checks the ABI version and refuses an incompatible library with a message; the symbol table approach also gives a stable surface for scripting-language bindings (Phase 26).
- **Unload and reload.** The engine can be shut down completely and the library unloaded and loaded again in one process (all threads joined, all registrations removed, no static destructor ordering hazards); documented limits (a host must not unload with the engine alive).
- **Importing glTF at run time (added 2026-11-14, the user; for the host).** The C API exposes Phase 22's importer library (`engine/asset_import`, Days 335-338) next to the memory backend: `engine_import_gltf(handle, bytes, size, options, ...)` imports a `.glb` or `.gltf` into the host memory backend (the asynchronous form returns a ticket the host polls or cancels; external URIs go through a host callback, so the host decides where bytes come from), and returns the import manifest as bytes for the host to keep and pass to a re-import. The importer is linked only into the library built for such a host (an option of the build), so the other builds do not carry the image decoders. The spec decides the exact signatures.
- **Plugins in the other direction (decided in the spec).** Whether the *game* can itself be a loadable library that the engine's host loads and reloads while running (hot reload of game code) is a question for the spec: the C ABI makes it possible; the work is deferred unless the spec includes it.
- **Platform notes.** Linux shared objects and `RTLD_LOCAL`/`RTLD_DEEPBIND` choices; Windows DLLs (one CRT, no `std` types across, `DllMain` limits: no work in it), delay-loading not used; macOS dylibs and hardened-runtime rules; iOS (Phase 28) and consoles (Phase 29) forbid or restrict dynamic loading of non-bundled code, so the static build remains the way there and the spec says what the C API means on them.
- **Host-provided content through the memory backend (added 2026-11-13, the user's request).** Phase 22's `HostMemoryBackend` (Day 315) is exposed in the C API so a host supplies engine content directly, without files: `engine_resources_add(handle, id, path_or_null, bytes, size, flags, release_fn, user)` (copied, or borrowed with a release callback the engine calls exactly once, on the thread the spec names, after the last reader is done), `engine_resources_replace`, `engine_resources_remove` (with the `InUse` status naming the dependents, and an explicit force that unloads them atomically), a query for what is mounted, and a content-hash check option; the memory backend is mounted at a configurable priority (default above the pak, so host content overrides shipped content). Ownership is explicit in the header (who frees what, which thread a release callback runs on, that a borrowed buffer must outlive the call that registered it until its callback runs), nothing crosses the boundary as a C++ type and the blobs a host adds are minted ones (made by `asset_mint` or loaded from the host's own storage); whether the C API also exposes minting entry points is a spec decision. Test: a C host adds a mesh, texture and material from memory, renders them, replaces the texture while a frame is in flight, removes a depended-on resource (refused), and unloads the library with borrowed buffers released exactly once.
- **Rendering into a host-provided native window (added 2026-11-13, the user's request; embedding is the driving case, confirmed the same day).** A host application owns a native window or view and the engine renders into it, with no engine-created window. The order of work: (1) **a device and swapchain on a foreign surface**: `os::Window`-independent surface creation from the host's handle (an `HWND`, an `NSView` or `CAMetalLayer`, a `wl_surface` with its `wl_display`, an X11 window with its display), for the Vulkan, Direct3D 12 and Metal backends, behind the RHI (a surface descriptor instead of an `os::Window`; `RecreateSurface` takes it too); (2) **the host owns size, visibility, DPI and the event loop**: the host tells the engine the surface size and scale (`engine_surface_resized`), the engine reports out-of-date and lost surfaces and recovers through the Phase 8 reset path, and the engine never creates or destroys the host's window; (3) **input arrives from the host**: the host forwards keyboard, pointer and text events through the C API into the engine's input stream (the engine's own window hosts stay the source for engine-created windows), and the cursor, clipboard and focus requests the engine makes come back as callbacks the host performs; (4) **the frame loop is driven by the host** (`engine_frame` from the host's timer or display link; no thread of the engine blocks on the host's loop); (5) the two fallbacks the spec weighs, **CPU readback** (also the screenshot and test path) and **shared GPU textures** (Vulkan external memory, D3D12 shared handle, `IOSurface`) for hosts that composite the frame themselves, built after the embedding. Each mode is a capability the host queries (`engine_caps`); a backend may refuse one with a clear status; the surface descriptor in the C ABI is versioned and size-prefixed so a mode added later is not an ABI break. Tests: a C host that creates a native window of its own (X11 and Wayland on Linux, Win32, Cocoa), embeds the engine, renders a known scene, resizes, loses and regains the surface, and compares pixels; locked-session caveats as for the other window tests. RHI and platform additions follow the usual rules: `BACKEND.md` checklists updated, the platform-neutral and boundary gates extended to the foreign-handle types, Metal and DX12 parity noted.
- **Tests and tools.** A C host (`tests/engine_library/host_c.c`) that loads the library at run time and runs a headless frame; an ABI snapshot test; a duplicated-singleton test (a second small library that links the C API sees the engine's registry and log); unload and reload cycles under asan; the existing suites run once more with the engine built shared; sizes and start-up time compared with the static build (a benchmark).
- **Docs.** `docs/guide/engine-library.md` (building it, the C API, versioning rules, writing a host, platform notes), a tutorial `docs/tutorials/loading-the-engine.md` (a C host that opens a window and clears it), and the spec `docs/superpowers/specs/2026-11-NN-engine-library-design.md` written on the phase's first day.

## Notes / open questions (to settle in the spec on the first day)

- Embedding: the host already runs on Linux, Windows and macOS, as the engine does (the user, 2026-11-13), so the surface path is built and tested on all three together, not one platform first: Linux needs both Wayland (`wl_display` and `wl_surface` from the host's connection; the engine must not open a second connection for the same surface) and X11, Windows needs Vulkan and D3D12 on an `HWND`, macOS needs Metal on the host's `NSView`. Decided (the user, 2026-11-13): **the host owns input and the clipboard** (it forwards events into the engine; the engine asks for cursor shape, clipboard and focus through callbacks, and opens no input or clipboard connection of its own on an embedded surface). Assumed, to confirm before the spec: the host's toolkit exposes the raw native handle (`HWND`, `NSView`, `wl_surface`/X11 window); if it turns out not to, the fallback is CPU readback or a shared texture for that toolkit.
- One shared library for the whole engine or one per module (per-module is better for development rebuilds and worse for symbol management and start-up). Recommendation: one aggregate library for distribution, per-module shared targets only as a development option.
- How much of the engine the C API exposes in this phase (the minimum is: engine, renderer frame loop, window, world and entity basics, resource loads, settings, logging). Later phases add to the API with their own version bump.
- Whether the C API is hand-written or generated from the C++ headers' doc comments (the project has `docgen`); recommendation: hand-written first, generated tables for the version check.
- Windows: one DLL needs the same CRT in the host and the engine only if memory or `FILE*` cross the boundary, which the C API forbids; confirm with a test host built with a different CRT setting.
- Interaction with `ENGINE_UNITY_BUILD` and with link-time optimization across the static libraries (the static default must not get slower).
- Not in this phase: a stable C++ ABI, language bindings (Phase 26 uses the C API for scripting), a plugin marketplace, or an editor plugin system (Phase 32).
