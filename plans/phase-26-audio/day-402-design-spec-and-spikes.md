# Phase 26 / Day 402 — Design Spec, Spikes and Phase Setup

**Phase:** [Phase 26 — Audio](../phase-26-audio.md)
**Depends on:** Phase 25 closed on Linux; the Phase 26 plan (user decisions, 2026-11-17).

Settle the architecture with numbers before any audio code: what the mixer is, how repeatable its output must be (the same on one build, equal within a tolerance across machines), which Linux backend, where decoders and test streams come from.

## Tasks

- [ ] Write `docs/superpowers/specs/2026-11-NN-audio-design.md`: the module (`engine/audio`, its layer and edges: it sits above `jobs`, `ecs`, `spatial`, `asset` and `physics`, which it reaches only through narrow interfaces such as an occlusion query), the device interface (a render callback that pulls interleaved `f32` frames), the mixer block (a fixed number of frames, a sample rate per device), the thread model (a game thread posts commands, the device thread renders), and the list of what is built and what is not (HRTF, ambisonics, MIDI, synthesis, voice chat are out).
- [ ] **Spike 1, the Linux backend:** a throwaway program (kept under `docs/superpowers/specs/2026-11-NN-audio-spikes/` as `.txt`) that plays a sine through (a) raw ALSA ioctls on `/dev/snd/pcmC*D*p` (hw_params, sw_params, mmap or write, `snd_pcm_status` equivalents) and (b) the PipeWire native protocol over its Unix socket; measure the work to write each, the latency at 256 and 1024 frames, and whether (a) works when PipeWire owns the card (its ALSA emulation, `pipewire-alsa`) and when it does not; recommend one to the user in the spec (the assumption #1 line: `libasound` is a distro library, the kernel ABI and the protocol are the OS boundary). The user decides if the recommendation is not the plan default.
- [ ] **Spike 2, repeatability and tolerance (the user, 2026-11-17: audio need not be byte-identical across machines):** render a reference scene (voices, resampling, pan, a filter, a reverb) on this machine under GCC and Clang, unity and not, Debug and Release, with and without FMA contraction; show it is bit-identical for one build run to run and for any callback size and producer timing, and measure how far builds and contraction modes drift apart (max absolute sample error and RMS error in dB); the result sets the cross-machine tolerance (plan: max abs error 1e-4, about -80 dB) and the comparison form (per-block RMS and peak plus sample probes, not byte equality). The audio code may use libm and the compiler's default floating-point flags; only the command ordering and the fixed voice and bus order are required for same-build repeatability.
- [ ] **Spike 3, the resampler:** linear, 4-point cubic Hermite and a 16-tap windowed sinc compared on a sine sweep for aliasing and cost per voice per block; fixed-point (`u64` 32.32) source positions so a long loop does not drift; the spec picks the default and the quality setting.
- [ ] **Spike 4, the command queue:** a single-producer single-consumer ring from the game thread to the device thread, each command stamped with a block number so an offline render and a live one apply it at the same block; measure the latency of a command and show the order is the same for any producer timing.
- [ ] **Spike 5, vendoring libvorbis (the user's decision, 2026-11-17):** pick the pinned releases of libogg and libvorbis (version, SHA-256, licence: BSD-3-Clause), build them from source with the project's flags (warnings are errors apply to our targets only, the vendored code keeps its own), and check: that the decode-only subset (`vorbisfile` is not used; `vorbisenc` and the encoder are left out) compiles under GCC, Clang, MSVC and clang-cl and Apple clang; what it allocates and how (`malloc` through the library's own calls, so decoding runs on a job and never on the audio thread); how it behaves on hostile streams (a mutation fuzz of the fixtures under asan: crashes, hangs, unbounded allocation) and the limits the facade must add; whether its output is the same bits on the three machines (its tables use libm `sin`/`cos`/`exp`: a per-machine tolerance and a Linux-only committed hash, or equal hashes); and where the committed test streams come from (an encoder installed here, or streams made once by a script and committed with their recipe and licence). The outcome is recorded in the spec and amends Days 420-422.
- [ ] **Spike 6, voices at scale:** how many voices one block mixes per millisecond with the resampler of spike 3 on one thread (1,000 and 5,000), to set the voice limit and the virtualisation rule (a voice beyond the limit keeps its position and costs no mixing).
- [ ] Fix in the spec: the settings (`audio.*` names, defaults, classification: which apply live and which need a device restart), the bus model, the ECS components (`AudioSource`, `AudioListener`), the units (metres, seconds, linear gain with decibel helpers, +Y up, the listener looks along -Z like the camera), the state hash of a rendered block, and the C API surface (Days 426-427); record where the plan's defaults changed and edit the later day files that the findings change.
- [ ] Set `CURRENT_PHASE` to 26 and add the phase to `tests/phases.txt`; `STATUS.md` names Day 403 next.
- [ ] **Runs (CLAUDE.md "Tests run by phase"):** `scripts/test-phase.sh --affected` plain; then the asan and tsan flavors (this phase is concurrency, lifetime and memory code on nearly every day); quote each run's final `ran X of Y tests (phases ...)` line in this file and never say "all tests pass" for a reduced run. `ctest -L docs` when a public header or a guide changed. Build clean (warnings are errors) with both compilers and unity on and off; `-DENGINE_BUILD_SHARED=ON` and `-DENGINE_LIBRARY_WITH_IMPORTER=OFF` still build.
- [ ] **Module rules (CLAUDE.md):** a new module, target or edge updates `ARCHITECTURE.md`, `tools/module_deps_check/modules.txt`, `tests/module_map.txt` and `BUILD.md` in the same commit; every new test file has its line in `tests/phases.txt` (phase 26); only wrapped types, no `std`, no raw platform macros; the audio thread never allocates, locks or does I/O.
- [ ] **Day review (CLAUDE.md, required):** `/code-review high` over the day's diff after the scoped tests; verify, fix (with a regression test shown to fail without the fix) or decline each finding with a reason; record the count and outcome under "Post-implementation code review" below and in `STATUS.md`.
