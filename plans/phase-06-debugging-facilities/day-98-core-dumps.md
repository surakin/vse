# Phase 6 / Day 98 — Core Dumps

**Phase:** [Phase 6 — Debugging Facilities](../phase-06-debugging-facilities.md)
**Depends on:** Day 97 (the crash handling that the core dump complements).

Make core dumps happen reliably, and make it easy to open the latest one in `gdb` with the right symbols.

## Tasks

- [ ] The interface is the platform-neutral idea of "post-mortem artifacts": `EnablePostMortemDumps(options) -> Result` with the result `Enabled`, `Limited(reason)` or `Unsupported` (iOS, consoles with their own system), documented per platform in the header: Linux cores, Windows WER `LocalDumps`, macOS cores and crash reports, Android tombstones. Only the Linux implementation exists now.
- [ ] `EnableCoreDumps(options)` in `engine/foundation/os/linux/debug/core_dump.cpp` (the Linux implementation behind that interface): raise the soft `RLIMIT_CORE` to the hard limit (or a given size) with `setrlimit`, return what the limit was and is, and report when the hard limit is zero (nothing the process can do; the report says how to raise it). Call it from `InstallCrashHandler` (Day 95) when the option is set. On Linux also `prctl(PR_SET_DUMPABLE, 1)` (a setuid or capability-dropping process may have cleared it).
- [ ] Report the destination so a developer knows where the core went: read `/proc/sys/kernel/core_pattern` at install time and put it in the crash context; if it starts with `|` (here: `systemd-coredump`) say "use `coredumpctl`"; otherwise print the expanded file name pattern. A test for each of the two forms using a function that takes the pattern text.
- [ ] The scripts are Linux/macOS shell scripts, named and documented as such; a PowerShell equivalent for WER dumps is a Phase 8 item recorded in the Phase 8 file.
- [ ] Script `scripts/find-core.sh`: finds the newest core for a given executable (via `coredumpctl list`/`coredumpctl dump -o` when available, otherwise the file the pattern names in the current directory), checks that the core's recorded build id (the `NT_GNU_BUILD_ID` note in the executable inside the core, read with `readelf -n`/`eu-unstrip`) matches the binary you pass, and prints the `gdb` command. `scripts/open-core.sh` runs `gdb -ex bt -ex 'thread apply all bt' <exe> <core>` batch mode and prints the result. Both are shell scripts, tested by a script test in the style of `tests/test_phase_script` with a fixture core generated by a crashing child (skipped with a clear message when core dumps are impossible on the machine, recorded in `KNOWN-ISSUES.md` if so).
- [ ] The developer guide section "Core dumps on Linux": `systemd-coredump` and `coredumpctl`, the `core_pattern` alternatives, `ulimit -c`, `/proc/sys/kernel/core_pattern` changes needing root (shown, never run by the engine), disk-space warnings, and the privacy note (a core contains process memory).
- [ ] A test (death-test helper, child with core enabled and a core size cap) that crashes, then locates the core with the script and runs `gdb` in batch mode asking for the faulting function's name; skipped (not failed) when `gdb` is missing or cores are disabled, with the reason printed.
- [ ] **Documentation:** `///` comments; the guide page extended; `docs/guide/building-and-testing.md` mentions the scripts; reference regenerated and committed; `docgen lint` at zero; `ctest -L docs` passes.
- [ ] Run the day's scoped tests (`--affected`, asan and tsan flavors) and quote the `ran X of Y tests` lines.
- [ ] **End-of-day review (CLAUDE.md):** `/code-review high` on the day's diff (code and scripts); record it here and in `STATUS.md`.
- [ ] Update `STATUS.md`; commit.

**Done:** `EnableCoreDumps` raises the limit and tells the developer where the core goes; the two scripts find the newest core for a binary, verify its build id, and open it in `gdb`; the test proves it end to end on a machine with `gdb`, or says why it skipped; the guide documents the setup for `systemd-coredump` and plain cores.
