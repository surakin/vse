# Phase 6 / Day 91 — Design & Spikes

**Phase:** [Phase 6 — Debugging Facilities](../phase-06-debugging-facilities.md)
**Depends on:** Phase 5 complete.

Settle the design and prove the risky mechanisms with throwaway spikes before any production code exists. Planning and
spikes only: no change to `engine/`, no new test.

## Tasks

- [ ] Inventory what exists: `AssertFail` and the two test sinks in `engine/foundation/log/log.cpp` (it prints to fd 1 and exits with code 1 through `os::Exit`, it does not abort); the number of `ENGINE_ASSERT` sites (334 at planning time) and how many tests redirect the exit (`SetExitSinkForTesting`, today `tests/foundation/container_vector_test.cpp`); every place that handles a signal or installs a sanitizer option (`lsan_options.cpp`, none else); the compile flags that matter for stack walking (`-fno-omit-frame-pointer` is set only on the asan/tsan flavors; the plain flavor and the release flavor omit it). Put the table in the design spec.
- [ ] Spike A, stack walking (scratchpad, not committed): walk frames by following `rbp` from a signal handler and from a normal call, with and without `-fno-omit-frame-pointer`, through a `std::thread`, a coroutine resumed on a job worker (`engine/jobs`), a frame inside `libvulkan`/driver code that has no frame pointers, and a frame inside libc. Record which cases stop early and what bounds check (stack range from `pthread_getattr_np`/`/proc/self/maps`, alignment, strictly increasing addresses) keeps the walker from faulting. Compare with the `.eh_frame` unwinder (`_Unwind_Backtrace`, not async-signal-safe) as the reference.
- [ ] Spike B, symbolization (scratchpad): read function names from `.symtab` and `.dynsym` of the main binary and of one shared library with an mmap'd ELF reader that uses no heap and no libc stdio; count lookups per second and note stripped binaries. Resolve `file:line` for the same addresses with `addr2line -f -C -i -e` and with `eu-addr2line` to see which tool prints inlined frames correctly (both exist on the development machine). Record the build-id note (`NT_GNU_BUILD_ID`) reading.
- [ ] Spike C, crash handler under the sanitizers (scratchpad): install a `SIGSEGV` handler on an alternate stack in a plain, an ASan/UBSan and a TSan binary; record for each whether the handler runs (`ASAN_OPTIONS=allow_user_segv_handler`, `handle_segv`, `handle_abort`), whether the sanitizer's own report appears first, and what `sigaction` returns for the previous handler (for chaining). Also try a fault on a worker thread and a stack overflow (alternate stack required).
- [ ] Spike D, minidump (scratchpad): write the smallest valid Microsoft minidump by hand (header, directory, SystemInfo, ThreadList with one thread, ModuleList from `/proc/self/maps`, Exception with the `ucontext` registers, one stack memory range) and open it with `lldb` (installed, 23.1.4, with its minidump plugin: `lldb -c file.dmp`; try `image list`, `thread list`, `register read`, `bt`, `memory read`). `minidump-stackwalk` is not installed (`rustup` is, so `cargo install minidump-stackwalk` is possible); try it too if it can be had. Record what each tool accepted and what it rejected (module name and CodeView/build-id conventions are the usual cause). The decision below depends on the result.
- [ ] Spike E, core dumps: record this machine's `core_pattern` (`systemd-coredump`), `ulimit -c`, and that `coredumpctl` and `gdb` are present; run a crashing program with `RLIMIT_CORE` raised by the program itself and see where the core goes and whether it can be opened by `gdb` with the binary's symbols.
- [ ] Decide and write down, each with its reason (the plan proposed some of these; settle them here): (1) **symbolization**: at crash time the handler prints raw addresses and `module+offset` first (always async-signal-safe), then adds function names from the own ELF symbol reader; `file:line` comes offline from `tools/symbolize` (a thin dev tool that runs `addr2line`; binutils are a developer tool, never linked or shipped); an own DWARF line reader is out of scope and filed in `KNOWN-ISSUES.md`. (2) **Linux minidump**: proposed yes, an own writer, limited to the crashing thread (registers, stack memory, module list, exception, system info) because other threads' contexts need ptrace from a helper process; other threads are listed by id only, and the gap is filed. If Spike D shows `lldb` cannot open even the minimal file and the cause is not fixable in the writer, keep the writer, make the in-tree reader the verification path, and file the incompatibility in `KNOWN-ISSUES.md`. (3) **assert semantics**: `ENGINE_ASSERT` stays always on and fatal, now through the new handler chain and ending in `abort()` (so a debugger and the crash handler see `SIGABRT`), not `os::Exit(1)`. (4) **where things live**: `engine/foundation/debug/` for interfaces, `engine/foundation/os/linux/debug/` for the Linux backends (the same split `os.h` uses), tests in a new `tests/debug/` directory with plain, ASan and TSan flavors (the crash handler must be proven under the sanitizers, and `tests/foundation` has no sanitizer flavors). (5) **sanitizer policy**: from the Spike C result.
- [ ] Decide the stack-trace data types (a fixed-capacity frame array of addresses, no heap; a `ModuleInfo` with path, base, build id) and the dump/report text format, so Days 94-100 do not each invent one. Decide what a report contains in order: reason, thread, build id, platform, trace, last log lines.
- [ ] Decide the privacy/size rules: where dumps go (`./crashes/` or `ENGINE_CRASH_DIR`, never a system path), a size cap for the stack memory range, and that nothing is ever uploaded.
- [ ] Write the design spec `docs/superpowers/specs/2026-11-06-debugging-design.md`: the inventory, the spike results (what worked, what did not, with command lines), every decision above with its reason, and a risk list (a handler that itself faults, a fault in the allocator or in a driver thread, double faults, the sanitizers swallowing the signal, a frame-pointer-less library cutting a trace short) with the mitigation for each.
- [ ] Update the Day 92-102 files where a spike result changes a task (edit the plan before continuing, per `CLAUDE.md`); correct `plans/phase-06-debugging-facilities.md` notes that the spikes settle.
- [ ] **Documentation:** no public API. The spec is linked from `docs/README.md`.
- [ ] Update `STATUS.md`; commit (planning and spec only; no code review is required for a planning-only commit).

**Done:** the spec exists with the inventory, five spike results and every listed decision with its reason; later day files are corrected where the spikes disagreed with the plan; nothing under `engine/` changed.
