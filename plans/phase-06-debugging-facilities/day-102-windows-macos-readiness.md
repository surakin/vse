# Phase 6 / Day 102 — Windows & macOS Readiness

**Phase:** [Phase 6 — Debugging Facilities](../phase-06-debugging-facilities.md)
**Depends on:** Days 91-101.

Phase 6 implements Linux only. This day makes everything that can be built and tested on a Linux machine for the
Windows (Phase 8) and macOS (Phase 9) backends **done now**, so what remains in those phases is exactly the OS-call
layer, written down as a checklist with the tests that must pass. Mobile and consoles are designed in (the neutral
interfaces do not preclude them, `Unsupported` is a valid answer) but get no work here.

## Tasks

- [ ] Portable module-file readers, pure byte parsers with every offset and size bounds-checked, under `engine/foundation/debug/`: `MachOImage` (64-bit header, load commands: `LC_UUID`, `LC_SYMTAB` with its `nlist_64` symbols and string table, `LC_SEGMENT_64` ranges, `LC_BUILD_VERSION`; a fat header selects the slice for the requested architecture) and `PeImage` (DOS and PE headers, section table, the debug directory's CodeView `RSDS` record giving GUID, age and PDB path, the export table's names, the machine type). Both plug into the Day 95 `BuildId` kinds and `ModuleSymbols` interface, so Phase 8 and 9 add only the call that lists the loaded images. They run on any host: a Linux machine can read a Mach-O or PE file.
- [ ] Fixtures: object files cross-compiled by the installed clang (`clang --target=arm64-apple-macos13 -c` and `clang --target=x86_64-pc-windows-msvc -c` from a committed source with two known functions), committed under `tests/debug/fixtures/` with the generating command lines in a README (a checkout without a cross-capable clang uses the committed files, like the shader outputs). There is no `lld` here, so linked images are produced by a test-side builder that writes a minimal Mach-O with `LC_UUID` and a minimal PE with a CodeView debug directory holding a known GUID and age. Tests: the planted UUID and GUID+age come back exactly, the two functions are found with correct offsets and sizes, an address between functions resolves to the previous symbol only inside its size, a stripped image falls back to the raw form, ELF and garbage are rejected by the wrong reader, and a byte-flip and truncation sweep under ASan never reads out of range.
- [ ] Minidump module records from those readers: the Day 99 serializer test is extended so a module list built from the Mach-O and PE readers (UUID, GUID+age, Windows-style and macOS-style paths) is written and read back by the Day 100 reader and opened by `lldb`.
- [ ] Backend conformance suite: confirm `tests/debug` talks only to the neutral API (fault injection through `InjectFault(FaultKind)`, results through `ChildResult::reason`, no signal, `fork` or `/proc` use outside the Linux backend); write `tests/debug/BACKEND-CONFORMANCE.md` listing every test group, the neutral function it exercises, the `CrashReason` each `FaultKind` must produce, and which groups are allowed to skip with `Unsupported`. Phases 8 and 9 build the same test sources and make the same groups pass.
- [ ] Backend checklists: `engine/foundation/os/windows/debug/BACKEND.md` and `engine/foundation/os/macos/debug/BACKEND.md`, one section per facility (stack walk, module list, symbols, crash handler, post-mortem dumps, snapshot, death-test spawn, debugger detection, crash-dump directory, thread registration, system info), each giving the neutral function signature to implement, the OS API to use, the constraints from the Day 91 research, and the conformance groups that exercise it. Every neutral function a platform implements carries a `Backend:` doc label; a ctest (`debug_backend_lists`) fails if a labeled function is missing from either checklist.
- [ ] Cross-target checks (from Day 91's Spike G, using the shim headers it settled on, or filed in `KNOWN-ISSUES.md` if it proved impossible): ctests `debug_cross_syntax_windows` (`x86_64-pc-windows-msvc`), `debug_cross_syntax_macos` (`arm64-apple-macos13`) and `debug_cross_syntax_aarch64_linux` compile every neutral header and every portable source (serializer, reader, formatter, ring buffer, module readers) with `-fsyntax-only`, skipping with a reason where clang is missing. They prove the portable code has no hidden Linux dependency.
- [ ] CMake: the platform selection for the debug sources (created on Day 92) has Windows and macOS branches that stop with a message naming Phase 8 or 9 and the `BACKEND.md` to implement, instead of a generic failure.
- [ ] Porting guide `docs/guide/porting-debugging.md`, a Windows section and a macOS section, written from the Day 91 research: the exact API sequence for each facility and its traps (what an exception filter may call, stack overflow and `SetThreadStackGuarantee`, the Mach exception port thread and `EXC_BAD_ACCESS`, entitlements and code signing for crash handling, dSYM and PDB lookup and age matching, WER `LocalDumps` registry keys, `~/Library/Logs/DiagnosticReports`), which Phase 6 pieces to reuse unchanged, and where each Phase 6 test expectation differs by platform. Code blocks that cannot compile on Linux are plain fences, not tagged samples; `docgen links` and `lint` still pass.
- [ ] Replace the placeholder bullets in `plans/phase-08-windows-dx12.md` and `plans/phase-09-macos-metal.md` (added when the plan was made multi-platform) with the real remaining work, copied from the two `BACKEND.md` files, and the tests that must pass; keep the Phase 17 and 18 notes short ("designed in, see Phase 6").
- [ ] **Documentation:** the `///` comments carry the `Backend:` labels; the guide page above; reference regenerated and committed; `docgen lint` at zero; `ctest -L docs` passes.
- [ ] Run the day's scoped tests (`--affected`, asan and tsan flavors) and quote the `ran X of Y tests` lines.
- [ ] **End-of-day review (CLAUDE.md):** `/code-review high` on the day's diff, with extra attention to every offset in the Mach-O and PE parsers; record it here and in `STATUS.md`.
- [ ] Update `STATUS.md`; commit.

**Done:** Mach-O and PE files are read correctly (build id, symbols) and robustly on this machine from committed fixtures; the portable code compiles for the Windows, macOS and AArch64 targets; `tests/debug/BACKEND-CONFORMANCE.md` and the two `BACKEND.md` files exist and are kept in step with the headers by a test; the porting guide is written; the Phase 8 and 9 plan files list exactly what is left for them.
