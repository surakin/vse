# Phase 6 / Day 97 — Crash Handling End to End

**Phase:** [Phase 6 — Debugging Facilities](../phase-06-debugging-facilities.md)
**Depends on:** Days 92-96.

The library catches the fault and writes the dump (Day 95); our report (Day 96) must appear on stderr and next to the
dump, on every thread, without making things worse. Day 91 showed the library's `on_crash` hook runs in the crashing
process, so the report is written there and the engine installs no signal handler of its own. This day connects them and proves the whole path, including the
cases that go wrong.

## Tasks

- [ ] Connect the report to the crash through the library's `on_crash` hook (Day 95 installs it): the hook writes the Day 96 report to the report sink and to the attached `crash-report.txt` before the library writes the dump; a fault inside the report path is caught by an atomic re-entry flag that prints `double fault` and returns so the dump still gets written; the original fault is still delivered (the process exit status shows the original signal and a debugger sees the original fault). The hook never blocks: it has a time budget (a `clock_gettime` check between sections) and stops writing sections when it is over.
- [ ] Coexistence rules written into the guide and tested: Day 91 Spike D found that a handler installed **before** `sentry_init` is replaced by Breakpad's and never runs, and one installed after runs and chains; the engine installs none, and the guide says an application that wants its own handler must install it after `InstallCrashHandler` and chain to the previous one (a test does exactly that). `UninstallCrashHandler` restores the previous disposition. Sanitizer policy: the handler is off in the sanitizer flavors unless asked (their own reports are the artifact), a smoke test installs and crashes under ASan (Day 91: it worked), and the TSan result from Day 95 is applied; a `SIGABRT` raised by `AssertFail` still prints our report because `AssertFail` printed it before aborting.
- [ ] Threads: a fault on a job worker, on the I/O thread, on a plain `std::thread`, inside a driver thread and on the main thread each produces a dump holding every thread and a report naming the faulting thread; a stack overflow produces a dump and a report (Day 91: it did, with the Breakpad backend; if a worker thread needs an alternate stack, add `RegisterThreadForCrashHandling`). Two threads faulting at once produce one report.
- [ ] Tests (death-test helper, child processes; written against the neutral API so Phases 8 and 9 run the same sources): `InjectFault` for each `FaultKind` gives the expected `CrashReason`, the report text on stderr (function name from Day 94, reason, build id, last log lines), one envelope (from which `crash_extract` yields the `.dmp`) and one attached `.txt` in the dump directory, and the original signal in the exit status; stack overflow; fault on a worker thread and on a plain thread; a second fault inside a provider; an application handler installed before is called after our report; uninstall restores the default; `ENGINE_ASSERT` failing in a child ends with `SIGABRT`, our report, and a dump; run the set 20 times with no flaky result.
- [ ] Open each extracted dump with `lldb` in an automated ctest (skips with a printed reason where `lldb` is missing): `lldb -b -c <dump> -o 'thread list' -o 'bt all' -o 'image list'` shows the faulting function on the faulting thread, the other threads, and the main module with the build id. Record the exact command lines in the guide.
- [ ] Debugger check (manual, recorded): a crashing program run under `gdb` stops at the original faulting instruction, not inside a handler; if no human has done it by the end of the day it goes to `KNOWN-ISSUES.md` as a check not yet done.
- [ ] Safety review of our own code in the crash path (the `on_crash` hook and the report writer): it calls only the Day 94 and 96 functions and raw syscalls (`write`, `open`, `close`, `getpid`, `gettid`, `clock_gettime`); no `malloc`, `printf`, `std::`, `pthread_mutex_*`. A CMake-script gate in the style of `tools/raw_new_check` (`tools/signal_safety_check`, with fixtures planting each forbidden identifier) enforces it on those files.
- [ ] **Documentation:** `///` comments with `Thread-safety:` and `Fails:`; the guide gets "When the program crashes" (what you see, the files, how to read the exit status, the sanitizer table); reference regenerated and committed; `docgen lint` at zero; `ctest -L docs` passes.
- [ ] Run the day's scoped tests (`--affected`, asan and tsan flavors) and quote the `ran X of Y tests` lines.
- [ ] **End-of-day review (CLAUDE.md):** `/code-review high`; the most signal-safety, lifetime and concurrency risk of the phase, so treat every finding seriously; record it here and in `STATUS.md`.
- [ ] Update `STATUS.md`; commit.

**Done:** a crash on any thread, a stack overflow, an abort and a failed assert each print our report, leave an envelope whose extracted dump holds every thread and opens in `lldb`, and end with the original signal; a fault in the report path cannot loop; the safety gate passes; the tests pass in plain, ASan and TSan and repeat 20 times without failure.
