# Phase 20 / Day 274 — UDP Transport I: Packet Format, Handshake & Connection State

**Phase:** [Phase 20 — Networking](../phase-20-networking.md)
**Depends on:** Days 268-269, 272, 273.

The first third of the UDP transport: how two endpoints establish a connection safely and exchange sequenced, acknowledged packets.

## Tasks

- [x] **Packet format** (fixed header: protocol id, packet type, connection id, sequence, ack, ack bitfield; versioned; big-endian through `NetWriter`), documented in the guide with a diagram; a packet shorter than its header or longer than the MTU is dropped and counted, never processed.
- [x] **Handshake with a challenge against address spoofing:** client hello (padded to full size so the server cannot be used as an amplifier), server challenge carrying a stateless cookie (HMAC-style keyed hash of the endpoint and a rotating secret, built on a documented non-cryptographic-in-this-phase construction unless Day 280 supplies an audited primitive: **never custom cryptography**, so before Day 280 the cookie is documented as an anti-spoofing measure for trusted networks only), client response, server accept; the server keeps **no per-connection state before the response validates**; retransmission of handshake packets with backoff; version and capacity negotiation.
- [x] **Connection state machine** (`Connecting`, `Connected`, `Closing`, `Closed`) with timeouts for each state, a connection table with a hard cap (`net.max_connections`) and per-endpoint limits, orderly close (a close packet repeated a few times) and reset on unknown connection ids.
- [x] **Sequence numbers and acknowledgements:** 16-bit packet sequence with wraparound-safe comparison, ack plus 32-bit bitfield (Gaffer-style), duplicate-packet detection window, tested across wraparound.
- [x] **Tests** (`tests/net/udp_handshake_test.cpp`) over the simulated network and, labelled `network`, loopback: handshake under 0-60 percent loss, reordering and duplication; spoofed-source hello floods leave the server with zero connection state; amplification factor at most 1; replayed and stale handshake packets rejected; wraparound of sequence numbers at 65535 with reordering around the boundary.

## Outcome (2026-11-12, Linux machine)

- Deviations from the task text, as the spec says: integers are little-endian (spec), not big-endian; the first byte is kind (3 bits), an ack-valid flag, a reserved bit and the version (3 bits); the sequence is 16 bits on the wire with an ack and a 32-bit bitfield. `net.max_connections` is `UdpTransportConfig::max_connections` until the settings of Day 281.
- Added: `net::DatagramPort` with `SocketDatagramPort` (real UDP socket) and `SimDatagramPort`; `udp::` helpers (`SipHash24`, `SeqNewer`, `ReceiveWindow`, `SendLog`, payload header); `net::UdpTransport` (stateless cookie handshake, connection table with total and per-address caps, Disconnect repeated, Reset for unknown ids, keep-alive, delayed acknowledgements; unreliable messages only until Days 275-276).
- The cookie is SipHash-2-4 (published vectors in the test), not custom cryptography, and stops spoofing only (trusted networks).
- Tests: `tests/net/udp_handshake_test.cpp` (wire helpers; handshake under 0/20/40/60% loss with reordering and duplication, 5 seeds each; 20,000 spoofed packets leave zero connections and the victim gets under a twentieth of the flood; short requests unanswered; replays and cookies older than two periods refused; wraparound at 65535 with reordering and duplication; capacity and address limits; close codes, reset, time-outs) and `tests/net/udp_loopback_test.cpp` (real sockets, labelled `network`).

## Post-implementation code review

`/code-review high`: 5 findings, 4 fixed, 1 declined. The automated security review of the commit then found one more (fixed): the table of closed handshakes, remembered to refuse a replayed response, evicted its oldest entry at 64, so 64 further handshakes let a captured response be replayed within its cookie's life. Entries now live until their cookie period is over (an epoch is stored), a source address may have 64 of them and is denied (`AddressLimit`) beyond that, so one address churning handshakes cannot lock out others; the table (16384) fails closed when full and never evicts an entry whose cookie can still be presented; it is a FIFO with a keyed-hash set and a per-group counter, so every check is O(1) (the third and fourth security-review findings: eviction was a replay hole and a quadratic scan); IPv6 addresses are grouped by /64. A second security-review finding (a global full table locked everyone out) led to the per-address quota; tests: `an address that churns handshakes is denied alone`, and the replay test below with 70 handshakes from 70 addresses in between with 70 handshakes in between (fails with the old eviction, checked).

- Fixed: a peer that had received nothing acknowledged sequence 0 (an ack-valid flag now travels in the first byte); a connection being closed answered the peer's payloads with Reset, racing the Disconnect (suppressed while the Disconnect is repeated); `Poll` rescanned all connections for every queued event and `FindById` was linear (scan only when the queue is empty; id map); `max_connections` above 65535 could reuse a wire id (clamped). Regression tests for the first two fail without their fixes (checked).
- Declined: closing a connection while still handshaking sends nothing, so a server that already accepted holds it until the 10 s time-out (the client does not yet know the server's id; filed in `KNOWN-ISSUES.md`).
